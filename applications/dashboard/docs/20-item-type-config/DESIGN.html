Phase 1 recap (approved for design)

  • Goal: make the tracking-item type list configurable at the system level — an admin can add / rename / reorder / archive types through an admin UI — while the type-specific behaviours certain types carry today are preserved.
  • User decision: "full config with a capability registry", not "just more free-text labels".
  • North-star (hard constraint): Labels are data; capabilities are code. The label list is admin-managed and free to change. The capability set is a fixed, code-owned registry; system types' capabilities are locked; a user can never invent a capability.
  • Backward compatibility is an acceptance criterion: after migration every existing item, the Property lens, and the bond register must behave identically. Renaming BOND → Government Bond must not change any behaviour.

A. Solution Design overview

A.1 Approach in one paragraph

Introduce a new item-type-config capability inside the existing tracking-backend bounded context: one new aggregate ItemType with its own model, Pydantic schemas, service, and router — layered exactly like the existing resources (endpoint → service/helper → model, business logic never in the handler). ft_tracking_item.type (a validated VARCHAR) is replaced as the source of truth by a foreign key ft_tracking_item.type_id → ft_item_type.id. The label / sort order / archived attributes of a type are admin-managed rows; the capabilities a type carries are a small fixed set defined in code and attached to types through a join table that the service writes only within code-enforced rules. Every runtime check that today compares the literal string (== "Property", == "BOND") is replaced by a capability test against a resolved item-type object — item_type.has_capability("counts_as_property") / has_capability("bond_register") on the server, and the equivalent check against a capabilities[] array that the item payload now carries on the client, so the frontend never hard-codes a label again.

B.2 Why one is_archived boolean, not an is_active / status pair

A type has exactly three lifecycle states in Phase 1: created, archived, deleted (custom only). "Archived" is the only reversible transition and it is a pure visibility toggle — capabilities and existing-item validity are unaffected. A second is_active column would always be the logical negation of is_archived and invites the two to drift. A wider status enum would be premature — there is no third non-terminal state. One boolean, one meaning.

B.3 Capability storage — join table vs. array column

OptionProsCons
(a) Join table ft_item_type_capability  RECOMMENDEDQueryable both ways ("which types grant bond_register?" is an indexed lookup, not a JSON scan); clean referential semantics with ON DELETE CASCADE so deleting a custom type drops its rows automatically; adding/removing one capability is a single-row INSERT/DELETE with no read-modify-write race; the whole table is tiny (< ~20 rows ever) so it is loaded once per request and cached (§B.5).One extra table and a join. Neutralised by the cache.
(b) capabilities TEXT[] or JSONB on ft_item_typeOne row read; migration is one ADD COLUMN.Concurrent capability edits are a lost-update hazard (read array, append, write); "types with capability X" needs a GIN index and array containment; no FK-style integrity; harder to reason about in the backup/restore round-trip.

Recommended shape

ft_item_type_capability
  item_type_id    UUID  NOT NULL  REFERENCES ft_item_type(id) ON DELETE CASCADE
  capability_key  VARCHAR(50) NOT NULL
  PRIMARY KEY (item_type_id, capability_key)
  -- capability_key values are validated against the code enum at the service
  -- layer on every write; a DB CHECK is intentionally NOT used so adding a
  -- new capability in a future release is a code-only change, not a migration.

B.5 Resolution & caching

A helper ItemTypeRegistry (request-scoped, or a 60 s TTL cache in the service) loads all ft_item_type rows + their capability rows in one query pair and exposes by_id[uuid] -> ResolvedItemType(slug, label, is_archived, capabilities: frozenset[str]) with has_capability(key) -> bool. The balance-grid service, the bonds gate, and the item router all read from this instead of touching the string. Because the table is a handful of rows the cache removes any per-request latency concern (Risk R-3).

C. FK cutover + backfill migration (design only)

One new Alembic revision, down_revision = "b1c2d3e4f5a6" (suggested id/slug c2d3e4f5a6b7_item_type_config, file 20260910_1200_c2d3e4f5a6b7_item_type_config.py — the exact date/hash is chosen at build time). It is safe to run against a populated, running pre-deploy app because every step is additive until the very end and the old type string stays authoritative for old code.

Ordered upgrade steps

  1. Create ft_item_type and ft_item_type_capability (shapes in §B).
  2. Seed the 7 system rows (is_system = true), sort_order = the current frontend array index, and attach the two capability rows. Label → slug → sort_order → capability map (label is verbatim the current enum string):
    #label (= old type string, verbatim)slugsort_ordercapability rows
    0Bank accountbank_account0—
    1Propertyproperty1counts_as_property
    2Investment Accountinvestment_account2—
    3TaxSavingtax_saving3—
    4Materialsmaterials4—
    5Insuranceinsurance5—
    6BONDbond6bond_register
    Seeds are written with explicit literal UUIDs in the migration (not uuid_generate_v4()) so the same ids exist in every environment and a golden-fixture parity test can pin them.
  3. Add the FK column ft_tracking_item.type_id UUID NULL REFERENCES ft_item_type(id) ON DELETE RESTRICT. Nullable at this point so the running old app (which does not set it) keeps inserting.
  4. Backfill: 
    UPDATE ft_tracking_item t
   SET type_id = it.id
  FROM ft_item_type it
 WHERE it.is_system = true
   AND it.label = t.type;      -- old string == seed label, exact match

-- guard: fail the migration loudly if anything did not map
SELECT count(*) FROM ft_tracking_item WHERE type_id IS NULL;  -- must be 0
    If the guard is non-zero the migration raises (mirrors the ea8407e31992 downgrade guard style) — it means a row holds a type outside the known 7, which must be investigated, not silently defaulted.
  5. Enforce ALTER COLUMN type_id SET NOT NULL and create ix_ft_tracking_item_type_id.
  6. Fate of the old ft_tracking_item.type VARCHAR column — RECOMMEND: keep it, populated, for one release (dual-write), then drop it in a follow-up migration.
    • Keep it as a denormalised read-through of ft_item_type.label. Add a BEFORE INSERT OR UPDATE trigger ft_tracking_item_sync_type: if NEW.type_id IS NOT NULL then NEW.type := (SELECT label FROM ft_item_type WHERE id = NEW.type_id); else leave NEW.type as supplied. The else branch keeps the still-running old app working during the deploy.
    • A type rename in the new admin service must, in the same transaction, UPDATE ft_tracking_item SET type = :new_label WHERE type_id = :id so the denormalised column and every consumer that still reads it (per-set export, the DashboardItemRow.type field, the analysis itemType label) stay correct. This write cost is exactly why the column is temporary — see Risk R-7.
    • Why not an atomic cutover in this one migration? Dropping type now would require the new backend and the new frontend to be already deployed and every read path switched in lock-step; a failed deploy would strand the DB in a state neither app version can read, and rollback would need a data-restore. The dual-write window keeps both app versions functional, keeps the backup files and the per-set export valid, and makes rollback a schema-only operation right up until the follow-up migration.
  7. Drop ck_ft_tracking_item_type in this same migration. Once type_id is NOT NULL and the FK is the integrity guarantee, the 7-value CHECK on the string column would actively break the first custom type (its label is not in the CHECK list) the moment the sync trigger writes it. The FK + ON DELETE RESTRICT is the replacement guarantee.

C.6 Follow-up migration (a later release)

DROP TRIGGER ft_tracking_item_sync_type; ALTER TABLE ft_tracking_item DROP COLUMN type. Precondition: the deployed backend reads type_id everywhere, the per-set export emits typeLabel/typeSlug from the FK (§D), and no consumer reads ft_tracking_item.type.

C.8 Ordering constraints vs. a running app

  • Backfill must complete before SET NOT NULL (step 4 before 5).
  • The migration (steps 1–7) can run while the old app is live: type_id is nullable during the old app's writes and the sync trigger's else branch preserves the old string path.
  • Deploy order for the build engagement: migrate → deploy backend that always sets type_id and reads capabilities → deploy frontend that sends typeId and reads itemType → (later release) follow-up migration to drop the type column.
  • The follow-up column drop must not run until zero code paths read ft_tracking_item.type.

D. Refactor-site inventory

The replacement model everywhere: a resolved item-type object carrying { id, slug, label, isArchived, capabilities[] }. Server checks item_type.has_capability("counts_as_property" | "bond_register"). The item payload (API response, and the DashboardItemRow in the balance grid) carries typeId, typeSlug and either capabilities[] or the single derived boolean countsAsProperty, so the client checks a flag, never a label.

E. API design

Base path /api/v1/tracking/item-types (the service mounts /api/v1/tracking in main.py; the router carries /item-types). Error bodies follow the service's existing convention — FastAPI's {"detail": "..."} — since the rest of tracking-backend does not emit RFC-9457 Problem Details; adopting Problem Details service-wide is a separate effort (OQ-8). Status codes below are the contract regardless of body shape.

E.1 GET /tracking/item-types — list

  • Auth: any authenticated tracker user (get_current_user_id). Needed by every item picker.
  • Query: ?includeArchived=true — default false returns only is_archived = false; true returns all (used by the admin screen and by the item-detail page to resolve an item's own archived type). No auth distinction on this flag — archived types are not secret.
  • Response 200: array, ordered by sort_order asc, then label: 
    [{ "id": "uuid", "slug": "property", "label": "Property",
   "sortOrder": 1, "isSystem": true, "isArchived": false,
   "capabilities": ["counts_as_property"] }]
  • Caching: Cache-Control: private, max-age=60; the client caches under React-Query key ['tracking-item-types'] with staleTime ~5 min, invalidated on any admin mutation.

E.2 POST /tracking/item-types — create custom type

  • Auth: admin only (require_admin).
  • Body: { "label": string (req, 1..100, trimmed, unique case-insensitively), "sortOrder": int? (default = max+1), "capabilities": string[]? (subset of ADMIN_ASSIGNABLE) }.
  • Server sets: slug = slugify(label) with a numeric suffix on collision; isSystem = false; isArchived = false; createdBy = JWT sub.
  • Responses: 201 ItemTypeOut; 400 validation (blank / too long / bad capability key); 409 duplicate label; 403 non-admin; 422 a capability key that is SYSTEM_ONLY or unknown.

E.3 PUT /tracking/item-types/{id} — edit label / order / capabilities

  • Auth: admin only. Presence-aware body: { "label"?, "sortOrder"?, "capabilities"? }. slug is never accepted (ignored or 422).
  • Rules: if the row is_system, capabilities in the body → 422 ("system type capabilities are locked"); label & sortOrder are allowed on system rows. Any capabilities entry not in ADMIN_ASSIGNABLE → 422 (covers bond_register and unknown keys, for every row). Duplicate label → 409.
  • Side effect (transition window): a label change also runs UPDATE ft_tracking_item SET type = :label WHERE type_id = :id in the same transaction (§C.6).
  • Responses: 200 ItemTypeOut; 400/404/409/422/403.

E.4 Archive / unarchive

  • PUT /tracking/item-types/{id}/archive and PUT /tracking/item-types/{id}/unarchive. Admin only. Idempotent.
  • Allowed on system rows (a system type can be archived; it stays valid on existing items and keeps its capabilities).
  • Guard: archiving the last non-archived type → 409 ("at least one active type must remain").
  • Responses: 200 ItemTypeOut; 404; 409; 403.

E.5 DELETE /tracking/item-types/{id}

  • Admin only. 409 when is_system = true ("system types cannot be deleted; archive instead"). 409 when any ft_tracking_item.type_id = id ("N items still use this type"); the FK ON DELETE RESTRICT is the backstop. Otherwise 204 and the capability rows cascade.

E.6 Reorder

RECOMMEND a bulk endpoint, matching the app's existing reorder convention (ReorderRequest = { items: [{ id, order }] }, used by categories / sub-categories / items and by the frontend toOrderItems helper):

PUT /tracking/item-types/order
body: { "items": [ { "id": "uuid", "order": 1 }, ... ] }   # must list every type id
-> 200 { "status": "ok" }   ;  400 if the id set is not exactly the full set

Server rewrites sort_order from the supplied positions in one transaction. (Per-row sortOrder via PUT /{id} also works for a single nudge, but the bulk form keeps the ordering atomic and consistent with the rest of the app.)

E.7 Item create / update contract change

  • RECOMMEND the request field changes from type: string to typeId: uuid on both POST /sub-categories/{id}/items and PUT /items/{id}.
  • Validation (in the endpoint/service, not a field validator — it needs a lookup): typeId must resolve to an ft_item_type row. On create: the row must not be archived → else 400. On update: switching to an archived type → 400; keeping an already-assigned archived type (i.e. typeId unchanged, or omitted) → allowed (Phase-1 BR).
  • Response: TrackingItemOut carries typeId + embedded itemType: ItemTypeOut; also type: string (label) during the transition window for any un-migrated client.

E.8 Bond routes re-gate

_require_bond_item resolves the item's type via the registry and checks has_capability("bond_register"). Unchanged: it runs after _get_item_or_404 (so a cross-user item id is 404, never 400); the failure is still 400 with a {"detail": ...} body; the 5 route paths and their success contracts are untouched. The bond create/update item path itself validates typeId as in E.7.

E.10 require_admin in tracking-backend

async def require_admin(
    credentials: HTTPAuthorizationCredentials | None = Depends(bearer_scheme),
) -> str:
    # identical verify + jti + Redis-blacklist path as get_current_user_id
    payload = verify_token(credentials.credentials)
    ... jti / blacklist checks ...
    if payload.get("role") != "admin":
        raise HTTPException(403, "Admin role required")
    return str(payload["sub"])

This reads the role claim that the main backend already signs into the token — no FK, no query against users, bounded-context isolation intact. It is the recommended answer to the Phase-1 "introduce a real admin boundary" item (OQ-3).

H. ADR-027 — Configurable tracking-item types with a code-owned capability registry

(Draft for the technical-writer to embed into docs/18-financial-tracker/TECHNICAL.html. Status: Proposed.)

Context

Tracking-item type is a closed 7-value enum enforced at three layers. Two types carry hard-wired behaviour: Property drives the dashboard property/non-property split and the Analysis lens; BOND gates a whole CRUD register (ft_bond + 5 routes + a UI section). The business wants admins to add / rename / reorder / archive types without an engineering release, while keeping those behaviours intact and never letting a user invent a behaviour that has no implementation behind it.

Decision

Split the concept in two. (1) A type is a row in a new ft_item_type table with an admin-managed label, sort_order and is_archived, and an immutable code-facing slug. ft_tracking_item.type (validated string) is replaced by an FK type_id. (2) Behaviours are capabilities — a fixed enum defined in code (counts_as_property, bond_register), attached to types through a join table that the service writes only under code rules: system types' capabilities are locked; bond_register is system-only and never grantable; counts_as_property is admin-assignable to custom types. Every runtime == "Property" / == "BOND" check becomes a capability test on a resolved type object; the item payload carries the type's slug + capabilities so the client checks a flag, not a label. The original-investment ledger stays a per-item boolean, unchanged.

Alternatives considered

OptionWhy not
Keep the closed enum, just add more values by migration each time.Fails the requirement — every change is an engineering release; no admin self-service.
Free-text labels only — make type an arbitrary string, drop the CHECK, no capability model.Breaks Property and BOND behaviour immediately (the string checks no longer have a stable target); a user renaming Property silently disables the split; no way to give a new type the property behaviour on purpose.
Full config with a capability registry (chosen).Meets the requirement, preserves behaviour byte-for-byte, keeps "capabilities are code" as a hard boundary, and the join table stays queryable and cache-cheap.
Capabilities as a JSONB/array column instead of a join table.Lost-update races on concurrent edits; weak queryability; messier in backup/restore. Join table chosen.
Atomic string-to-FK cutover in one migration.Requires new backend + frontend deployed in lock-step; a failed deploy strands the DB. Dual-write transition column chosen instead.
Give tracking-backend real RBAC by adding a users FK.Violates the service's bounded-context isolation. The signed JWT already carries a role claim — read that instead.

Consequences

  • Adding/renaming/reordering/archiving a type is an admin action, no deploy.
  • One new FK column, two new tables; the type string lingers as a denormalised column for one release, then is dropped.
  • A new admin boundary exists in tracking-backend, enforced from the token's role claim.
  • Renaming a type touches every item row that references it (to keep the denormalised column correct) during the transition window.
  • The Property lens and bond register are now capability-driven and survive any rename.

Risks

See §J. Principal ones: a missed string-comparison site diverging after cutover; backfill mis-map; lossy rollback once custom types exist; stale client cache after an admin edit.

Rollback

Schema-only and lossless while no custom type exists and no system label was renamed (drop FK + trigger, restore the CHECK, drop the two tables). Past that point the downgrade refuses (guarded), matching the ea8407e31992 precedent.

R-3Capability lookup adds a query per request / per item on hot read paths (balance grid iterates every item).MMItemTypeRegistry loads the whole (tiny) type + capability set in one query pair per request and serves has_capability from memory; optional 60 s process cache. No per-item query.
R-4Dual-write window inconsistency — the denormalised type string drifts from ft_item_type.label.MMA BEFORE INSERT/UPDATE trigger derives type from type_id; renames run UPDATE ft_tracking_item SET type = :label in the same transaction; a reconciliation query is in the runbook; the window is closed by the follow-up drop-column migration.
R-5Rollback is lossy once a custom type exists or a system label was renamed.MHDocumented explicitly (§C.7); the downgrade is guarded and refuses rather than corrupting data; operators are told the safe window ends at first custom-type creation / first rename; take a backup before the migration (backup covers the new tables automatically).
R-6An admin archives a heavily-used type, confusing users who can no longer pick it.MLArchive confirm dialog shows the assigned-item count and states existing items and all totals are unaffected; archived types still resolve on existing items; unarchive is one click; cannot archive the last active type.
R-7Renaming a type rewrites N item rows (denormalised column) — a big type could mean thousands of row updates in one request.LMSingle indexed UPDATE ... WHERE type_id = :id, one statement, inside the rename transaction; this cost exists only during the transition window and vanishes when type is dropped; for very large data the rename can be a background job (noted, not needed at this app's scale).
R-8A type label leaks into an external export / past report and a later rename makes historical documents inconsistent.MLPer-set export carries typeSlug (stable) alongside typeLabel; reports render the current label from the type list; slug is the join key on re-import. Users are warned in the rename dialog that the change is retroactive across reports.
R-9Slug collision when two custom types slugify to the same value (e.g. "Crypto Assets" and "Crypto-Assets").LLSlug generation appends _2, _3… on collision, checked against the unique index inside the create transaction; slug is never shown as primary UI, only the label is.
R-10Frontend cache goes stale after an admin edit — other users keep seeing the old label / options until refetch.MLstaleTime ~5 min + explicit invalidateQueries on every mutation in the admin screen; balance-grid / analysis queries invalidated too; acceptable eventual consistency for a low-churn config list (no realtime requirement).
R-11The new admin boundary rejects a legitimate user because the app currently treats everyone as admin / tokens predate the role claim.MMVerified: the main backend already signs role into every access token today. Build task must confirm all environments issue such tokens and that at least one admin user exists; fallback plan (temporary allow-all) captured in OQ-3.
R-12Item create/update contract change (type → typeId) breaks an un-migrated client or an external caller.LMResponse keeps the type label field during the transition; if any external caller sends type, the endpoint can accept both (resolve type label → id) for one release — flag in OQ-10.

Deployment / migration ordering

  1. Take a backup (covers the new tables automatically).
  2. Run the migration (create + seed + FK + backfill + NOT NULL + trigger + drop CHECK).
  3. Deploy the backend that always sets type_id and reads capabilities.
  4. Deploy the frontend that sends typeId and reads itemType.
  5. Bake for one release; reconcile the denormalised type column.
  6. Later release: follow-up migration to drop ft_tracking_item.type and the sync trigger; switch the per-set export to typeSlug/typeLabel.

Rollback checkpoint

Lossless schema-only downgrade is available only until the first custom type is created or the first system label is renamed. Past that, the downgrade is guarded and refuses. The build's deployment plan must state this explicitly and require a fresh backup immediately before step 2.
