Backup & Restore — Technical Design

Version: 2.0  ·  Last updated: 2026-09-01  ·  Owner: Dashboard backend team  ·  Audience: backend / platform engineers.

This document describes the in-app database backup and restore feature: the dynamic table-discovery model, the backup file format (v2.0), the restore transaction and rollback semantics, the PostgreSQL privilege requirement, and the operational configuration. It is written to be sufficient to rebuild the feature from scratch.

1. Goals and scope

  • Total coverage. A full backup must contain every application table in the investment_db database — including tables owned by the sibling tracking-backend service (ft_*) that share the same physical database — with no hard-coded table list to maintain.
  • Non-destructive by default. A restore must never silently overwrite a populated database. Destroying data requires an explicit mode plus a typed confirmation phrase.
  • Schema-version isolation. The Alembic bookkeeping tables (alembic_version, ft_alembic_version) are captured for reference but never written by a restore. A data restore must not roll a schema forward or backward.
  • Integrity signalling. Each table carries a SHA-256 checksum so a restore can detect a backup file that was edited after it was written.
  • Injection-safe. Every dynamically built SQL identifier is validated against the live catalogue and quoted; every value is a bound parameter.
  • Admin-only. Every endpoint is guarded by the require_admin FastAPI dependency.

2. Shared-database / two-service ownership

investment_db is a single PostgreSQL 16 database used by two services:

Owning serviceTablesMigrated bySchema-version table

The backup code lives in the backend service but reads and writes the ft_* tables directly. This is only possible because both services connect as the same PostgreSQL role (a superuser) in this deployment — see §7, Privilege requirement.

3. Dynamic table discovery

On every call to create, restore and GET /backup/tables, the table set and a foreign-key-safe insert order are derived from the live PostgreSQL catalogue. No table list is stored in code.

3.1 Catalogue queries

-- base tables in schema public (backup.py :: _discover_tables)
SELECT c.relname AS name
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
  AND NOT c.relispartition
  AND n.nspname = 'public';

-- foreign-key edges  (child, parent)  (backup.py :: _fk_edges)
SELECT c.relname AS child, p.relname AS parent
FROM pg_constraint con
JOIN pg_class c      ON c.oid = con.conrelid
JOIN pg_class p      ON p.oid = con.confrelid
JOIN pg_namespace n  ON n.oid = c.relnamespace
JOIN pg_namespace pn ON pn.oid = p.relnamespace
WHERE con.contype = 'f' AND n.nspname = 'public' AND pn.nspname = 'public';

Because discovery is purely catalogue-driven, a table added by a future migration in either service — for example ft_bond from the Financial Tracker bond register — is included in the next backup with no code change. A table that exists in the database but no longer has an ORM model is also captured.

3.2 Topological sort (services/backup/__init__.py :: toposort)

A deterministic Kahn topological sort turns the FK edge list into an insert order where every parent precedes its children.

RuleBehaviour
Edge direction(child, parent) read as “parent must be inserted before child”.
Self-referential FK (child == parent)Dropped. The row-level ordering inside such a table is handled by session_replication_role = replica during restore.
Edge to an unknown nodeIgnored.
Duplicate edgesCollapsed.
Tie-breakThe ready set is always drained in alphabetical order, so the output is identical regardless of catalogue row order.
FK cycleUnresolved nodes are appended sorted by name and a warning is logged. Cyclic inserts succeed because FK checks are deferred during the load.

TRUNCATE order for a destructive restore is simply reversed(insert_order).

3.3 Covered vs excluded tables

covered = [t for t in discovered if t not in {"alembic_version", "ft_alembic_version"}]. The two schema-version tables are excluded from the tables payload block and from the restore write path; they are captured separately (see §4).

Coverage at ship date (2026-09-01): 28 covered tables reported by GET /api/v1/backup/tables, plus the 2 excluded schema-version tables. 27 of the covered tables map to current ORM models across the two services (19 backend + 8 ft_*); dynamic discovery also captures any additional table present in the live database. The authoritative, always-current list is the response of GET /api/v1/backup/tables.
⚠ Assumption: the “28” figure is taken from the delivery hand-off notes and reflects the live catalogue on the ship date; it is expected to grow as migrations land.

4. Backup file format v2.0

A backup is a gzip-compressed JSON object. Stored files are named backup_<YYYYMMDD_HHMMSS>.json.gz (UTC timestamp) under BACKUP_DIR with permissions 0o600.

4.1 Top-level keys

KeyTypeMeaning
versionstringAlways "2.0" for files written by this build.
created_atstringISO-8601 UTC timestamp of the backup.
created_bystringUUID of the admin user who ran the backup.
source_dbstring"investment_db".
generatorstring"backend/backup@2.0".
covered_tablesstring[]Every table in the backup, in FK-safe insert order.
insert_orderstring[]Identical to covered_tables. TRUNCATE order is the reverse.
excluded_tablesobject{table: reason} for the schema-version tables.

schema_versionsobject{alembic_version: [{version_num: "..."}], ft_alembic_version: [...]}. Empty list if the table is absent.
tablesobject{table: [row objects]}. Does not contain the schema-version tables.

4.2 Value normalisation

One serialiser, services/backup/__init__.py :: json_default_payload, is used for both the tables block and the checksum input:

Python typeOn disk
UUIDstring
datetime / dateISO-8601 string
Decimalfloat
bytes / bytearray / memoryviewbase64 ASCII string
anything else unexpectedTypeError — the backup fails loudly rather than dropping a column
Fidelity caveat. The Decimal → float step can round a high-precision NUMERIC. Because the checksum is computed over the already-normalised shape, that rounding is invisible to the checksum. The checksum detects post-backup modification of the file, not divergence from the source database.

4.3 Per-table checksum

table_checksum(rows) =
  "sha256:" + sha256( "\n".join( sorted( json.dumps(row, sort_keys=True, default=json_default_payload)
                                         for row in rows ) ) ).hexdigest()

Sorting the per-row JSON strings makes the digest independent of the row order the database returned. A restore recomputes the digest from the file contents and compares: ok (match), mismatch (file edited), or skipped (no checksum present, e.g. a legacy file).

4.4 Legacy (pre-2.0) files

A file is handled by the legacy path when its version is "1.0", "1.1" or absent, or it is missing the covered_tables or checksums key. Legacy restores:

  • Report legacy_backup: true and mode: "legacy".
  • List uncovered_tables (live tables absent from the file) and file_tables_not_in_db.
  • Return checksum_verification as "skipped" for every table and an empty schema_version_drift.
  • Apply the same conflict / confirm policy as the v2.0 path — a legacy file cannot implicitly TRUNCATE a populated database.

A version that is a non-empty string but is neither "2.0" nor a known legacy value is rejected with 400 urn:backup:error:unsupported-version before any work is done.

5. Restore semantics

Two modes, selected by the mode field (body for the stored-file endpoint, query parameter for the upload endpoint). Default: skip_if_conflict.

5.1 mode=skip_if_conflict (default, safe)

  1. Acquire pg_advisory_xact_lock(917283641) and SET LOCAL statement_timeout = '30s'.
  2. Version gate; parse tables; discover live tables and compute the insert order restricted to covered ∩ live.
  3. Pre-write conflict check: SELECT 1 FROM <t> LIMIT 1 for each covered table (the two schema-version tables are never checked).
  4. If any covered target table is non-empty → ROLLBACK and return 409 application/problem+json urn:backup:error:target-not-empty with conflicting_tables: [{table, row_count}]. Nothing is written.
  5. Otherwise: load every covered table in insert order, then COMMIT.

5.2 mode=replace_all (destructive)

  1. The request must carry confirm equal to the verbatim string REPLACE ALL DATA. Otherwise → ROLLBACK, 400 urn:backup:error:confirm-required.
  2. Validate that no column in the file is absent from the live schema (urn:backup:error:unknown-column, 422, with errors).
  3. SET LOCAL session_replication_role = replica (see §7).
  4. TRUNCATE TABLE <t> CASCADE for each table in reverse insert order — only for tables in covered ∩ live.
  5. Bulk-insert every covered table in insert order (chunks of 1000 rows).
  6. Any row failure → the whole transaction ROLLBACKs and the endpoint returns 422 urn:backup:error:restore-failed with a per-table errors list. There is no partial restore.
  7. Otherwise COMMIT.

5.3 Invariants that hold on both modes and both (v2.0 / legacy) paths

  • One transaction. The advisory lock opens it; an explicit commit / rollback closes it on every code path. SET LOCAL statements therefore auto-revert and never leak into the pooled connection.
  • Tables in the DB but absent from the backup are left untouched — they are neither truncated nor inserted into.
  • Schema-version tables are never written. After the load, drift is reported as schema_version_drift: {name: {file, live, match}} comparing the file's version_num against the live value.
  • Identifiers are validated against the live catalogue / information_schema.columns and double-quoted via safe_ident. Values are positional bind parameters (p0, p1, …) so a column name such as as of cannot corrupt the parameter list.
  • Type coercion on insert (_coerce): ISO strings → datetime / date; base64 → bytes for bytea; nested object → JSON text for json / jsonb; "true"/"t"/"1"/"yes" → bool.

6. Concurrency

  • create_backup and _do_restore each take pg_advisory_xact_lock(917283641) as their first statement. The same key means a backup and a restore (or two of either) serialise instead of racing; the lock is released automatically when the transaction ends.
  • SET LOCAL statement_timeout = '30s' bounds every statement in create, _do_restore and GET /backup/tables.
  • There is no HTTP-level rate limit or semaphore on POST /backup/create — see §10.

7. PostgreSQL privilege requirement

The restore path issues SET LOCAL session_replication_role = replica to defer foreign-key and trigger enforcement during the bulk load. This command requires a superuser role (or a role with the replication attribute). If the role cannot set it, the restore fails fast with 500 urn:backup:error:insufficient-privilege and the message “backup restore requires a superuser-capable DB role”. The transaction is rolled back; nothing is written.
  • POST /backup/create and GET /backup/tables do not need this privilege — they only read.
  • Because backup.py runs in the backend service but also reads / writes the ft_* tables, the backend DB role must hold SELECT, INSERT, TRUNCATE and TRIGGER on the ft_* tables.
  • In this deployment both services connect as the same postgres superuser, so both conditions already hold. If the roles are ever split, these grants and the superuser/replication attribute on the backend role must be preserved or restore breaks.

8. Backup-file path containment

Every endpoint that takes a {filename} path parameter (download, DELETE, restore/{filename}) routes it through _resolve_backup_path, which rejects with 400 urn:backup:error:invalid-filename when the name:

  • contains /, \ or a NUL byte;
  • is . or ..;
  • does not match backup_*.json.gz;
  • after resolution does not sit directly in BACKUP_DIR (this also catches a symlink pointing outside the directory).

9. Upload restore — bounded decompression

POST /backup/restore/upload streams the uploaded gzip through _bounded_gunzip, which aborts as soon as the decompressed output would exceed BACKUP_MAX_UNCOMPRESSED_BYTES (default 200 MiB), returning 413 urn:backup:error:too-large with limit_bytes. This defends against a decompression bomb. mode and confirm are query parameters so the multipart body stays a single file part.

11. Error model

All backup endpoints emit application/problem+json (RFC 7807 / RFC 9457) on error:

{
  "type":   "urn:backup:error:target-not-empty",
  "title":  "Conflict",
  "status": 409,
  "detail": "target database already contains data for one or more covered tables; retry with mode=replace_all to overwrite",
  "instance": "/api/v1/backup/restore/backup_20260901_021407.json.gz",
  "mode": "skip_if_conflict",
  "conflicting_tables": [ { "table": "users", "row_count": 4 } ]
}

A top-level detail string is always retained for older frontend clients that read error.detail. DB error messages are scrubbed to the exception class name only — never SQL text, DSNs or filesystem paths. The full catalogue of urn:backup:error:* types and status codes is in API-BACKUP.html §Error catalogue. 401 (no token) and 403 (non-admin) come from require_admin as ordinary FastAPI {"detail": …} bodies.

12. PSV per-table export / import

A lighter-weight path for moving a single table, used by the “Per-Table Export / Import” panel in the UI.

  • Format: pipe-separated. Line 1 is the header (column names); each following line is one row. NULL is the empty field; a literal | is escaped \|, a newline \n; json/jsonb values are embedded as JSON.
  • GET /backup/export-table/{table} → text/plain attachment <table>_<YYYYMMDD_HHMMSS>.psv.
  • POST /backup/import-table/{table}?mode=append|replace&confirm=…. append → INSERT … ON CONFLICT DO NOTHING. replace → TRUNCATE … CASCADE first and requires confirm == REPLACE <table>.
  • Both directions reject the schema-version tables with 400 urn:backup:error:schema-version-table.
  • The uploaded header is validated against information_schema.columns for the real target; unknown columns → 422 urn:backup:error:unknown-column. Import runs under session_replication_role = replica in one transaction; failure → ROLLBACK + 422 urn:backup:error:import-failed.

13. Frontend integration

See FUNCTIONAL.html for the full UX. Key wiring:

  • GET /backup/tables feeds the collapsible coverage card and the PSV table selector. The selector filters out rows with restorable === false or in_conflict_check === false (the schema-version tables); the coverage card still lists them with their note.
  • The wipe preview shown for a replace-all restore is tables.filter(t => t.in_conflict_check && t.row_count > 0).
  • RestoreModal.tsx owns the mode choice. The submit button is disabled until mode === 'skip_if_conflict' or the typed text equals REPLACE ALL DATA. A 409 response is caught and its conflicting_tables rendered inline so the admin can switch to replace-all without losing context.

16. Feature rollback

The feature adds no database migration — it only reads and writes existing tables. To remove it:

  1. Revert backend/app/api/v1/endpoints/backup.py, backend/app/services/backup/, backend/app/schemas/backup.py, and the router registration.
  2. Revert the frontend files frontend/src/app/(dashboard)/settings/backup/page.tsx and RestoreModal.tsx (and the route entry).
  3. Backend hot-reloads; rebuild and redeploy the frontend (docker compose build frontend && docker compose up -d --no-deps frontend).
  4. Existing backup_*.json.gz files under BACKUP_DIR are inert and can be deleted at leisure.
