Backup & Restore — Functional Specification

Version: 2.0  ·  Last updated: 2026-09-01  ·  Audience: administrators (the page is admin-only)  ·  Location in app: Settings → Backup (/settings/backup).

The Backup & Restore page lets an administrator take a full snapshot of the application database, restore one, and move individual tables in and out as pipe-separated files. Every table in the shared investment_db database is covered — including the Financial Tracker (ft_*) tables owned by the separate tracking-backend service.

Related: Technical Design · Operations Runbook · API reference · Database schema

1. Access

  • The page is visible only to users with the admin role and every endpoint is enforced server-side by require_admin. A non-admin who navigates directly to the URL gets 403 on every call.
  • An “Admin only” badge is shown in the page header.

2. Coverage card

A collapsible card at the top of the page summarises what a backup will contain, from GET /api/v1/backup/tables.

  • Header: “Covers N tables”, the database name, and the snapshot timestamp.
  • Expanded list — one row per table with:
    • table name;
    • current row count;
    • an owner-service badge: backend or tracking-backend (the ft_* tables);
    • for the two schema-version tables (alembic_version, ft_alembic_version) an italic note explaining they are “managed by Alembic migrations, never restored”.

The list reflects the live database at the moment it was loaded, so a table added by a future migration appears automatically with no app update.

3. Full database backup

3.1 Create a backup

  • Create Backup button → POST /api/v1/backup/create.
  • The server writes a gzip-compressed JSON file backup_<UTC timestamp>.json.gz to the server-side backup directory, readable only by the service account.
  • On success a green result box shows the file name, and the “Stored Backups” list refreshes.
  • Only the newest 7 backups are kept on the server; older ones are deleted automatically after each successful create.

3.2 Stored backups list

Each stored file shows its name, creation date/time and size, with three actions:

ActionBehaviour
DownloadDownloads the .json.gz file to the admin's machine.
RestoreOpens the Restore dialog (§4) for that stored file.
DeleteAsks for confirmation, then permanently deletes the stored file.

3.3 Restore from a local file

Upload & Restore lets the admin pick a .json / .json.gz file from their machine; it opens the same Restore dialog (§4). The upload is size-capped after decompression; an oversized file is rejected with a clear message.

4. Restore dialog

Replaces the old blind browser confirm with an explicit, keyboard-accessible dialog (Esc closes it). It forces a deliberate choice of restore mode.

4.1 Safe restore — “only into empty tables” (default)

  • Sends mode=skip_if_conflict.
  • Before writing anything, the server checks whether any covered table already holds data.
  • If every covered table is empty, the restore proceeds and the result box shows per-table row counts.
  • If any covered table already has rows, nothing is written. The dialog shows an amber panel: “These tables already contain data” with the table names and row counts, and suggests switching to Replace all data or restoring into a fresh database.

This is the correct path for rebuilding a brand-new / empty environment from a backup.

4.2 Replace all data (destructive)

  • Selecting this radio reveals a red panel listing exactly which tables and how many rows will be permanently deleted (the populated covered tables).
  • The admin must type REPLACE ALL DATA verbatim into a text field. The confirm button stays disabled until the text matches exactly.
  • On confirm, the server wipes every covered table and reloads it from the backup, all in a single transaction. If any row fails to load, the entire restore is rolled back and an error with the failing tables is shown — the database is left as it was.
  • Tables that exist in the database but are not in the backup file are left completely untouched.

4.3 Result and diagnostics

After any restore the result box can show:

SectionMeaning
Restored rowsPer-table count of rows loaded.
Checksum verificationPer-table chip: ok (file intact), mismatch (the backup file was modified after it was created — treat the data as suspect), skipped (no checksum in the file, e.g. an old backup).
Schema version driftAmber warning when the migration version recorded in the backup differs from the live database (file X → live Y). The schema-version tables themselves are never changed by a restore — this is informational, telling you the backup was taken against a different schema.
Legacy backup formatAmber banner when an older (pre-2.0) backup was restored, listing any tables that were not present in that older file.
ErrorsAny per-table failure messages (restore was rolled back).

5. Per-table export / import (PSV)

A collapsible panel for moving one table at a time as a pipe-separated (|) text file — useful for spot fixes and for copying a single table between environments.

  • Table selector — lists every restorable table. The two schema-version tables are deliberately not offered (the server rejects them anyway).
  • Export — downloads <table>_<date>.psv: a header row of column names, then one line per row. Empty field = NULL; JSON values are preserved; a literal | in a value is written as \|.
  • Import — Append — adds rows, skipping any that collide with an existing key (ON CONFLICT DO NOTHING).
  • Import — Replace — empties the table first, then loads the file. The admin must type REPLACE <table> verbatim to unlock the import button.
  • Unknown column names in the uploaded header are rejected with a clear message; a failed import is rolled back entirely.

6. What a backup contains — and the sensitivity of the file

A full backup contains every row of every application table, including users with password hashes and any personal data held in the platform. Backup files are not encrypted. Treat a downloaded .json.gz as a credential-bearing secret: store it somewhere access-controlled and delete copies you no longer need. See the Runbook for handling guidance.
