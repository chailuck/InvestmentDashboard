Runbook: Database Backup & Restore

Version: 1.0  ·  Last updated: 2026-09-01  ·  Owner: Dashboard backend team  ·  Estimated duration: backup < 1 min; restore 1–5 min depending on data volume.

Operational procedures for the in-app Settings → Backup feature: taking a backup, where files live, restoring into an empty or a populated database, what the error codes mean, and how to recover. Design detail is in TECHNICAL.html; the endpoint contract is in API-BACKUP.html.

1. Preconditions

  • You are logged in as a user with the admin role.
  • All containers are healthy: docker compose ps shows inv_backend, inv_postgres (and, if the Financial Tracker is deployed, the tracking-backend) as Up (healthy).
  • The backend service's PostgreSQL role is superuser-capable (needed for restore — see §5). In this deployment both services connect as the postgres superuser, so this holds by default.
  • For a restore: you have the correct backup_*.json.gz file, either already in the stored list or on your machine.
  • Disk headroom in the uploads_data Docker volume for at least BACKUP_RETENTION (default 7) backup files.

Verify the DB role can perform a restore

docker exec inv_postgres psql -U postgres -d investment_db -tAc \
  "SELECT rolsuper OR rolreplication FROM pg_roles WHERE rolname = current_user;"
# Expected: t

2. Where backup files live

PropertyValue
Directory (in container)BACKUP_DIR, default /app/uploads/backups
Docker volumeuploads_data (mounted at /app/uploads in inv_backend)
File namebackup_<YYYYMMDD_HHMMSS>.json.gz (UTC)
Permissions0o600 (owner read/write only)
RetentionNewest BACKUP_RETENTION files (default 7); older ones deleted after each successful create
EncryptionNONE — see the warning below
Sensitivity. A backup file is a full dump of every table, including users.hashed_password and all personal data. It is not encrypted at rest. It is protected only by (a) the 0o600 file mode inside a Docker volume and (b) the admin-authenticated download endpoint. When you download a copy: keep it on access-controlled storage, never commit it to git, never attach it to a ticket or chat, and delete it when done. Planned hardening: envelope/AES-GCM encryption with a KMS-held key.

Inspect stored files directly

docker exec inv_backend ls -la /app/uploads/backups
docker exec inv_backend sh -c 'gzip -dc /app/uploads/backups/backup_YYYYMMDD_HHMMSS.json.gz | head -c 600'

3. Procedure — take a backup

  1. Open Settings → Backup (/settings/backup).
  2. (Optional) Expand the coverage card and confirm the table list and row counts look right.
  3. Click Create Backup. Wait for the green result box (“Backup created: backup_…json.gz”).
  4. The new file appears at the top of Stored Backups.
  5. If you need an off-box copy, click Download and move the file to access-controlled storage.

API equivalent (admin bearer token):

curl -sS -X POST https://<host>/api/v1/backup/create \
  -H "Authorization: Bearer $ADMIN_TOKEN" | jq '{filename, total_rows, version, covered_tables: (.covered_tables|length)}'

Validation

  • Result box shows a filename and a non-zero total_rows.
  • GET /api/v1/backup/list shows the file with version: "2.0" and a covered_table_count matching the coverage card's table count.
  • Optional integrity spot check: download the file, then gzip -dc backup_*.json.gz | jq '.version, (.tables | keys | length), .checksums | keys | length'.

4. Procedure — restore into a fresh / empty database (safe mode)

Use this when standing up a new environment or recovering after a docker compose down -v.

  1. Bring the stack up so the schema exists but holds no data: 
    cd applications/dashboard
docker compose up -d postgres redis backend
docker exec inv_backend alembic upgrade head          # backend schema
# if the Financial Tracker is deployed:
docker exec inv_tracking_backend alembic upgrade head  # ft_* schema
    The admin user is seeded on first backend startup from ADMIN_EMAIL / ADMIN_PASSWORD. That single row does not trip the safe-mode conflict check on its own only if users is still empty — if the seed already ran, users has a row and safe mode will report a conflict on users. In that case use §5 (replace-all) or truncate users first.
  2. Log in as admin → Settings → Backup.
  3. Either click Restore on a stored file, or Upload & Restore and pick your .json.gz.
  4. In the dialog keep the default “Safe restore — only into empty tables” and click Restore.
  5. Wait for the green result box with per-table row counts.

API equivalent:

curl -sS -X POST "https://<host>/api/v1/backup/restore/backup_YYYYMMDD_HHMMSS.json.gz" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"mode":"skip_if_conflict"}'

Validation

  • Result: errors is empty; restored row counts match the backup's row_counts.
  • checksum_verification is ok for every table (or skipped for a legacy file).
  • Spot-check the app: users can log in, portfolios/plans/scans render.
  • Review schema_version_drift — if match: false, the backup was taken on a different schema; run alembic upgrade head and verify the app, or restore a backup that matches the current schema.

5. Procedure — destructive restore (replace_all)

This permanently deletes the current contents of every covered table before reloading. Take a fresh backup first (§3).
  1. Take and download a current backup (§3) as a safety net.
  2. Settings → Backup → Restore / Upload & Restore.
  3. In the dialog choose “Replace all data (destructive)”.
  4. Read the red panel listing the tables and row counts that will be deleted.
  5. Type REPLACE ALL DATA exactly into the confirmation field.
  6. Click Replace all data. The wipe + reload runs in one transaction.

API equivalent:

curl -sS -X POST "https://<host>/api/v1/backup/restore/backup_YYYYMMDD_HHMMSS.json.gz" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"mode":"replace_all","confirm":"REPLACE ALL DATA"}'

# From a local file instead (mode/confirm are QUERY params):
curl -sS -X POST "https://<host>/api/v1/backup/restore/upload?mode=replace_all&confirm=REPLACE%20ALL%20DATA" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -F "file=@backup_YYYYMMDD_HHMMSS.json.gz"

Validation

  • HTTP 200 with mode: "replace_all", empty errors, expected total_rows.
  • Tables present in the DB but absent from the backup are unchanged (check one you know the backup did not include, if any).
  • App smoke test as in §4.

6. Error / status reference

HTTPtypeMeaningOperator action
400urn:backup:error:confirm-requiredReplace-all requested without the exact phrase REPLACE ALL DATA (PSV: REPLACE <table>).Re-issue with the exact confirmation string. Nothing was written.
400urn:backup:error:unsupported-versionFile's version is not 2.0 and not a known legacy value.Use a backup produced by this build, or a genuine v1.0/1.1 file.
400urn:backup:error:invalid-fileNot gzip/JSON, or missing the tables object.File is corrupt or not a backup. Try another; re-download if the copy is bad.
400urn:backup:error:invalid-filenamePath-traversal or malformed name on a {filename} route.Use the name exactly as shown in GET /backup/list.
409urn:backup:error:target-not-emptySafe restore: one or more covered tables already hold data. Nothing written.Restore into an empty DB, or switch to replace_all (§5). Response lists conflicting_tables.
413urn:backup:error:too-largeUploaded backup exceeds BACKUP_MAX_UNCOMPRESSED_BYTES (200 MiB) decompressed.Restore from a server-side stored file instead, or raise the limit env var and restart the backend.
422urn:backup:error:unknown-columnThe file has a column that does not exist in the live schema.Schema/file mismatch. Align the schema (alembic) to the backup's era, or use a matching backup. Nothing written.
422urn:backup:error:restore-failedA table failed during load; the whole restore was rolled back.Read errors for the offending table. Common cause: schema drift. DB is unchanged — fix and retry.
500urn:backup:error:insufficient-privilegeThe DB role cannot SET session_replication_role = replica.Grant the backend role superuser / replication (see §1), restart backend, retry. Backup + coverage card are unaffected.
403(FastAPI detail)Caller is not an admin.Use an admin account.

7. Rollback

7.1 A restore went wrong

Because every restore is a single transaction, a failed restore (409, 422, 500) leaves the database exactly as it was — no rollback needed. If a successful replace_all restored the wrong file:

  1. Run replace_all again with the safety-net backup you took in §5 step 1.
  2. If you have no safety net but Postgres data is intact, restore from the most recent known-good backup_*.json.gz in the stored list via replace_all.
  3. Last resort — restore the Postgres volume from an infrastructure-level snapshot (out of scope for this feature).

7.2 Roll back the feature itself

No database migration is involved. Revert the code and redeploy:

# backend (hot-reloads on save; restart only if requirements changed)
git revert <commit(s) touching backend/app/api/v1/endpoints/backup.py, backend/app/services/backup/, backend/app/schemas/backup.py>

# frontend (must rebuild)
git revert <commit(s) touching frontend/.../settings/backup/page.tsx, RestoreModal.tsx>
docker compose build frontend && docker compose up -d --no-deps frontend

Existing backup_*.json.gz files under BACKUP_DIR become inert and can be deleted at leisure.

8. Common failures & recovery

Create hangs, then times out (~30 s)Another create/restore holds pg_advisory_xact_lock(917283641), or a long-running query; statement_timeout fired.Wait for the other operation to finish and retry. Check pg_stat_activity for blockers.
Restore reports checksum_verification: mismatchThe backup file was modified after it was created.The data may be tampered/corrupt. Prefer a different, intact backup. If you must use it, verify the affected tables manually after restore.
schema_version_drift.match = falseBackup taken against a different migration head.Run alembic upgrade head in the relevant service and re-test the app; or use a backup that matches the current schema.
Legacy banner + tables missingRestored a pre-2.0 backup that predates some tables.Expected. Load the missing tables separately (PSV) if you have the data.

10. Escalation

  • First responder: the acting administrator.
  • Owning team: Dashboard backend team (feature code in backend/app/api/v1/endpoints/backup.py).
  • Escalate to the backend team when: a successful restore left the app inconsistent; insufficient-privilege appears in a deployment that previously worked; repeated restore-failed that is not explained by schema drift; or a suspected tampered backup (checksum mismatch) whose provenance matters.
  • Data-protection note: if an unencrypted backup file is exposed to an unauthorised party, treat it as a credential + personal-data incident (it contains password hashes and PII) and follow the organisation's incident process.
