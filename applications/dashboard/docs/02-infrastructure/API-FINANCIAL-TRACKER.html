API Spec — Financial Tracker

Objective: Full CRUD for the Financial Tracker ("Tracking") feature — Tracking Sets, Categories, Sub-categories, Tracking Items, Initial Investment Ledger entries (Phase 1), and Update Tracking Lists with read-time balance deltas (Phase 2). Served by the independent tracking-backend microservice. No "Dashboard" (quarterly/annual rollup reporting) endpoints exist yet. All routes are mounted under /api/v1/tracking.
Deployment note: the Next.js proxy (frontend/src/app/api/proxy/[...path]/route.ts) does not currently route /api/v1/tracking/* requests to this service — see 18-financial-tracker/TECHNICAL.html §8.1 / §10 (TD-FT-01). The endpoints below are accurate to the running tracking-backend service reachable directly on port 8001; the browser-facing path through the frontend proxy is not yet wired to it.

Authentication

All endpoints except /health/* require Authorization: Bearer <access_token>, where the token was issued by the main backend's login endpoint. tracking-backend only verifies the token (shared APP_SECRET_KEY, same Redis blacklist) — it never issues tokens itself. See TECHNICAL.html §2 for the full verification flow.

Health

GET /api/v1/tracking/health/live

No auth. Never touches the database or Redis — always returns fast so an orchestrator cannot mistake a transient dependency blip for a dead process.

{ "status": "ok" }

GET /api/v1/tracking/health/ready

No auth. Checks Postgres (SELECT 1) and Redis (PING).

// 200 OK — both dependencies healthy
{ "status": "ok", "checks": { "database": "ok", "redis": "ok" } }

// 503 Service Unavailable — one dependency down
{ "status": "unavailable", "checks": { "database": "ok", "redis": "error: Connection refused" } }

Initial Investment Ledger

Ledger endpoints (POST/GET .../entries, GET .../running-total) are gated at the application layer: the target Tracking Item's initialInvestmentTracking flag must already be true, or these endpoints reject the call with 400 — even though the underlying ft_initial_investment_entry table has no DB-level constraint tying it to the flag.

POST /api/v1/tracking/items/{itemId}/entries

// Request — amount must be non-zero; positive = increase, negative = decrease
{ "amount": 50000.00, "entryDate": "2026-01-15" }

// Response 201
{
  "id":              "f5a6b7c8-...",
  "trackingItemId":  "e4d5f6a7-...",
  "amount":          50000.00,
  "entryDate":       "2026-01-15",
  "createdAt":       "2026-08-23T09:30:00+00:00",

}

404 Not Found — item not found.
422 Unprocessable Entity — amount is zero: "amount must not be zero (positive = increase, negative = decrease)"

Update Tracking Lists (Phase 2)

Periodic balance snapshots ("updates") against a Tracking Set's category/sub-category/tracking-item hierarchy, plus read-time delta computation against the immediately preceding snapshot. Implemented in app/api/v1/endpoints/update_tracking_lists.py. Two URL families share this one router — nested /sets/{setId}/update-lists for header create/list, and standalone /update-lists/{listId}... for everything else — mirroring how tracking_sets.py already nests /sets/{setId}/categories. See 18-financial-tracker/FUNCTIONAL.html §11 for user-facing behaviour and 18-financial-tracker/TECHNICAL.html §7 for the delta-computation algorithm.

Update Tracking List header response shape

{
  "id":                "a1b2c3d4-...",
  "trackingSetId":     "b1a2c3d4-...",
  "transactionDate":   "2026-06-30",
  "quarter":           2,
  "year":              2026,
  "createdAt":         "2026-08-25T09:00:00+00:00",
  "updatedAt":         "2026-08-25T09:00:00+00:00"
}
FieldTypeNotes
quarterinteger, nullable1-4. Independent of year — either may be set/cleared without touching the other.
yearinteger, nullablee.g. 2000-2100. Independent of quarter.
Replaces the former free-text quarterYearLabel field (migration 20260827_1000_d112fa78e9c2_split_quarter_year_label_into_quarter_and_year). quarter and year are independently settable or clearable via the partial-update endpoint below — passing one without the other leaves the untouched field as-is.

POST /api/v1/tracking/sets/{setId}/update-lists

// Request — transactionDate required; quarter and year independently optional
{ "transactionDate": "2026-06-30", "quarter": 2, "year": 2026 }

// Response 201 — full header object (see shape above)
404 Not Found — parent tracking set not found: {"detail": "Tracking set not found"}
No uniqueness check is applied — creating a second list with the same transactionDate for the same set succeeds and produces two independent rows. See TECHNICAL.html §3 for why.

GET /api/v1/tracking/update-lists/{listId}/detail

Returns the tracking set's current category → sub-category → tracking-item hierarchy — not a structural snapshot frozen at list-creation time — with each item's balance on this list, its balance on the chronologically previous list in the same set, and the computed delta. Note the item/category/sub-category ordering field in this response is orderIndex, not the order alias used by the plain Category/SubCategory/TrackingItem endpoints above.

// Response 200
{
  "list": {
    "id": "a1b2c3d4-...", "trackingSetId": "b1a2c3d4-...",
    "transactionDate": "2026-06-30", "quarter": 2, "year": 2026,
    "createdAt": "...", "updatedAt": "..."
  },
  "previousListId": "9f8e7d6c-...",
  "categories": [
    {
      "id": "c2b3d4e5-...", "name": "Assets", "orderIndex": 0,
      "subCategories": [
        {
          "id": "d3c4e5f6-...", "name": "Current Assets", "orderIndex": 0,
          "items": [
            {
              "id": "e4d5f6a7-...", "name": "SCB Savings Account", "type": "Bank account", "orderIndex": 0,
              "balance": 105000.00, "previousBalance": 100000.00,
              "deltaAmount": 5000.00, "deltaPercent": 5.00, "hasPreviousData": true
            },
            {
              "id": "f5a6b7c8-...", "name": "New item added this quarter", "type": "Bank account", "orderIndex": 1,
              "balance": null, "previousBalance": null,
              "deltaAmount": null, "deltaPercent": null, "hasPreviousData": false
            }
          ]
        }
      ]
    }
  ]
}
Reading the delta fields: hasPreviousData=false means either this is the first list for the set, or this item had no balance recorded on the previous list — the UI must show a "no data" indicator, not a fabricated zero. When hasPreviousData=true but the previous balance was exactly 0, deltaAmount is still computed but deltaPercent is null (division by zero is avoided deliberately, not a bug). All four delta-related fields are computed fresh on every call — never cached or stored — so editing an older list's balance changes what this response returns on the very next call.
404 Not Found — list not found: {"detail": "Update tracking list not found"}

PUT /api/v1/tracking/update-lists/{listId}/balances

// Request — bulk upsert; balance may be a number or null (null clears/records "no value")
{
  "balances": [
    { "trackingItemId": "e4d5f6a7-...", "balance": 105000.00 },
    { "trackingItemId": "f5a6b7c8-...", "balance": null }
  ]
}

// Response 200 — the written balance rows
[
  {
    "id": "1a2b3c4d-...", "updateTrackingListId": "a1b2c3d4-...",
    "trackingItemId": "e4d5f6a7-...", "balance": 105000.00,
    "createdAt": "...", "updatedAt": "..."
  },
  {
    "id": "2b3c4d5e-...", "updateTrackingListId": "a1b2c3d4-...",
    "trackingItemId": "f5a6b7c8-...", "balance": null,
    "createdAt": "...", "updatedAt": "..."
  }
]
All-or-nothing validation: every trackingItemId in the request must resolve to a tracking item owned by the caller and belonging to this list's own trackingSetId (checked in one query before any row is written). If even one id fails — belongs to a different tracking set, belongs to another user, or doesn't exist — the entire request is rejected and nothing in the batch is written. An empty balances array is accepted and returns [] without touching the database.
400 Bad Request — one or more ids don't belong to this list's tracking set: {"detail": "Invalid trackingItemId(s) for this tracking set: <id>, <id>"}
404 Not Found — list not found.
422 Unprocessable Entity — malformed body (e.g. missing trackingItemId, non-numeric balance).
