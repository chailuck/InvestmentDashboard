API Spec — Financial Tracker

Objective: Full CRUD for the Financial Tracker ("Tracking") feature — Tracking Sets, Categories, Sub-categories, Tracking Items, Initial Investment Ledger entries (Phase 1); Update Tracking Lists with read-time balance deltas (Phase 2); a read-only quarterly/yearly balance-grid rollup report (Phase 3); and a full-snapshot export endpoint (Phase 4) used by the Dashboard page's "Email Dashboard" button. Phase 5 (ADR-018) adds an optional note on ledger entries, a profitVsOriginal block on the running-total response, and a per-set "profit vs original investment" rollup endpoint. Served by the independent tracking-backend microservice. All routes are mounted under /api/v1/tracking.
Scope note: this file covers only endpoints served by tracking-backend. The Phase 4 "Email Dashboard" feature also added a new endpoint on the separate main backend service (POST /api/v1/email/send-export) — that endpoint is documented in 18-financial-tracker/TECHNICAL.html §12.2/§12.3 instead, since no standalone API reference page exists anywhere in this docs tree for any main-backend /email/* endpoint (a pre-existing gap, not one introduced by this feature — see TECHNICAL.html §12.6).
Deployment note: the Next.js proxy (frontend/src/app/api/proxy/[...path]/route.ts) does not currently route /api/v1/tracking/* requests to this service — see 18-financial-tracker/TECHNICAL.html §9.1 / §11 (TD-FT-01). The endpoints below are accurate to the running tracking-backend service reachable directly on port 8001; the browser-facing path through the frontend proxy is not yet wired to it.

Authentication

All endpoints except /health/* require Authorization: Bearer <access_token>, where the token was issued by the main backend's login endpoint. tracking-backend only verifies the token (shared APP_SECRET_KEY, same Redis blacklist) — it never issues tokens itself. See TECHNICAL.html §2 for the full verification flow.

Initial Investment Ledger

Ledger endpoints (POST/GET .../entries, GET .../running-total) are gated at the application layer: the target Tracking Item's initialInvestmentTracking flag must already be true, or these endpoints reject the call with 400 — even though the underlying ft_initial_investment_entry table has no DB-level constraint tying it to the flag.

The profitVsOriginal object (Phase 5)

Always present on the response — it compares this item's cost basis against its latest recorded balance. Produced by the shared profit_math.compute_profit helper (TECHNICAL.html §13.2), so the null rules below match those of the set-wide rollup endpoint.

FieldTypeNotes
netOriginalInvestmentnumber, nullableRunning signed sum of every ledger entry amount for this item (same value as currentTotal). null only when the item has no entries at all.
currentValuenumber, nullableThe item's balance in its most-recent populated (year, quarter) slot, using the same winning-Update-Tracking-List selection as the Dashboard balance grid. null when the item has never had a balance recorded on any Update Tracking List.
currentValueSlot{year, quarter}, nullableWhich slot currentValue came from; null whenever currentValue is null.
profitnumber, nullablecurrentValue - netOriginalInvestment; null unless both inputs are present.
profitPercentnumber, nullableprofit / netOriginalInvestment * 100, only when netOriginalInvestment > 0 and currentValue exists. When the net is 0 or negative, profit is still populated but profitPercent is null — never Infinity, NaN, or a string.
isCoveredbooleantrue when the flag is on AND the item has at least one entry AND currentValue is present. Does not require a positive net.
400 Bad Request — item does not have initialInvestmentTracking enabled (unchanged from Phase 1 — the profitVsOriginal block does not relax this).
404 Not Found — item not found.

GET /api/v1/tracking/entries/{id}

404 Not Found — entry not found.

PUT /api/v1/tracking/entries/{id}

// Request — presence-aware (Phase 5): only the fields you send are changed.
//   omit a field                       -> left untouched
//   "note": null  /  "note": ""        -> clears the note (blank/whitespace is coerced to null)
//   "amount": null  /  "entryDate": null -> rejected with 422 (these are non-nullable)
{ "amount": 55000.00, "note": "sold half position" }

// Response 200 — updated entry (same shape as the POST response, including note)
Presence-aware semantics: the handler applies model_dump(exclude_unset=True), so a field absent from the request body is not modified. This is what lets a caller change only note without resending amount / entryDate. Explicit null is meaningful only for note (it clears it); for amount and entryDate, null is a validation error, not "leave as-is".
404 Not Found — entry not found.
422 Unprocessable Entity — amount provided as zero; amount or entryDate provided as null; or note longer than 500 characters.

Update Tracking Lists (Phase 2)

Periodic balance snapshots ("updates") against a Tracking Set's category/sub-category/tracking-item hierarchy, plus read-time delta computation against the immediately preceding snapshot. Implemented in app/api/v1/endpoints/update_tracking_lists.py. Two URL families share this one router — nested /sets/{setId}/update-lists for header create/list, and standalone /update-lists/{listId}... for everything else — mirroring how tracking_sets.py already nests /sets/{setId}/categories. See 18-financial-tracker/FUNCTIONAL.html §11 for user-facing behaviour and 18-financial-tracker/TECHNICAL.html §7 for the delta-computation algorithm.

            {
              "id": "f5a6b7c8-...", "name": "New item added this quarter", "type": "Bank account", "orderIndex": 1,

Reading the delta fields: hasPreviousData=false means either this is the first list for the set, or this item had no balance recorded on the previous list — the UI must show a "no data" indicator, not a fabricated zero. When hasPreviousData=true but the previous balance was exactly 0, deltaAmount is still computed but deltaPercent is null (division by zero is avoided deliberately, not a bug). All four delta-related fields are computed fresh on every call — never cached or stored — so editing an older list's balance changes what this response returns on the very next call.

All-or-nothing validation: every trackingItemId in the request must resolve to a tracking item owned by the caller and belonging to this list's own trackingSetId (checked in one query before any row is written). If even one id fails — belongs to a different tracking set, belongs to another user, or doesn't exist — the entire request is rejected and nothing in the batch is written. An empty balances array is accepted and returns [] without touching the database.
400 Bad Request — one or more ids don't belong to this list's tracking set: {"detail": "Invalid trackingItemId(s) for this tracking set: <id>, <id>"}
404 Not Found — list not found.
422 Unprocessable Entity — malformed body (e.g. missing trackingItemId, non-numeric balance).

Dashboard (Phase 3)

A single read-only report endpoint that rolls up every balance ever recorded via Update Tracking Lists into one quarterly/yearly grid, following the same Category → Sub-category → Tracking Item hierarchy as every other view in this service. Implemented in app/api/v1/endpoints/dashboard.py, with all aggregation logic in app/services/dashboard_balance_grid.py. No request body, no query parameters beyond the path's setId, and nothing is ever written — every field is recomputed on each call. See 18-financial-tracker/FUNCTIONAL.html §12 for user-facing behaviour and 18-financial-tracker/TECHNICAL.html §8 for the aggregation algorithm.

GET /api/v1/tracking/sets/{setId}/dashboard/balance-grid

Returns the tracking set's current category/sub-category/tracking-item hierarchy with a balance-grid cell for every quarter of every year that has at least one Update Tracking List with both year and quarter set. Years are ordered descending (most recent first); every year that appears always has all four quarters present in its cells/subtotal/etc. arrays, even a quarter with no recorded data (hasData: false, balance: null — never omitted from the array). Every cells, subtotal, grandTotal, propertyTotal, and nonPropertyTotal array has exactly years.length * 4 entries, positionally aligned to iterating years top-to-bottom then quarters [1, 2, 3, 4] ascending for each year — callers should zip against that same flattened index rather than matching on (year, quarter) per cell.

Response field reference

FieldTypeNotes
trackingSetIdUUIDEchoes the path parameter.
years[].yearintegerDescending order — the response's array order IS the intended display order.
years[].quartersinteger[]Always exactly [1, 2, 3, 4].
categories[].subCategories[].items[].orderIndexintegerNot aliased to order — this composite response follows the same orderIndex convention as the Update Tracking List detail response (see TECHNICAL.html §11 TD-FT-06), not the flat Category/SubCategory/TrackingItem endpoints above.

Original Investment vs Profit (Phase 5)

A read-only rollup that pairs each tracked item's original invested amount (the signed sum of its Initial Investment Ledger entries) with its current balance (its latest recorded Update Tracking List balance), for the whole tracking set at once. Implemented in app/api/v1/endpoints/dashboard.py alongside the Phase 3 balance-grid route; profit math is the shared app/services/profit_math.py — compute_profit(); the set-wide assembly is app/services/original_investment_rollup.py. No request body, no query parameters beyond the path's setId; nothing is written or cached. See 18-financial-tracker/FUNCTIONAL.html §12.13 and 18-financial-tracker/TECHNICAL.html §13.

GET /api/v1/tracking/sets/{setId}/dashboard/original-investment

Definitions

  • Net original investment — running signed sum of every ledger entry amount for the item. null (render "—", never 0) when the item has no entries.
  • Current value — the item's balance in its most-recent populated (year, quarter) slot, from the same winning-list selection the balance grid uses. null when the item has never had a recorded balance.
  • Profit — currentValue - netOriginalInvestment; null unless both are present.
  • Profit % — profit / netOriginalInvestment * 100, only when netOriginalInvestment > 0 and a current value exists; otherwise null (the profit amount is still shown). Never Infinity / NaN.
  • Covered — flag on AND at least one entry AND a current value exists. Does not require a positive net.

Scope

items[] and coverage.totalCount (M) include every non-exclusive item in the set with initialInvestmentTracking = true — covered items and not-yet-covered items alike (the latter with null numeric fields). Items with the flag off, and exclusive items, are excluded entirely — never a row, never in a total. coverage.shownCount (N) is the covered count; coverage.excludedItemNames lists the in-scope items that are not covered. totals aggregate covered items only; totals.profitPercent is null when the summed net is 0 or negative.

Export (Phase 4)

A single read-only endpoint returning a full, restorable snapshot of one Tracking Set — every Category, Sub-category, Tracking Item, Update Tracking List, Update Tracking List balance, and Initial Investment Ledger entry it contains, as raw fields with no derived or calculated values. Implemented in app/api/v1/endpoints/export.py; schemas in app/schemas/export.py. This is the JSON backup attached to the email sent by the Dashboard page's "Email Dashboard" button. See 18-financial-tracker/FUNCTIONAL.html §13 for user-facing behaviour and 18-financial-tracker/TECHNICAL.html §12.1 for the ownership and query-scoping detail. (Phase 5) exportVersion is now 2: initialInvestmentEntries[] rows carry the new optional note field.

GET /api/v1/tracking/sets/{setId}/export

No request body, no query parameters beyond the path's setId. Nothing is ever written by this endpoint. Every returned row is scoped both by the FK chain down from the verified tracking set AND by an explicit user_id filter on every query (belt-and-suspenders, since this response is intended for later re-import).
