Migration detail — b2c3d4e5f6a7

Uses a three-phase NOT NULL strategy to handle tables that may or may not have existing rows at migration time:

  1. Add portfolio_id as nullable + FK constraint.
  2. DELETE FROM daily_performance WHERE portfolio_id IS NULL — pre-existing user-scoped rows are irrecoverably purged because they cannot be attributed to a single portfolio.
  3. Alter column to NOT NULL.
  4. Drop uq_daily_performance_user_date; create uq_daily_performance_portfolio_date; create ix_daily_performance_portfolio_id.
The data purge in Phase 2 is intentional and documented in the migration header. On a fresh deployment with no pre-existing data it is a no-op.

3. Service API

Source: backend/app/services/daily_performance_service.py

run_daily_snapshot

async def run_daily_snapshot(
    db: AsyncSession,
    user_id: str,          # string UUID of the owner user
    snapshot_date: date,   # calendar date for the snapshot
    portfolio_id: str,     # string UUID of the target portfolio (required)
) -> DailyPerformance

Computes and upserts a snapshot for one portfolio. Steps:

  1. Query all PortfolioDbPosition rows where portfolio_id matches and entry_date <= snapshot_date.
  2. Sum entry_price × position_size for all positions → investment.
  3. Filter positions with status="closed" and exit_date <= snapshot_date; sum _pos_net_pnl(pos) → closed_pnl; compute closed_pnl_pct.
  4. Collect unique symbols for active positions; fetch live prices in parallel via asyncio.gather + loop.run_in_executor (yfinance is blocking); compute per-position and aggregate open_pnl; build open_positions list.
  5. Execute PostgreSQL INSERT ... ON CONFLICT (uq_daily_performance_portfolio_date) DO UPDATE. Sets updated_at = now() on conflict.
  6. Re-query and return the upserted row.

open_positions, purchased_positions, and sold_positions are each passed through _merge_same_symbol_positions() before being returned, which collapses same-symbol/same-price/same-entry_date duplicates produced by partial sells (a shrunk active row plus its closed remainder); merging never crosses list boundaries and never applies to entries with a null entry_date.

Price-fetch failures are caught per-symbol; the symbol's P&L contribution is treated as 0.0 and a warning is logged. The snapshot always completes even if all price fetches fail.

run_snapshot_for_all_portfolios

async def run_snapshot_for_all_portfolios(
    db: AsyncSession,
    snapshot_date: date,
) -> dict  # {"succeeded": int, "failed": int, "total": int}

Called by the APScheduler nightly job. Queries SELECT id, user_id FROM portfolios (all portfolios, all users). Iterates the result list and calls run_daily_snapshot for each portfolio. Per-portfolio exceptions are caught; a failed portfolio triggers a rollback of the current session state before continuing. The returned dict carries succeeded, failed, and total counts.

Price helper — _fetch_price

def _fetch_price(symbol: str) -> float | None

Calls yf.Ticker(f"{symbol}.BK").history(period="2d") and returns the most recent closing price as a float, or None on any exception. Runs synchronously; callers must invoke via loop.run_in_executor.

P&L helper — _pos_net_pnl

def _pos_net_pnl(pos: PortfolioDbPosition) -> float

Returns realised net P&L for a closed position. Returns 0.0 if any of entry_price, exit_price, or position_size is None. Direction defaults to LONG when pos.direction is absent.

TD-DP-05: _pos_net_pnl duplicates logic from portfolio_db.py. The duplication is intentional to break a circular import cycle at module-load time, as noted in the source comment.

4. REST API

Router prefix: /api/v1/daily-performance — all endpoints require Authorization: Bearer <token>.

GET /daily-performance

Returns daily performance snapshots for one portfolio, ordered by date ascending.

ParameterTypeRequiredDefaultDescription
date_fromdate (YYYY-MM-DD)Notoday − 60 daysWindow start
date_todate (YYYY-MM-DD)NotodayWindow end
portfolio_idUUIDNouser's default portfolioTarget portfolio; resolved via _resolve_portfolio_id

Error codes:

  • 400 — date range exceeds 366 days.
  • 403 — portfolio_id does not belong to the authenticated user.
  • 404 — no default portfolio found and portfolio_id was not provided.

Response: 200 OK — JSON array of serialised DailyPerformance records (see serialisation helper below).

POST /daily-performance/run

Triggers an on-demand snapshot for the authenticated user's portfolio using date.today().

ParameterTypeRequiredDescription
portfolio_idUUID (query)NoDefaults to the user's default portfolio

Response: 200 OK — {"status": "ok", ...serialised_record}. Idempotent — re-running overwrites today's record.

PUT /daily-performance/{date_str}

Partially patches a stored snapshot. Only fields present and non-None in the request body are written. Percentage columns are recomputed server-side.

ParameterLocationTypeRequiredDescription
date_strpathstringYesDate in YYYY-MM-DD format
portfolio_idqueryUUIDNoDefaults to the user's default portfolio

{

  "open_pnl":       float | null,

5. _resolve_portfolio_id

async def _resolve_portfolio_id(
    db: AsyncSession,
    uid: uuid.UUID,
    portfolio_id_param: uuid.UUID | None,
) -> uuid.UUID

Used by all three endpoints to resolve the target portfolio UUID and enforce ownership.

With portfolio_id_param provided

  1. Query SELECT * FROM portfolios WHERE id = portfolio_id_param.
  2. If no row found → raise HTTP 404 "Portfolio not found."
  3. If portfolio.user_id != uid → raise HTTP 403 "Portfolio does not belong to the authenticated user." (IDOR protection)
  4. Return portfolio.id.

Without portfolio_id_param (None)

  1. Query SELECT * FROM portfolios WHERE user_id = uid AND is_default IS TRUE.
  2. If no default portfolio found → raise HTTP 404 with message instructing the caller to pass ?portfolio_id=<uuid> explicitly or mark a portfolio as default.
  3. Return the default portfolio's id.
The function intentionally never returns a portfolio that does not belong to uid. There is no path that allows a user to read or write another user's snapshots.

Effects

  • Portfolio fetch (useEffect([], [])): Fetches GET /portfolios once on mount. Sets portfolios, resolves default, sets portfoliosLoading = false. Cancels via a cancelled flag on unmount.
  • Chart resize (useEffect([], [])): Attaches a ResizeObserver to the chart container div. Updates containerWidth on each resize event. Disconnects on unmount.
  • Data fetch (useEffect([fetchData], [fetchData])): Calls fetchData whenever the memoised callback changes (i.e., when selectedPortfolioId, dateFrom, or dateTo changes). fetchData exits early if selectedPortfolioId is null.

Chart computation

chartData is derived via useMemo([records, containerWidth]). It computes inner dimensions, coordinate-mapping functions (xOf, yOf), five evenly spaced Y ticks, up to eight X axis labels, and SVG point arrays for all three series. Returns null when records is empty or containerWidth is zero.

Inline edit flow

  1. User clicks an EditableNumberCell; startEdit(rowId, field, value) sets editCell and editValue.
  2. User types; controlled input updates editValue.
  3. On blur or Enter: commitEdit is called. Parses editValue to float; if invalid, cancels. Otherwise calls dailyPerformanceService.updateRecord then fetchData.
  4. On Escape: cancelEdit clears editCell without a network call.

8. Known technical debt

IDDescriptionImpact
TD-DP-01 No unit or integration tests for run_daily_snapshot or run_snapshot_for_all_portfolios. Regression risk on service logic changes.
TD-DP-02 _fetch_price has no retry on transient network failures. A single exception causes the symbol's P&L to silently default to 0.0. Snapshot may understate open P&L on flaky connections.
TD-DP-03 The scheduler fires on SET market holidays — a snapshot is written even when the market is closed, recording stale prices from the previous session. Holiday-day rows show incorrect open P&L.
TD-DP-04 No rate-limiting on POST /daily-performance/run. A user can trigger repeated snapshots within milliseconds, each spawning parallel yfinance fetches. Potential for accidental API abuse of the Yahoo Finance endpoint.
TD-DP-05 _pos_net_pnl is duplicated from portfolio_db.py to avoid a circular import. Source comment acknowledges this. Business logic divergence risk if the two copies are modified independently.
TD-DP-06 The GET endpoint defaults to a 60-day window but the hard cap is 366 days. The discrepancy is not surfaced in the API schema or UI. Minor documentation gap; no runtime consequence.
TD-DP-07 The frontend does not validate that date_from <= date_to before submitting. An inverted range returns an empty array with no user-visible error. Confusing UX when dates are accidentally reversed.
TD-DP-08 open_positions is stored as NULL rather than [] when a portfolio has no active positions. Code that checks open_positions.length must guard for null. Frontend already handles null correctly; a future consumer may not.
TD-DP-09 No page-level frontend tests for acceptance criteria AC-004 (preset buttons update date range), AC-005 (inline edit commits via Enter/blur), or AC-010 (portfolio selector re-fetches data). Interaction regressions will not be caught automatically.
TD-DP-10 No migration integration test covers the three-phase NOT NULL strategy in b2c3d4e5f6a7. The purge of pre-existing rows (Phase 2) is untested. Correctness of the migration on a non-empty table is unverified.

9. Architecture decision records

ADR-DP-01: Portfolio-scoped snapshots

Date: 2026-07-18  |  Status: Accepted

Context

The initial daily_performance table (migration a1b2c3d4e5f6) stored one snapshot per user per day via a UNIQUE constraint on (user_id, date). Position data in portfolio_positions_db is already scoped to individual portfolios via portfolio_id. Computing a user-level snapshot required aggregating across all portfolios, collapsing portfolio-specific P&L into a single row. This prevented independent performance tracking for users who maintain separate trading strategies in separate portfolios.

Decision

We will scope daily snapshots to individual portfolios. The UNIQUE constraint changes from (user_id, date) to (portfolio_id, date). One snapshot row is written per portfolio per day.

Alternatives considered

  • Keep user-scoped snapshots: Simple, no migration required. Rejected because it aggregates across portfolios with different risk profiles, making per-portfolio performance analysis impossible.
  • Add portfolio_id as a nullable column alongside the old user-scoped constraint: Preserves backward compatibility. Rejected because the two constraint forms are mutually inconsistent and would require dual-write logic.

Consequences

  • A user with N portfolios now receives N snapshot rows per day rather than one.
  • The scheduler must iterate all portfolios across all users (handled by run_snapshot_for_all_portfolios).
  • Existing snapshot rows created before this migration are purged — they cannot be attributed to a single portfolio without ambiguity.
  • Frontend must pass portfolio_id as a required context for all API calls.

ADR-DP-02: Portfolio resolution in the API layer

Date: 2026-07-18  |  Status: Accepted

Context

After moving to portfolio-scoped snapshots, every endpoint must determine which portfolio to act on. Options were: (a) resolve in each endpoint handler, (b) resolve in the service layer, (c) extract into a shared helper in the API layer.

Decision

We will centralise portfolio resolution in a single async helper function _resolve_portfolio_id in the endpoint module. The function enforces IDOR protection (portfolio must belong to the authenticated user) and provides a default-portfolio fallback when no portfolio_id is passed.

Consequences

  • IDOR protection is applied consistently — it cannot be accidentally skipped by a new endpoint.
  • The service layer receives a fully resolved portfolio_id (already validated), keeping the service free of auth concerns.
  • All three endpoints share a single resolution path, making security audits straightforward.

ADR-DP-03: Retain user_id as a denormalised field

Date: 2026-07-18  |  Status: Accepted

Context

After adding portfolio_id, user_id is technically derivable via a join: daily_performance JOIN portfolios ON portfolio_id = portfolios.id. Keeping user_id duplicates data already present in the portfolios table.

Decision

We will retain user_id as a denormalised foreign key on daily_performance. It is documented in the model docstring as a convenience field for direct user-scoped queries without a join.

Consequences

  • Queries scoped to a user (e.g., "show all snapshots for user X") do not require a join to portfolios.
  • The field must be kept in sync when portfolio.user_id changes (edge case; portfolio ownership transfers are not currently supported).
  • The user_id index (ix_daily_performance_user_id) retained from the original migration supports these queries efficiently.
