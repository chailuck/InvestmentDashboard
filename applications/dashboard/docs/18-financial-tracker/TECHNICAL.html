Financial Tracker — Technical Design

Version: 3.0 (Phase 1 + Phase 2 + Phase 3)  |  Last updated: 2026-08-28

1. Architecture

The Financial Tracker is implemented as a genuinely separate FastAPI microservice — tracking-backend — rather than a module inside the existing backend service. It has its own codebase, its own Docker image, its own process, and its own Alembic migration chain. It shares only two things with the rest of the application: the same physical PostgreSQL instance/database, and the same Next.js frontend.

1.1 Why a separate service (ADR summary)

Decision: Build the Financial Tracker as an independently deployable FastAPI service rather than extending backend, driven by the explicit technical requirement to add this feature "so that we can restart this pod without impacting the current functionalities" (see docs/REQUIREMENTS FINANCIAL TRACKER.md, §2).

Trade-offAccepted consequence
JWT verification logic duplicatedtracking-backend/app/auth/jwt.py and dependencies.py are a deliberately duplicated subset of the main backend's auth code, not imported. A future change to token shape/claims (e.g. adding a new claim, changing the blacklist key prefix) must be applied to both services by hand, or they will silently diverge on which tokens they accept.
RBAC / role-scoping deferredThis service has no concept of roles (admin/analyst/viewer) and no FK to the users table — see §2.2. Every endpoint is available to any authenticated user for their own data only. If role-based restrictions are ever required for this feature, they must be added as a new capability, not inherited from the main backend.
Independent Alembic chainOwn version_table="ft_alembic_version" in the same database (§4) — deploying this service requires its own separate alembic upgrade head step; it is not covered by the main backend's migration run.
Shared secret file operational burden.env.shared (§2.1) must exist and be kept identical for both services in every environment; a missed copy causes 100% of tracking-backend requests to fail with 401 with no config-level error to point at the cause.

Alternatives considered:

  • Add a new router/module inside the existing backend service. Rejected — the explicit requirement was independent restart/deploy without touching the main backend's running process, which a shared FastAPI app cannot provide.
  • Separate service with its own database. Rejected for Phase 1 — the requirement asked to "share the same... DB", presumably to avoid provisioning and operating a second Postgres instance for what is currently a small table set.

2. Authentication

2.1 Shared secret

Both backend and tracking-backend load APP_SECRET_KEY from a shared, untracked .env.shared file at the repo root (template: applications/dashboard/.env.shared.example), wired into both services via env_file in docker-compose.yml. tracking-backend never issues tokens — it only verifies signatures on tokens the main backend already issued, using the identical key and HS256 algorithm.

If the two services' APP_SECRET_KEY values ever diverge (e.g. one environment's .env.shared is stale), every tracking-backend request fails with a generic 401 — there is no diagnostic pointing at a key mismatch specifically.

2.2 Verification-only, no RBAC

app/auth/jwt.py and app/auth/dependencies.py are intentionally a duplicated subset of the main backend's equivalent files — not imported — to keep the two codebases fully independent. get_current_user_id reproduces the main backend's rules exactly so both services accept/reject the same tokens identically:

  1. Missing Authorization header → 401
  2. Invalid signature / expired / wrong token type → 401
  3. Token missing the jti claim → 401
  4. Redis unreachable while checking the blacklist → 503 (fails CLOSED, not open)
  5. Token's jti present under blacklist:<jti> in Redis → 401 (revoked)
  6. Otherwise → returns payload["sub"] as an opaque user-id string

This service has no get_current_user, no role checks, and no foreign key into the main backend's users table. It only ever knows the caller as an opaque user-id string and enforces per-row ownership via bare user_id columns on its own tables (§3).

2.3 Redis blacklist

Shares the same Redis instance/db as the main backend, reading the same blacklist:<jti> key pattern the main backend's logout endpoint writes to (see docs/02-infrastructure/DATABASE.html §4). A logout on the main backend therefore also revokes that token's access to tracking-backend — there is no separate logout needed.

3. Data model

All 7 tables (5 from Phase 1, 2 from Phase 2) live in the same physical Postgres database as the main application (investment_db), but are prefixed ft_ and carry no foreign keys into any table owned by backend (e.g. no FK to users). Ownership is enforced purely at the application layer via a bare user_id UUID column on every table. This is deliberate bounded-context isolation — the two services could point at physically separate databases in the future with no schema change on this side.

5.1 Ownership pattern

Every single-resource endpoint (get/update/delete by id, and every nested "belongs to" check) goes through a per-router _get_or_404(id, user_id, db) helper that filters by both id AND user_id in the same query, and raises HTTP 404 — never 403 — when no row matches. This means a cross-user access attempt is indistinguishable from a nonexistent resource; the API never confirms or denies that a given id exists for another user. This mirrors applications/dashboard/backend/app/api/v1/endpoints/portfolio_db.py's identical pattern.

5.2 Auto-numbering of order

On create, if the client omits order, the endpoint queries the current maximum order_index among siblings and assigns max + 1 (or 1 if there are no siblings yet). Reordering is always an explicit, full replacement via the PUT .../reorder endpoints — there is no "move by one position" endpoint.

6. Cascade creation service

Source: app/services/cascade.py — create_tracking_set_with_defaults()

Creating a Tracking Set and its default category/sub-category skeleton (§ FUNCTIONAL.html §3.1) happens as 8 inserts in a single database transaction — 1 tracking set + 2 categories + 5 sub-categories:

  1. Insert the TrackingSet row, then db.flush() (assigns its id without committing).
  2. For each of the two default categories (Assets, Liabilities): insert the Category row, then flush() to obtain its id.
  3. For each category's default sub-category names, insert the SubCategory rows.
  4. A final flush(); the endpoint layer (via the get_db dependency) performs the actual commit() after the handler returns normally.

If any insert fails mid-cascade — most likely a duplicate tracking-set name violating uq_ft_tracking_set_user_id_name on flush — the entire session rolls back and nothing is persisted. There is no possible state where a Tracking Set exists without its default categories, or vice versa.

The default rows are ordinary rows: nothing marks them as system-created versus user-created, so they are immediately and fully editable/deletable through the same CRUD endpoints as anything else.

7. Update Tracking List service (Phase 2)

Source: app/services/update_tracking.py — get_update_list_detail(), consumed by exactly one endpoint (GET /update-lists/{list_id}/detail). Kept out of the endpoints file for the same reason as cascade.py (§6): assembling the previous-list lookup, the full current hierarchy, and the per-item delta math is business logic, not request/response wiring.

7.1 Detail assembly algorithm

get_update_list_detail(db, list_id, user_id) returns None (never raises) when the list doesn't exist or isn't owned by user_id; the endpoint converts that into a bare 404, consistent with every other resource in this service. When found, it performs, in order:

  1. Load the UpdateTrackingList header, confirming id + user_id match in the same query.
  2. Find the chronologically previous list in the same tracking set — see §7.2.
  3. Load that previous list's balance rows (if a previous list was found) into a {tracking_item_id: balance} dict. Row-absence and balance IS NULL both collapse to "no previous data" via a plain dict .get() returning None.
  4. Load the tracking set's current Category → SubCategory → TrackingItem hierarchy in full — not anything frozen at list-creation time (see FUNCTIONAL.html §11.5 for the user-facing implication). Every item currently in the hierarchy appears, even one added to the set after this list was created.
  5. Load the current list's own balance rows into a second {tracking_item_id: balance} dict.
  6. Walk the hierarchy and compute one ItemDelta per tracking item (§7.3), assembling the nested CategoryDetail → SubCategoryDetail → ItemDelta dataclasses the endpoint serialises into the response.

All balance and hierarchy data is fetched with a small, fixed number of queries (one per level/table), not one query per item — no N+1 pattern.

7.2 Previous-list lookup — deterministic tie-break

_find_previous_list() selects the row in the same tracking_set_id with the greatest (transaction_date, created_at, id) tuple that is strictly less than the current list's own tuple, expressed as an explicit OR-of-ANDs (transaction_date < current, OR transaction_date = current AND created_at < current, OR transaction_date = current AND created_at = current AND id < current) rather than SQLAlchemy's tuple_() row-comparison helper, to avoid relying on composite ROW() comparison semantics that could vary across dialects/drivers. This guarantees a single, deterministic "previous" list even when two lists share the same Transaction Date (allowed — §3) or, in the further edge case, the same created_at timestamp too.

7.3 Delta computation

_compute_item_delta() is pure and stateless — given one item plus the two balance dicts from §7.1, it returns:

FieldRule
has_previous_dataprevious_balance is not None
delta_amountbalance - previous_balance, only when both are non-null; otherwise None
delta_percent(delta_amount / previous_balance) * 100, only when delta_amount is computable and previous_balance != 0 — the explicit non-zero guard avoids ZeroDivisionError and, per FUNCTIONAL.html §11.4, deliberately shows the amount without a misleading percentage when the previous balance was exactly zero
Nothing computed here is ever written back to the database. Every field is recomputed on every call to GET /update-lists/{list_id}/detail, so editing an older list's balance immediately and correctly changes what a newer list's detail reports the next time it is fetched — there is no cache invalidation step because there is no cache.

7.4 Bulk balance upsert — validation and write pattern

Source: PUT /update-lists/{list_id}/balances in app/api/v1/endpoints/update_tracking_lists.py (this logic is small enough to live in the endpoint rather than a service module, unlike the detail assembly above).

  1. Resolve the list via _get_list_or_404 (id + user_id).
  2. Collect the distinct trackingItemIds from the request body.
  3. Run one query joining TrackingItem → SubCategory → Category to confirm every requested id belongs to a tracking item owned by this user and whose category's tracking_set_id equals this list's own tracking_set_id — i.e. the item must belong to the same tracking set as the list, not merely the same user's account.
  4. If any requested id fails that check, the entire request is rejected with 400 before any row is written — an all-or-nothing guarantee at the request level.
  5. For the validated ids, load any existing UpdateTrackingListBalance rows for this (list, item) pairing, then update-in-place or insert a new row per requested item, and commit() exactly once for the whole batch.
Explicit null for a balance in the request clears an existing value (records "no balance" — distinct from a real zero); omitting the field from an item's JSON object entirely is treated identically, both resulting in balance=None being written.

8. Dashboard balance-grid service (Phase 3)

Source: app/services/dashboard_balance_grid.py — get_balance_grid(), consumed by exactly one endpoint (GET /sets/{set_id}/dashboard/balance-grid, app/api/v1/endpoints/dashboard.py). Same division of responsibility as §7: aggregation is business logic and lives in a service module, not in the endpoint (CLAUDE.md: "NEVER place business logic inside controllers/handlers"). Phase 3 adds no new database tables, columns, or Alembic migration — it is a pure read-time rollup over the existing ft_category / ft_sub_category / ft_tracking_item / ft_update_tracking_list / ft_update_tracking_list_balance tables described in §3.

8.1 The grid model — slots, series, and cells

The service works in three layers of abstraction, each with its own dataclass family:

  1. Slot — a bare tuple[int, int] of (year, quarter), the atomic unit of the grid. _slot_sort_key() gives slots a single ascending integer (year * 4 + quarter) for chronological sorting, kept separate from the descending-by-year display order built later.
  2. Series — one row's or rollup tier's populated values, as a plain dict[Slot, Decimal] containing only the slots that actually have data. Absence from the dict, not a stored null, is what "blank" means at this layer.
  3. Cell — the fully positioned, wire-shaped result (year, quarter, balance, delta_amount, delta_percent, has_data, has_previous_data) produced by materializing a series against the grid's ordered display_slots list via _materialize() — one Cell per display slot, blank ones filled from a shared _BLANK_CELL_MATH sentinel.

8.2 compute_series_deltas — the one shared delta engine

compute_series_deltas(values_by_slot, ascending_slots) is the single function used to compute deltas for every row and every rollup tier in the grid — item rows, sub-category subtotals, category subtotals, the grand total, and the Property/Non-Property breakdown. It is deliberately generic over what the series represents: it has no idea whether it is walking one tracking item's own balances or a whole category's summed total, which is exactly why one function can serve all six use sites in get_balance_grid() rather than duplicating near-identical loop logic per tier.

Walking ascending_slots (oldest first) with a running last_seen value:

  • A slot absent from values_by_slot produces a blank CellMath (has_data=False) and does not advance last_seen — so a later populated slot still diffs against the last real value, not against the blank gap. This is what lets a delta look arbitrarily far back, skipping blank quarters and crossing year boundaries freely, with no extra query per row (FUNCTIONAL.html §12.6).
  • A populated slot sets has_previous_data = last_seen is not None, computes delta_amount = balance - last_seen only when a previous value exists (a first data point gets None, never a fabricated zero delta), and computes delta_percent only when delta_amount is computable and last_seen != 0 — the same zero-guard convention as update_tracking.py's _compute_item_delta (§7.3): the amount is still shown, the percentage is suppressed.
  • last_seen is then set to the current balance before moving to the next slot.

8.3 Rollup — the "at least one populated" rule

_rollup_values(items_subset, ascending_slots, item_values_by_id) sums a group of items' per-slot values for every subtotal tier (sub-category, category, grand total, property/non-property). For each slot, it sums only the items that actually have a value that slot; if zero items in the group have data for a slot, that slot is left absent from the result (blank), not written as zero. This means a subtotal is populated as soon as any one item beneath it has data for a quarter — it never disappears just because a sibling item in the same group has no history yet (FUNCTIONAL.html §12.4). Category subtotals are computed by summing directly over every non-Exclusive leaf item in the category (flattened across its sub-categories), not by re-summing the already-computed sub-category subtotal cells — so the "at least one populated" rule is applied once, at the leaf-item granularity, rather than compounding across two levels of rollup.

8.4 Duplicate (year, quarter) slot — winner selection

Only UpdateTrackingList rows with both year and quarter set are eligible for the grid at all — rows missing either are silently excluded from this report (not an error). Eligible rows are grouped in Python by their (year, quarter) tuple; when more than one list shares the same slot (allowed by design — §3, FUNCTIONAL.html §11.1's duplicate-date behavior extends naturally to duplicate quarter/year labels too), the winner is the row with the greatest (created_at, id) tuple — i.e. most recently created wins, with id descending as the final deterministic tiebreak for the vanishingly unlikely case of an identical created_at. This mirrors the tie-break direction of _find_previous_list() in §7.2, but is computed via a plain Python sorted(..., reverse=True)[0] over already-loaded rows rather than a second SQL query, since all candidate rows for the set are loaded in one query up front (§8.5).

8.5 Performance — exactly 6 queries, no N+1

get_balance_grid() issues a fixed, small number of queries regardless of how many years, quarters, categories, or items the tracking set has:

  1. Every UpdateTrackingList row for the set with year and quarter both non-null.
  2. Every UpdateTrackingListBalance row for the winning lists selected in-memory from query 1 (§8.4) — a single WHERE update_tracking_list_id IN (...), not one query per slot.
  3. Category rows for the set.
  4. SubCategory rows for those categories.
  5. TrackingItem rows for those sub-categories.

(Ownership verification of the TrackingSet itself, via _get_set_or_404 in the endpoint, is a 6th query performed by the caller before the service function is entered — see §8.6.) Every grouping, winner-selection, summation, and delta computation described in §8.2–§8.4 happens afterward, entirely in Python against data already loaded — there is no query inside a per-item, per-slot, or per-tier loop.

8.6 Endpoint and ownership

Source: app/api/v1/endpoints/dashboard.py, mounted with no fixed router-level prefix (its one route spells out the full /sets/{set_id}/dashboard/balance-grid path itself, the same pattern already used by update_tracking_lists.py — §5). The endpoint reuses _get_set_or_404 imported directly from update_tracking_lists.py rather than duplicating it, so a cross-user request against someone else's tracking set gets the identical bare 404 (never 403) as every other resource in this service (§5.1). Once ownership is confirmed, the endpoint calls get_balance_grid(db, tracking_set_id=...) and maps the returned dataclasses onto the DashboardBalanceGridOut Pydantic response via a small local _to_response()/_to_cells() pair — kept in the endpoint module rather than the service module, since it is pure schema mapping with no business logic of its own.

9. Frontend integration

9.1 Proxy routing

The browser never talks to either backend directly — every API call from the frontend goes through the existing Next.js catch-all proxy route frontend/src/app/api/proxy/[...path]/route.ts, which the app already used for the main backend. trackingService (in frontend/src/services/tracking.ts) builds paths as /tracking/<resource>, which the shared apiClient (baseURL /api/proxy/api/v1) turns into a browser request to /api/proxy/api/v1/tracking/<resource>.

Known gap — proxy does not yet route to tracking-backend. As implemented today, route.ts forwards every request it receives — regardless of path — to a single BACKEND_URL environment variable (default http://backend:8000, the main backend). There is no branch on the /api/v1/tracking/ prefix, and no TRACKING_BACKEND_URL variable exists anywhere in the codebase (checked: not in route.ts, not in docker-compose.yml, not in any .env* file). docker-compose.yml does run tracking-backend as its own container on port 8001, but nothing in the frontend currently points at it. In the current wiring, every /api/proxy/api/v1/tracking/... call is forwarded to the main backend, which does not mount these routes and will return 404. This must be fixed — e.g. by branching in route.ts on params.path[0..2] === ['api','v1','tracking'] and forwarding to a new TRACKING_BACKEND_URL env var pointing at http://tracking-backend:8001 — before this feature works end-to-end in the Docker Compose deployment. Track as a release blocker, not a cosmetic doc gap.

9.2 Frontend service layer

Source: frontend/src/services/tracking.ts. All types and payloads use camelCase field names (trackingSetId, orderIndex serialised as order, entryDate, etc.) to match what the tracking-backend API returns — unlike the legacy snake_case services elsewhere in this frontend for the main backend.

The three reorder* methods (reorderCategories, reorderSubCategories, reorderItems) are confirmed against the actual backend implementation: they are PUT requests with a body of { items: [{ id, order }, ...] }, built by a local toOrderItems() helper that converts a flat, newly-ordered id array into 1-indexed {id, order} pairs.

(Phase 3) trackingService.getBalanceGrid(setId) is a single GET to /tracking/sets/{setId}/dashboard/balance-grid, added directly to this same file rather than a new sibling service module — unlike Update Tracking Lists (§9.2.1), the Dashboard has exactly one read-only method, which does not justify its own file. The DashboardBalanceGridOut/DashboardCategoryRow/DashboardSubCategoryRow/DashboardItemRow/BalanceCell TypeScript types mirror the backend's CamelModel schemas (§8) field-for-field, including the module-header note that every cells/subtotal/grandTotal/propertyTotal/nonPropertyTotal array is positionally aligned to the flattened years × [1,2,3,4] order — the page zips its rendered columns against these arrays by index, with no client-side date/quarter matching.

9.3.1 Update Tracking List detail page — edit/save state design

updates/[listId]/page.tsx hydrates a local values: Record<itemId, string> state from the loaded detail exactly once (guarded by a hydrated flag) rather than binding inputs directly to query data, so that an invalidate+refetch after a partial save does not clobber the user's still-unsaved edits to other fields — the same "hydrate once from server data, edit locally, one explicit save" pattern the Tracking Item detail page (items/[itemId]/page.tsx, Phase 1) established for this app. A parallel dirty: Set<itemId> tracks which fields have actually changed; Save All is disabled whenever this set is empty and sends only the dirty entries (as { trackingItemId, balance: number | null }[]) to upsertBalances() in one call — not one call per field — because the backend endpoint is purpose-built for batch upsert. An empty/cleared input is sent as balance: null; a non-numeric value blocks the whole Save All action with an inline error before any request is made.

9.3.2 Dashboard page — collapse/expand state design (Phase 3)

dashboard/page.tsx is entirely read-only (no values/dirty state at all, unlike §9.3.1) — its only local state is which row-groups and year-columns are collapsed. This is implemented with a small generic hook, useToggleSet<T>(), private to this page file: it wraps a Set<T> tracking which keys are collapsed (default: empty, i.e. everything expanded, matching the reference spreadsheet's default fully-expanded view) and exposes has(key), toggle(key), setAll(keys), and clear(). Three independent instances are created — collapsedYears: useToggleSet<number>(), collapsedCategories: useToggleSet<string>(), collapsedSubCategories: useToggleSet<string>() — so a year-column collapse and a Category/Sub-category row-collapse never interfere with each other.

This is deliberately not useExpandableList — the existing shared hook used by the Action Plan page's tables for "show latest N of a flat list, expand for the rest." That hook's shape (a flat list with a numeric reveal count) does not fit this page's requirement (arbitrary keyed nodes, independently toggled, in two unrelated dimensions — rows and columns). Rather than force-fit the existing hook, useToggleSet is a new, smaller, purpose-built one, local to this page rather than promoted to a shared hooks file, since nothing else in the app needs this exact shape yet.

The global Detail/Summary buttons (FUNCTIONAL.html §12.5) call collapsedCategories.clear() + collapsedSubCategories.clear() (Detail) or collapsedCategories.setAll(allCategoryIds) + collapsedSubCategories.setAll(allSubCategoryIds) (Summary) — bulk operations against the same underlying Sets the per-row chevrons toggle individually, so a user can click Summary and then re-expand one Category by its own chevron with no special-casing required.

Year-column collapsing is handled differently from row collapsing: a visibleColumnIndices array (useMemo, keyed off grid and collapsedYears.set) is built by walking grid.years in the exact order the backend returned them and, for every non-collapsed year, pushing that year's four flattened cell-array indices. A collapsed year contributes zero indices. Every row's <GridCells> renderer then maps over visibleColumnIndices rather than the full cell array — this is what actually removes a collapsed year's columns from the DOM (not a CSS display:none), while its header <th> still renders via rowSpan as a single narrow re-expand target. Because the page never re-sorts grid.years (already descending from the backend — §8.5, §8.4), the flattened index math (yearIdx * 4 + q) stays valid without any client-side date arithmetic.

Decimal-as-string defensiveness mirrors §9.2.1's callout for the Update Tracking List detail page: every balance/deltaAmount/deltaPercent value is passed through a local toFiniteOrNull() helper before formatting, and the formatting helpers (fmtAmount, fmtPercent) are deliberately duplicated from updates/[listId]/page.tsx rather than imported, because Next.js App Router statically rejects named exports from a page.tsx module other than the specific ones it recognizes (default, metadata, generateStaticParams, ...).

10.4 Observability

Structured JSON logging via structlog (mirrors the main backend's setup, duplicated rather than imported). Every log line carries service_name="tracking-backend" so aggregated logs can be filtered to this service specifically. RequestContextMiddleware binds request_id/correlation_id (from incoming X-Request-ID/X-Correlation-ID headers, or newly generated) into structlog's contextvars for the duration of each request, and echoes both back as response headers. SecurityHeadersMiddleware sets X-Content-Type-Options, X-Frame-Options: DENY, Referrer-Policy, and a restrictive Content-Security-Policy on every response.
