1. Architecture

The Financial Tracker is implemented as a genuinely separate FastAPI microservice — tracking-backend — rather than a module inside the existing backend service. It has its own codebase, its own Docker image, its own process, and its own Alembic migration chain. It shares only two things with the rest of the application: the same physical PostgreSQL instance/database, and the same Next.js frontend.

1.1 Why a separate service (ADR summary)

Decision: Build the Financial Tracker as an independently deployable FastAPI service rather than extending backend, driven by the explicit technical requirement to add this feature "so that we can restart this pod without impacting the current functionalities" (see docs/REQUIREMENTS FINANCIAL TRACKER.md, §2).

Trade-offAccepted consequence
JWT verification logic duplicatedtracking-backend/app/auth/jwt.py and dependencies.py are a deliberately duplicated subset of the main backend's auth code, not imported. A future change to token shape/claims (e.g. adding a new claim, changing the blacklist key prefix) must be applied to both services by hand, or they will silently diverge on which tokens they accept.
RBAC / role-scoping deferredThis service has no concept of roles (admin/analyst/viewer) and no FK to the users table — see §2.2. Every endpoint is available to any authenticated user for their own data only. If role-based restrictions are ever required for this feature, they must be added as a new capability, not inherited from the main backend.
Independent Alembic chainOwn version_table="ft_alembic_version" in the same database (§4) — deploying this service requires its own separate alembic upgrade head step; it is not covered by the main backend's migration run.
Shared secret file operational burden.env.shared (§2.1) must exist and be kept identical for both services in every environment; a missed copy causes 100% of tracking-backend requests to fail with 401 with no config-level error to point at the cause.

Alternatives considered:

  • Add a new router/module inside the existing backend service. Rejected — the explicit requirement was independent restart/deploy without touching the main backend's running process, which a shared FastAPI app cannot provide.
  • Separate service with its own database. Rejected for Phase 1 — the requirement asked to "share the same... DB", presumably to avoid provisioning and operating a second Postgres instance for what is currently a small table set.

2. Authentication

2.1 Shared secret

Both backend and tracking-backend load APP_SECRET_KEY from a shared, untracked .env.shared file at the repo root (template: applications/dashboard/.env.shared.example), wired into both services via env_file in docker-compose.yml. tracking-backend never issues tokens — it only verifies signatures on tokens the main backend already issued, using the identical key and HS256 algorithm.

If the two services' APP_SECRET_KEY values ever diverge (e.g. one environment's .env.shared is stale), every tracking-backend request fails with a generic 401 — there is no diagnostic pointing at a key mismatch specifically.

2.2 Verification-only, no RBAC

app/auth/jwt.py and app/auth/dependencies.py are intentionally a duplicated subset of the main backend's equivalent files — not imported — to keep the two codebases fully independent. get_current_user_id reproduces the main backend's rules exactly so both services accept/reject the same tokens identically:

  1. Missing Authorization header → 401
  2. Invalid signature / expired / wrong token type → 401
  3. Token missing the jti claim → 401
  4. Redis unreachable while checking the blacklist → 503 (fails CLOSED, not open)
  5. Token's jti present under blacklist:<jti> in Redis → 401 (revoked)
  6. Otherwise → returns payload["sub"] as an opaque user-id string

This service has no get_current_user, no role checks, and no foreign key into the main backend's users table. It only ever knows the caller as an opaque user-id string and enforces per-row ownership via bare user_id columns on its own tables (§3).

2.3 Redis blacklist

Shares the same Redis instance/db as the main backend, reading the same blacklist:<jti> key pattern the main backend's logout endpoint writes to (see docs/02-infrastructure/DATABASE.html §4). A logout on the main backend therefore also revokes that token's access to tracking-backend — there is no separate logout needed.

3. Data model

All 7 tables (5 from Phase 1, 2 from Phase 2) live in the same physical Postgres database as the main application (investment_db), but are prefixed ft_ and carry no foreign keys into any table owned by backend (e.g. no FK to users). Ownership is enforced purely at the application layer via a bare user_id UUID column on every table. This is deliberate bounded-context isolation — the two services could point at physically separate databases in the future with no schema change on this side.

5.1 Ownership pattern

Every single-resource endpoint (get/update/delete by id, and every nested "belongs to" check) goes through a per-router _get_or_404(id, user_id, db) helper that filters by both id AND user_id in the same query, and raises HTTP 404 — never 403 — when no row matches. This means a cross-user access attempt is indistinguishable from a nonexistent resource; the API never confirms or denies that a given id exists for another user. This mirrors applications/dashboard/backend/app/api/v1/endpoints/portfolio_db.py's identical pattern.

5.2 Auto-numbering of order

On create, if the client omits order, the endpoint queries the current maximum order_index among siblings and assigns max + 1 (or 1 if there are no siblings yet). Reordering is always an explicit, full replacement via the PUT .../reorder endpoints — there is no "move by one position" endpoint.

6. Cascade creation service

Source: app/services/cascade.py — create_tracking_set_with_defaults()

Creating a Tracking Set and its default category/sub-category skeleton (§ FUNCTIONAL.html §3.1) happens as 8 inserts in a single database transaction — 1 tracking set + 2 categories + 5 sub-categories:

  1. Insert the TrackingSet row, then db.flush() (assigns its id without committing).
  2. For each of the two default categories (Assets, Liabilities): insert the Category row, then flush() to obtain its id.
  3. For each category's default sub-category names, insert the SubCategory rows.
  4. A final flush(); the endpoint layer (via the get_db dependency) performs the actual commit() after the handler returns normally.

If any insert fails mid-cascade — most likely a duplicate tracking-set name violating uq_ft_tracking_set_user_id_name on flush — the entire session rolls back and nothing is persisted. There is no possible state where a Tracking Set exists without its default categories, or vice versa.

The default rows are ordinary rows: nothing marks them as system-created versus user-created, so they are immediately and fully editable/deletable through the same CRUD endpoints as anything else.

7. Update Tracking List service (Phase 2)

Source: app/services/update_tracking.py — get_update_list_detail(), consumed by exactly one endpoint (GET /update-lists/{list_id}/detail). Kept out of the endpoints file for the same reason as cascade.py (§6): assembling the previous-list lookup, the full current hierarchy, and the per-item delta math is business logic, not request/response wiring.

7.1 Detail assembly algorithm

get_update_list_detail(db, list_id, user_id) returns None (never raises) when the list doesn't exist or isn't owned by user_id; the endpoint converts that into a bare 404, consistent with every other resource in this service. When found, it performs, in order:

  1. Load the UpdateTrackingList header, confirming id + user_id match in the same query.
  2. Find the chronologically previous list in the same tracking set — see §7.2.
  3. Load that previous list's balance rows (if a previous list was found) into a {tracking_item_id: balance} dict. Row-absence and balance IS NULL both collapse to "no previous data" via a plain dict .get() returning None.
  4. Load the tracking set's current Category → SubCategory → TrackingItem hierarchy in full — not anything frozen at list-creation time (see FUNCTIONAL.html §11.5 for the user-facing implication). Every item currently in the hierarchy appears, even one added to the set after this list was created.
  5. Load the current list's own balance rows into a second {tracking_item_id: balance} dict.
  6. Walk the hierarchy and compute one ItemDelta per tracking item (§7.3), assembling the nested CategoryDetail → SubCategoryDetail → ItemDelta dataclasses the endpoint serialises into the response.

All balance and hierarchy data is fetched with a small, fixed number of queries (one per level/table), not one query per item — no N+1 pattern.

7.2 Previous-list lookup — deterministic tie-break

_find_previous_list() selects the row in the same tracking_set_id with the greatest (transaction_date, created_at, id) tuple that is strictly less than the current list's own tuple, expressed as an explicit OR-of-ANDs (transaction_date < current, OR transaction_date = current AND created_at < current, OR transaction_date = current AND created_at = current AND id < current) rather than SQLAlchemy's tuple_() row-comparison helper, to avoid relying on composite ROW() comparison semantics that could vary across dialects/drivers. This guarantees a single, deterministic "previous" list even when two lists share the same Transaction Date (allowed — §3) or, in the further edge case, the same created_at timestamp too.

7.3 Delta computation

_compute_item_delta() is pure and stateless — given one item plus the two balance dicts from §7.1, it returns:

FieldRule
has_previous_dataprevious_balance is not None
delta_amountbalance - previous_balance, only when both are non-null; otherwise None
delta_percent(delta_amount / previous_balance) * 100, only when delta_amount is computable and previous_balance != 0 — the explicit non-zero guard avoids ZeroDivisionError and, per FUNCTIONAL.html §11.4, deliberately shows the amount without a misleading percentage when the previous balance was exactly zero
Nothing computed here is ever written back to the database. Every field is recomputed on every call to GET /update-lists/{list_id}/detail, so editing an older list's balance immediately and correctly changes what a newer list's detail reports the next time it is fetched — there is no cache invalidation step because there is no cache.

7.4 Bulk balance upsert — validation and write pattern

Source: PUT /update-lists/{list_id}/balances in app/api/v1/endpoints/update_tracking_lists.py (this logic is small enough to live in the endpoint rather than a service module, unlike the detail assembly above).

  1. Resolve the list via _get_list_or_404 (id + user_id).
  2. Collect the distinct trackingItemIds from the request body.
  3. Run one query joining TrackingItem → SubCategory → Category to confirm every requested id belongs to a tracking item owned by this user and whose category's tracking_set_id equals this list's own tracking_set_id — i.e. the item must belong to the same tracking set as the list, not merely the same user's account.
  4. If any requested id fails that check, the entire request is rejected with 400 before any row is written — an all-or-nothing guarantee at the request level.
  5. For the validated ids, load any existing UpdateTrackingListBalance rows for this (list, item) pairing, then update-in-place or insert a new row per requested item, and commit() exactly once for the whole batch.
Explicit null for a balance in the request clears an existing value (records "no balance" — distinct from a real zero); omitting the field from an item's JSON object entirely is treated identically, both resulting in balance=None being written.

8.1 The grid model — slots, series, and cells

The service works in three layers of abstraction, each with its own dataclass family:

  1. Slot — a bare tuple[int, int] of (year, quarter), the atomic unit of the grid. _slot_sort_key() gives slots a single ascending integer (year * 4 + quarter) for chronological sorting, kept separate from the descending-by-year display order built later.
  2. Series — one row's or rollup tier's populated values, as a plain dict[Slot, Decimal] containing only the slots that actually have data. Absence from the dict, not a stored null, is what "blank" means at this layer.
  3. Cell — the fully positioned, wire-shaped result (year, quarter, balance, delta_amount, delta_percent, has_data, has_previous_data) produced by materializing a series against the grid's ordered display_slots list via _materialize() — one Cell per display slot, blank ones filled from a shared _BLANK_CELL_MATH sentinel.

8.2 compute_series_deltas — the one shared delta engine

compute_series_deltas(values_by_slot, ascending_slots) is the single function used to compute deltas for every row and every rollup tier in the grid — item rows, sub-category subtotals, category subtotals, the grand total, and the Property/Non-Property breakdown. It is deliberately generic over what the series represents: it has no idea whether it is walking one tracking item's own balances or a whole category's summed total, which is exactly why one function can serve all six use sites in get_balance_grid() rather than duplicating near-identical loop logic per tier.

Walking ascending_slots (oldest first) with a running last_seen value:

  • A slot absent from values_by_slot produces a blank CellMath (has_data=False) and does not advance last_seen — so a later populated slot still diffs against the last real value, not against the blank gap. This is what lets a delta look arbitrarily far back, skipping blank quarters and crossing year boundaries freely, with no extra query per row (FUNCTIONAL.html §12.6).
  • A populated slot sets has_previous_data = last_seen is not None, computes delta_amount = balance - last_seen only when a previous value exists (a first data point gets None, never a fabricated zero delta), and computes delta_percent only when delta_amount is computable and last_seen != 0 — the same zero-guard convention as update_tracking.py's _compute_item_delta (§7.3): the amount is still shown, the percentage is suppressed.
  • last_seen is then set to the current balance before moving to the next slot.

8.3 Rollup — the "at least one populated" rule

_rollup_values(items_subset, ascending_slots, item_values_by_id) sums a group of items' per-slot values for every subtotal tier (sub-category, category, grand total, property/non-property). For each slot, it sums only the items that actually have a value that slot; if zero items in the group have data for a slot, that slot is left absent from the result (blank), not written as zero. This means a subtotal is populated as soon as any one item beneath it has data for a quarter — it never disappears just because a sibling item in the same group has no history yet (FUNCTIONAL.html §12.4). Category subtotals are computed by summing directly over every non-Exclusive leaf item in the category (flattened across its sub-categories), not by re-summing the already-computed sub-category subtotal cells — so the "at least one populated" rule is applied once, at the leaf-item granularity, rather than compounding across two levels of rollup.

8.4 Duplicate (year, quarter) slot — winner selection

Only UpdateTrackingList rows with both year and quarter set are eligible for the grid at all — rows missing either are silently excluded from this report (not an error). Eligible rows are grouped in Python by their (year, quarter) tuple; when more than one list shares the same slot (allowed by design — §3, FUNCTIONAL.html §11.1's duplicate-date behavior extends naturally to duplicate quarter/year labels too), the winner is the row with the greatest (created_at, id) tuple — i.e. most recently created wins, with id descending as the final deterministic tiebreak for the vanishingly unlikely case of an identical created_at. This mirrors the tie-break direction of _find_previous_list() in §7.2, but is computed via a plain Python sorted(..., reverse=True)[0] over already-loaded rows rather than a second SQL query, since all candidate rows for the set are loaded in one query up front (§8.5).

8.5 Performance — exactly 6 queries, no N+1

get_balance_grid() issues a fixed, small number of queries regardless of how many years, quarters, categories, or items the tracking set has:

  1. Every UpdateTrackingList row for the set with year and quarter both non-null.
  2. Every UpdateTrackingListBalance row for the winning lists selected in-memory from query 1 (§8.4) — a single WHERE update_tracking_list_id IN (...), not one query per slot.
  3. Category rows for the set.
  4. SubCategory rows for those categories.
  5. TrackingItem rows for those sub-categories.

(Ownership verification of the TrackingSet itself, via _get_set_or_404 in the endpoint, is a 6th query performed by the caller before the service function is entered — see §8.6.) Every grouping, winner-selection, summation, and delta computation described in §8.2–§8.4 happens afterward, entirely in Python against data already loaded — there is no query inside a per-item, per-slot, or per-tier loop.

8.6 Endpoint and ownership

Source: app/api/v1/endpoints/dashboard.py, mounted with no fixed router-level prefix (its one route spells out the full /sets/{set_id}/dashboard/balance-grid path itself, the same pattern already used by update_tracking_lists.py — §5). The endpoint reuses _get_set_or_404 imported directly from update_tracking_lists.py rather than duplicating it, so a cross-user request against someone else's tracking set gets the identical bare 404 (never 403) as every other resource in this service (§5.1). Shared quarter-range computation (chartQuarters, page-level)

A single ChartQuarter[] array, chartQuarters, is computed exactly once at the page level (TrackingDashboardPage) via useMemo and passed as a prop to both chart components — this is what guarantees the two charts' x-axis ranges can never independently drift apart. Each ChartQuarter carries a display label (e.g. "Q3 2026") and a cellIdx: the ORIGINAL (non-reversed) yearIdx*4+quarterIdx position that every cells/subtotal/grandTotal/propertyBreakdown array is positionally aligned to (§8), so both chart components read series values straight out of the existing arrays with no re-derivation of quarter positions.

Construction order inside the useMemo:

  1. Build the full chronological (oldest→newest) list by reversing grid.years — the opposite of the newest-first order the year tables render in below the charts — and flat-mapping each year's 4 quarters, looking up each entry's original (non-reversed) yearIdx via years.indexOf(yearCol) to compute cellIdx.
  2. Define hasDataAt(q) as: any category's subtotal[q.cellIdx]?.hasData is true, OR grandTotal[q.cellIdx]?.hasData is true.
  3. Leading trim (unchanged from the prior revision): firstDataIdx = all.findIndex(hasDataAt) — the first quarter, from the start, with data in any series.
  4. Trailing trim (new in this version): a manual reverse for loop (not Array.prototype.findLastIndex, to stay consistent with this file's existing findIndex/loop idioms elsewhere) finds lastDataIdx — the last quarter, from the end, with data in any series — using the exact same hasDataAt predicate as the leading trim.
  5. The array is sliced to all.slice(firstDataIdx, lastDataIdx + 1), dropping both the leading AND trailing runs of quarters with no data anywhere. Interior gaps (a blank quarter between two populated ones) are untouched by this slice — buildLinePathWithGaps() (below) is what renders those as visible line breaks, not this trim. A defensive guard checks both indices for -1 (only possible together, since both searches use the identical predicate over the identical array) and falls back to the untrimmed all rather than assuming the invariant always holds.

This trim is chart-only. Neither chartQuarters nor its trim logic touches grid.years or any per-year <YearTable> — those still render all 4 quarters of every year exactly as before (FUNCTIONAL.html §12.3/§12.4), unaffected by what the charts choose to trim.

  • Inter-segment gap: a small fixed pixel gap (BAR_SEGMENT_GAP, 2px) separates adjacent segments within one stack, implemented by shrinking each internal segment boundary by half the gap on both sides — never a visible border between segments. The bar's own top and bottom edges are left untouched so its total height still reads accurately against the y-axis.
  • Bar width: capped at a fixed maximum (BAR_MAX_WIDTH, 24px) and scaled down from the available per-quarter horizontal spacing when many quarters are in view, with a floor (BAR_MIN_WIDTH, 4px) so a bar never disappears entirely on a chart with a long history.

Non-Property Total and Grand Total overlay lines (new in this version)

Two additional TrendSeries are built in the same useMemo block as the bars, INDEPENDENTLY of the bar-stacking loop:

  • nonPropertySeries — one point per quarter, read from nonPropertyTotal[q.cellIdx] (null when !hasData, never a fabricated 0), styled with NON_PROPERTY_TOTAL_LINE_COLOR (#06B6D4, this app's existing "info" cyan — the same accent <GrandTotalRows> already uses for the Non-Property Total row's bg-info/border-info highlight, §9.3.5) and a 2,4 dash pattern.
  • grandTotalSeries — one point per quarter, read from grandTotal[q.cellIdx] the same way, styled with the same GRAND_TOTAL_LINE_COLOR used on the left chart's Grand Total line, but with a distinct 6,3 dash pattern here (matching the left chart's own Grand Total dash) — deliberately different from nonPropertySeries's 2,4 pattern so the two overlay lines are never mistaken for each other at a glance even where both are cyan-adjacent in value.

Both series are rendered via the shared buildLinePathWithGaps() helper (§9.3.3), exactly like an ordinary category line — critically, their point values come straight from the nonPropertyTotal/grandTotal arrays, never from reading the computed yTop/yBottom pixel coordinates of the bar segments. The stacking loop and the two overlay-series builders are independent code paths over the same underlying source arrays; any visual alignment between the Non-Property Total line and a stack boundary (the expected outcome when every Property item lives in a distinct category — FUNCTIONAL.html §12.11) is a consequence of both being correct on the same scale, not a computed/enforced relationship in the code.

Always-visible millions-format labels

A local lastPlotted(points) helper walks a series' points backward from the end and returns the last { idx, value } pair with a non-null value — a genuine backward search, not "read the final array entry," since a series can have its own trailing gap at the very last chart-trimmed quarter even after the page-level both-ends trim (§9.3.3) has already removed quarters where every series is blank. The resulting nonPropertyLast/grandTotalLast values are rendered twice: once as an <svg> <text> element anchored at that point (fmtMillions() — the existing value / 1_000_000, 2-decimal, "M"-suffixed convention already used by fmtPnl in action-plan/purchase/[id]/page.tsx and PortfolioSummaryWidget.tsx), and once inline in the legend next to that line's name — both without requiring a hover. The hover tooltip (below) continues to show the fuller thousand-comma fmtBalance() figure for every series at the hovered quarter; mixing fmtMillions into that tooltip was deliberately avoided since these are the only two places on the whole page that use the millions format at all.

Y-axis rescale and shared mechanics

  • Per-quarter stacked total and three-way y-axis rescale: a stackedTotalsByQuarter array sums each quarter's category subtotals (skipping any category with hasData:false that quarter, per the absent-segment convention above). domainValues then concatenates stackedTotalsByQuarter with the non-null values of BOTH grandTotalValues and nonPropertyValues (revised in this version — previously only the stacked totals and the (single, then-combined) chart's own line values were considered) before taking Math.min/Math.max across all three sources — since none of the three is guaranteed by the data model to bound the other two, checking only one or two would risk silently clipping a line or a bar at the top of the chart.
  • Category tooltip series without lines: categoryTooltipSeries builds one TrendSeries per category with strokeWidth: 0 and y: null for every point — these are never drawn as paths, they exist purely so the hover tooltip (below) can list every category's own value alongside the two overlay lines, matching what the pre-split combined chart's tooltip already showed.
  • Hover tooltip: tooltipRows concatenates categoryTooltipSeries with nonPropertySeries and grandTotalSeries; the same onMouseMove/nearest-quarter/crosshair/clamped-tooltip-position mechanics as the left chart (§9.3.3, via the shared clampTooltipX() helper) apply here unchanged.
  • X-axis trimming: this component receives the already-trimmed, both-ends-trimmed quarters prop from the page (§9.3.3) — it performs no trimming of its own, so its x-axis range is identical to the left chart's by construction, not by re-derivation.
  • Documented minimal edge case: if every category has hasData:false for a quarter but the Grand Total or Non-Property Total line still has data there (an inconsistency that should not occur under normal use), the accumulated segment list for that quarter is empty and no bar renders at all — judged less misleading than fabricating a single guessed segment to represent an unknown split. The two overlay lines are unaffected and still plot normally for that quarter, since they are computed independently of the bar-segment loop.

12.1 Tracking-backend export endpoint — contract and ownership model

Source: tracking-backend/app/api/v1/endpoints/export.py, schemas in tracking-backend/app/schemas/export.py.

GET /api/v1/tracking/sets/{set_id}/export

Read-only. This was a deliberate, security-reviewed design choice: an endpoint that emails a JSON dump of a user's full financial data must not be redirectable to an arbitrary address by a malicious or buggy caller, so the recipient is architecturally incapable of being anything other than the authenticated caller's own address.

12.3 get_current_user_with_email — additive dependency pattern and why

Source: backend/app/auth/dependencies.py. A new CurrentUser frozen dataclass ({id: str, email: str}) and a new get_current_user_with_email dependency function were added alongside the existing get_current_user_id — the existing function's signature, return type, and behavior are completely untouched.

get_current_user_with_email duplicates get_current_user_id's entire validation sequence verbatim (missing-credentials check, signature/expiry verification, jti-claim check, Redis blacklist check — fail closed on Redis error) and then additionally extracts the email claim from the already-decoded token payload, raising 401 with "Token missing email claim" if it is absent, rather than falling back to a database lookup.

Why an additive new dependency rather than modifying get_current_user_id to also return the email: get_current_user_id returns a bare str (the user id) and is depended on by a large number of existing endpoints across this backend — changing its return type to a richer object would be a breaking change to every one of those call sites for a capability only this one new endpoint needs. A new, narrowly-scoped dependency avoids that blast radius entirely: every existing endpoint using get_current_user_id is provably unaffected, and the new endpoint's auth requirement (needs the email claim) is visible directly in its own dependency declaration rather than being an incidental side effect of a shared dependency's return shape changing underneath it.

An alternative considered and rejected: looking up the user's email from the users table via user_id (the way send-now already does for its digest-recipient setting, which is a separate, user-editable field). Rejected because the JWT's email claim is exactly the account's registered email at the time of login — sourcing the recipient from the token, not a mutable database column, keeps the "recipient is always the authenticated identity, never a value that could have been separately edited" guarantee (§12.2) airtight without an extra DB round-trip.

12.4 Frontend orchestration sequence and the three failure paths

Source: handleEmailDashboard() in frontend/src/app/(dashboard)/tracking/dashboard/page.tsx, calling buildDashboardEmailHtml() (frontend/src/lib/tracking-export-html.ts), trackingService.getExport() (frontend/src/services/tracking.ts — GET /tracking/sets/{setId}/export, §12.1), and sendExportEmail() (frontend/src/services/emailExport.ts — POST /email/send-export, §12.2).

  1. Build the HTML body — no network call. buildDashboardEmailHtml() is a pure function over data the page has already loaded: the current DashboardBalanceGridOut grid plus the page's own collapsedYears/collapsedCategories/collapsedSubCategories state. It mirrors YearTable's and GrandTotalRows' actual rendering rules exactly (§9.3.2) — a collapsed year renders as a one-line "collapsed, not included in this export" notice with no rows beneath it; a collapsed Category/Sub-category still renders its own subtotal row (exactly like the on-screen collapse behaviour) but omits its children; Grand Total / Property Total / Non-Property Total always render for every visible year. Every user-controlled string (category/item names) is HTML-escaped before being embedded, since this HTML becomes an email body. Uses only inline style="..." attributes — no <style> block or CSS classes — because mail clients unpredictably strip embedded/external stylesheets.
  2. Fetch the full backup export. trackingService.getExport(selectedSetId) calls §12.1's endpoint. If this call fails, the flow stops here — no email is sent at all, since this feature's design rule is that it never sends a dashboard email without a genuine, complete backup attached (a partial send would violate the feature's own purpose). The user sees "Could not build backup — dashboard not emailed".
  3. Base64-encode the backup. utf8ToBase64() (exported from dashboard/page.tsx) runs the export JSON through TextEncoder first and base64-encodes the resulting byte sequence one byte at a time — plain btoa(jsonString) is avoided because it only handles Latin-1 correctly and mangles or throws on any non-ASCII character. This app's real user works in Thai, and tracking data routinely contains Thai text in remark/description-style fields, so this path is exercised by real data, not a theoretical edge case; it is covered by round-trip tests using real Thai text.
  4. Send. sendExportEmail() translates the camelCase payload (subject, htmlBody, attachmentFilename, attachmentContent) to the wire's snake_case body (§12.2) and POSTs to /email/send-export through the same proxy every other call in this app uses. On success, a toast names the recipient address returned by the API.

The button's sendingEmail boolean is set before step 1 and cleared in a finally block wrapping the whole sequence, so the button re-enables after success, after the export-fetch failure, and after a send failure alike.

12.5 MIME structure

EmailService.send_export_email() (backend/app/services/email_service.py) builds the outgoing message independently of send_daily_digest — no price refresh, no widget-data fetch, no DB access at all, since everything it needs (HTML body, subject, attachment bytes) arrives already assembled in the request body:

multipart/mixed                          (top-level message)
├── multipart/alternative                (body_part)
│    └── text/html; charset=utf-8        (the dashboard HTML table)
└── application/json                     (attachment_part)
     Content-Disposition: attachment; filename="<attachment_filename>"

The HTML body is nested inside a multipart/alternative even though there is no plain-text sibling part — mail clients conventionally expect that nesting for an HTML-only body, so it is included for compatibility rather than because a second part exists. Sent via aiosmtplib to smtp.gmail.com:587 with STARTTLS, using the same GMAIL_USER/GMAIL_APP_PASSWORD settings already used by send-now. Any SMTP exception is caught and reported back as SendResult(success=False, error=...) using the same generic, non-leaking error message (_GENERIC_SMTP_ERROR) as every other send path in this service — the real exception (which may contain SMTP hostnames or connection details) is logged server-side only, never returned to the client.

13.1 The note column and presence-aware EntryUpdate

Source: app/models/initial_investment_entry.py (column), app/schemas/entry.py (EntryCreate / EntryUpdate / EntryOut), app/api/v1/endpoints/tracking_items.py and entries.py (handlers).

  • ft_initial_investment_entry.note — VARCHAR(500) NULL (§3). Blank or whitespace-only input is normalised to NULL by a Pydantic field validator before it reaches the DB; any other string is stored verbatim, Thai included. Input longer than 500 characters fails schema validation → HTTP 422.
  • EntryCreate and EntryUpdate gain a camelCase note field. EntryOut and each RunningTotalRow gain note: str | null.
  • EntryUpdate is now presence-aware: the handler applies model_dump(exclude_unset=True), so a field the client omits is left untouched, whereas an explicit note: null or note: "" clears the note. amount: null and entryDate: null are rejected with 422 — those fields are non-nullable and may only be omitted, not nulled.
Existing rows created before this migration have note = NULL and are unaffected. No endpoint requires a note; every ledger read simply returns null for entries that have none.

13.2 profit_math.compute_profit — the single profit formula

Source: new pure module app/services/profit_math.py. compute_profit(*, net_original_investment, current_value) -> ProfitFigures is the only place the profit amount and the profit-percentage guard are implemented. Both the per-item running-total endpoint (§13.6) and the rollup service (§13.3) call it; the frontend never recomputes a percentage of its own.

Output fieldRule
profitcurrent_value - net_original_investment, only when both inputs are non-null; otherwise None.
profit_percentprofit / net_original_investment * 100, only when profit is computable and net_original_investment > 0. When the net is 0 or negative the profit amount is still returned but profit_percent is None — never inf, nan, or a string sentinel. Same zero-guard philosophy as update_tracking.py's _compute_item_delta (§7.3) and dashboard_balance_grid.py's compute_series_deltas (§8.2), except the guard here is > 0 rather than != 0, because a negative cost basis also produces a meaningless percentage.

Definitions the callers pass in:

  • Net original investment (cost basis) — the running signed sum of every ft_initial_investment_entry.amount for the item. None when the item has zero entries; callers render that as "—", never 0.
  • Current value / snapshot — the item's balance in its most-recent populated (year, quarter) slot, taken from the same winning-UpdateTrackingList selection the Dashboard balance grid already uses (§8.4). None when the item has never appeared in any Update Tracking List balance.
  • Covered — initial_investment_tracking = true AND at least one entry AND a current value exists. Being covered does not require the net to be positive.

13.3 original_investment_rollup — the set-wide rollup service

Source: new service app/services/original_investment_rollup.py. get_original_investment_rollup(db, *, tracking_set_id, user_id) builds the per-item and set-level "profit vs original investment" figures for a whole tracking set. As in §7 and §8, aggregation is business logic and lives in a service module, not the endpoint.

Scope and coverage

  • In scope (items[], and coverage.totalCount = M): every non-exclusive item in the set with initial_investment_tracking = true — covered rows and not-yet-covered rows alike (the latter serialised with null numerics). exclusive items and flag-off items are excluded entirely — never a row, never in a total.
  • coverage.shownCount (N) — the number of covered items (§13.2).
  • coverage.excludedItemNames — the names of in-scope items that are not covered.
  • Set-level totals aggregate covered items only. totals.profitPercent is null when the summed net original investment is 0 or negative (the same compute_profit guard, §13.2, applied to the summed inputs).

Reuse of the balance grid

The service calls the existing get_balance_grid() (§8) plus a new additive helper in app/services/dashboard_balance_grid.py, current_value_by_item(BalanceGridResult) -> dict[item_id, Decimal | None], which walks each item's already-materialised cells newest-slot-first and returns the first populated balance — i.e. the item's "current value / snapshot" (§13.2), using the grid's own winner-selection and slot ordering rather than a second, independently-written query path. Net original investment per item comes from one bulk query of all ledger entries for the in-scope item ids, summed in Python.

Fixed query budget — exactly 8

get_original_investment_rollup issues a constant 8 database queries end-to-end, independent of item, entry, or slot count — no N+1:

  1. 1 — tracking-set ownership check (_get_or_404, §5.1).
  2. 5 — the queries inside get_balance_grid() (§8.5: update-lists, winning balances, categories, sub-categories, tracking items).
  3. 1 — the in-scope item ids (non-exclusive, initial_investment_tracking = true) for the set.
  4. 1 — all ft_initial_investment_entry rows for those item ids.
An earlier design draft cited 9 queries; that double-counted the ownership check. The shipped and documented figure is 8.

13.4 Endpoint — GET /sets/{set_id}/dashboard/original-investment

Source: app/api/v1/endpoints/dashboard.py — a second route added alongside the Phase 3 /sets/{set_id}/dashboard/balance-grid route, under the same already-existing /sets/{set_id}/dashboard/... family (no new router, no new prefix — each route spells out its own path, §5).

14.3 Derivation approach — lib/tracking-analysis.ts

Everything Analysis shows is a pure transform of the one DashboardBalanceGridOut response, memoised in the page on [grid, viewState]. Key functions:

  • periodsAsc / cellIndex / readCellSeries — reverse the response's descending years to an ascending (year, quarter) axis and read the positionally-aligned BalanceCell[] arrays into ascending order.
  • nodeTotalSeries(grid, drill) — the authoritative series for the current drill node: depth 0 → the lens aggregate array verbatim; depth 1/2 under Grand Total → subtotal[] verbatim; depth 1/2 under Property / No-Property → a derived per-period sum (rollupBalances) over lens-qualifying non-exclusive leaf items; depth 3 → the item's cells[].
  • deriveChartModel — builds group-by buckets (verbatim vs derived per lens/depth/groupBy), applies the "Other" rollup (rollupOther, cap 8), trims leading/trailing all-null periods (trimEmptyEnds, the exact rule the dashboard chart uses), applies granularity, and computes 100%-stacked shares (computeComposition).
  • asOfYearlySeries(balances, axis) — the one genuinely new derivation: per year, pick the highest-index quarter that has data (Q4→Q3→Q2→Q1); null if none; also returns the as-of quarter for labelling ("2025 (as of Q3)").
  • buildScopedGrid(grid, viewState) — the Scoped Dashboard model: drill-subtree selection, verbatim-vs-derived scope total per lens, split-row derivation, exclusive block, per-depth row shape, and the empty / lens-mismatch states. Reacts to lens + drill; groupBy + comparison are ignored.
  • resolveComparison, buildStatRow (scope-aware — computed from the same nodeTotalSeries), annualisedChange.

14.4 The delta-engine TypeScript replica and parity tests

The authoritative delta math is compute_series_deltas in tracking-backend/app/services/dashboard_balance_grid.py (§8.2). Analysis uses the server-provided deltaAmount / deltaPercent verbatim wherever a matching row exists (every item's cells[]; every category / sub-category subtotal[] under the Grand Total lens). It re-computes deltas in TypeScript (computeSeriesDeltas in lib/tracking-analysis.ts) only for derived series with no server row: item-type buckets, lens-filtered hierarchy subtotals (Property / No-Property), yearly as-of series, Scoped Dashboard derived totals and split rows, and the "Other" band.

The replica is byte-for-byte: a blank slot yields null deltas and does not advance the "last seen" value; the first populated slot yields null (never 0); deltaPercent is null only when the prior populated value is exactly 0 (no epsilon, no cap); year boundaries are crossed freely. Two tests in lib/__tests__/tracking-analysis.test.ts lock this:

  • Golden-fixture delta parity — balance / deltaAmount / deltaPercent values copied from a real balance-grid response; the TS replica must reproduce the server deltas on the Grand Total lens.
  • Trim parity — trimEmptyEnds must produce the identical leading/trailing-null window the dashboard chart produces for the same data.

ADR-019's Consequences note that this parity must be re-verified on any change to the server engine.

14.5 URL serialisation and hostile-input handling

ViewState ⇄ URL via flat query params (lens, g, m, groupBy, cat/sub/item, delta, cmp/cmpA/cmpB, snap, scoped), each omitted at its default; this shareable link is the only "saved view". queryToViewState clamps every enum param through an allow-list back to the default, parses period refs with a strict ^(\d{4})(?:Q([1-4]))?$ regex, only honours a deeper drill id if its parent id is present, and forces groupBy to a value allowed for the hydrated depth.
