Part I — Functional

1. Overview & purpose

The Analysis view is a read-only exploration surface over the data already captured by the Tracking Updates sub-menu (§11 of FUNCTIONAL.html) and already exposed by the Dashboard balance-grid endpoint (§12). It adds no data entry and no new stored data. It lets a single investor answer, from one screen fed by one API call, four questions about their tracked net worth:

InstrumentQuestion it answers
TrendHow has a value moved over time? (multi-series line / area across quarters or years)
CompositionWhat share of a total does each part hold, and how is the mix shifting? (100% stacked area over time; ranked horizontal bar at one period)
Delta trendHow large was each period-over-period change, and when did the big moves happen? (diverging bars around a zero baseline; waterfall toggle)
Scoped DashboardWhat does the main Dashboard's numeric table look like for just this category / sub-category / item? (per-year quarterly grid or a yearly "as-of" grid, with scope totals, sub-totals, item rows and per-period deltas)

Every instrument is sliceable by an amount-type lens, by the category hierarchy (drill Category → Sub-category → Item), and — for the charts — optionally by item type. Granularity is quarterly or yearly only. A quarter-vs-quarter / year-vs-year comparison panel and a client-side CSV export of the current view are also provided.

1.1 Navigation

Analysis is the 4th sub-link under the Tracking sidebar accordion, after Category, Updates and Dashboard, at /tracking/analysis. The set is chosen with the same on-page tracking-set <select> used on the other tracking pages; it defaults to the user's first set.

1.2 What it is not (this iteration)

  • No data entry or editing — balances are recorded only via Updates.
  • No persistent saved / named views. The current view is serialised to the URL query string; that link is the only "saved view" and is ephemeral, not a stored preset.
  • No annotations, notes, thresholds or alerts on charts or grid rows.
  • No real-time, auto, or scheduled refresh, and no emailed / pushed snapshots. Data loads once per navigation from the single balance-grid call; the user re-navigates or reloads to refresh.
  • No monthly or finer granularity.
  • No server-rendered / PDF / formatted export report — CSV only.
  • Dark theme only. A light theme is deferred to an app-wide theming effort.

2. Global controls

All controls are global — one filter row scopes every chart, the Scoped Dashboard and the export. A single ViewState object is the source of truth; every control mutates it and one render pass follows. The control row is: Amount lens · Granularity · Measure · Group by · Comparison.

2.1 Amount-type lens

A 3-way selector: Grand Total / Property / No Property. The mapping is exactly the server's:

  • Grand Total — every non-exclusive tracking item.
  • Property — items of type Property only.
  • No Property — the other five types (Bank account, Investment Account, TaxSaving, Materials, Insurance).

Exclusive items are always excluded from every series, subtotal, total, breakdown and export, under every lens — they remain reachable only as an explicit leaf drill target, where they are shown greyed and annotated "excluded from totals". Switching the lens re-filters which items feed every series and re-renders everything. Changing the lens keeps the current drill path (a deliberate change from an earlier design draft) so a lens that has no qualifying items in the current scope surfaces an explicit "switch to Grand Total" recovery state rather than silently resetting; clicking the lens breadcrumb crumb still resets the drill to root.

2.2 Group by

The group-by options depend on drill depth:

DepthNode shownDefault group-byAllowed group-by
0Lens total (whole set)CategoryCategory, Item type
1One categorySub-categorySub-category, Item type
2One sub-categoryItemItem, Item type
3One item (leaf)— (single series)—

Item type is an orthogonal cross-cut: at any depth it buckets the current node's descendant items by TrackingItem.type, ignoring category structure. Item-type buckets are not drillable and are most meaningful under the Grand Total lens.

2.3 Drill-down & breadcrumb

The drill path is Lens → Category → Sub-category → Item. A breadcrumb shows the path with clickable ancestor crumbs and an Up control that steps one level. Clicking a chart line, band or bar drills into that bucket unless already at a leaf item; clicking an item row in the Scoped Dashboard also drills the whole view to that item (depth 3). Drilling one level advances the group-by to that depth's default and clears the breakdown snapshot period. A leaf shows a single series with a "most detailed level — drill disabled" note.

2.4 Granularity — and the "as-of year end" rule

Quarterly / Yearly only.

  • Quarterly plots one point per populated (year, quarter) slot; interior blanks are skipped (rendered as gaps, never interpolated); leading and trailing all-blank periods are trimmed.
  • Yearly uses the "as-of year end" rollup: a year's value is the balance of that year's latest populated quarter (Q4 if present, else Q3, else Q2, else Q1); null if the year has no populated quarter. Every yearly label and tooltip names the source quarter — e.g. "2025 (as of Q3)" — so a yearly number is never ambiguous. Year-over-year deltas run the same delta algorithm over the yearly series (one value per year, ascending), comparing to the nearest earlier year that has an as-of value; the first populated year shows "No prior data".

Rationale: balances are stock quantities (point-in-time net worth), not flows — summing four quarters double-counts and averaging has no net-worth meaning, so both were rejected. "Latest populated quarter" approximates "net worth at year end" and degrades gracefully when Q4 is missing (normal for the in-progress year). A granularity change while a comparison is active clears the comparison with a transient notice ("Comparison cleared due to granularity change") — a comparison never mixes a quarter with a year.

2.5 Measure

Balance / Δ Amount / Δ %. In the charts, measure selects the plotted quantity outright. In the Scoped Dashboard grid the Balance column is always shown and measure only selects the companion delta column (Δ Amount vs Δ %).

Δ% is null only when the prior populated value is exactly 0 — no epsilon, no magnitude cap. This matches the server engine (compute_series_deltas) verbatim. In that case a tooltip / cell reads "n/a (prior was ฿0)", never "∞" or "NaN". The first populated period of any series has null deltas (never 0).

3. The four charts

Common conventions. Charts render chronological ascending (the response's descending years is reversed once). Categorical palette ['#3987e5','#d95926','#199e70','#c98500','#d55181','#008300','#9085e9','#e66767'], fixed order, modulo-wrapped; a bucket keeps its colour across all four charts of a view. The lens/scope-total overlay line is #E2E8F0, dashed and thicker, with a bold legend label — never a categorical slot. Interior nulls are gaps (never interpolated); leading/trailing all-null periods trimmed. More than 8 buckets → the smallest are folded into a muted, non-drillable "Other (n)" band (#64748B). Every chart <svg> is role="img" with a descriptive aria-label; sign is carried by an arrow and a +/− label as well as colour.

4. KPI stat row

Five always-visible tiles below the breadcrumb. Each is a mono uppercase caption, a big value, a sign-coloured delta chip carrying an arrow + sign, and a muted label. The row is scope-aware: it reacts to both the lens and the drill node, and is computed from the same node-total series the Scoped Dashboard scope-total row uses, so the two never disagree by construction.

TileDefinition
Latest valueThe latest populated period's value, plus its period label.
Latest changeΔ amount + Δ % for the latest populated period vs the nearest earlier populated period.
Change over rangelast − first populated value; % = amount / first × 100, null when first is 0; label spans e.g. "Q2 2022 → Q3 2025".
Annualized change(last / first)^(1/years) − 1, only when first > 0, last > 0 and the span is ≥ ~1 year; otherwise "n/a".
Populated periodscount / total in the visible range.

When the current node has no qualifying items for the lens, the row renders in a cleared state.

5. Scoped Dashboard section

A full-width, titled, collapsible card positioned below the KPI stat row and above the four charts — precise figures first, visual analysis second. It reproduces the main Tracking Dashboard's numeric readout but constrained to the current drill scope. It reacts to lens, drill, granularity and measure; it deliberately ignores groupBy and comparison and always rolls up the natural Category → Sub-category → Item hierarchy. It is 100% client-side off the one already-fetched balance-grid response — no new endpoint, no new fetch.

Header: a chevron + "Scoped Dashboard" title and a right-aligned sub-caption echoing the live scope, e.g. Category: Investments · Quarterly · Grand Total. The header is one keyboard-operable <button> (aria-expanded + aria-controls). Wide grids scroll inside their own overflow-x:auto container; the page body never scrolls sideways.

5.1 The lens interaction rule (critical)

The server subtotal[] / grandTotal[] arrays are NOT type-filtered — they sum all non-exclusive items regardless of type. Therefore:
  • Under the Grand Total lens, a scoped category / sub-category total uses the server subtotal[] verbatim.
  • Under the Property or No Property lens, the scoped total must be a derived per-period sum over only the lens-qualifying, non-exclusive leaf descendant items, with deltas from the client TS re-implementation of the server delta rule (§Part II).
Exclusive items are always their own badged row and never enter any total, verbatim or derived, and are never type-filtered by the lens.

5.2 Rendering by drill depth

Depth 0 — the grid does not render

A whole-set grid would duplicate /tracking/dashboard, and the page's own KPI row + charts already cover the whole-set view. The card stays visible but collapsed, with the hint "Drill into a category, sub-category, or item to populate the Scoped Dashboard." If manually expanded at depth 0, it shows only a slim 3-row lens-total strip — Grand Total / Property / Non-Property, each as its as-of-latest-populated value, sourced verbatim from grandTotal[], propertyBreakdown.propertyTotal[], propertyBreakdown.nonPropertyTotal[].

Depth 1 — category

Rows, top to bottom:

  1. Scope total "Total: {category}" — Grand Total lens → category.subtotal[] verbatim; Property / No-Property → derived sum over the category's lens-qualifying non-exclusive leaf items.
  2. Per sub-category in orderIndex order: a bold subtotal row (same verbatim-vs-derived rule) then its indented item rows (item.cells[] verbatim; non-qualifying-type items hidden under a Property / No-Property lens).
  3. Grand Total lens only: two split rows "Property portion" / "Non-Property portion" — derived sums split on item.type === 'Property' vs the other five types. Placed immediately under the scope total (a split of it), before the sub-category breakdown.
  4. If the category has exclusive descendants: a separated "Excluded from total (exclusive)" block — each row badged, no rollup.

Depth 2 — sub-category

Rows: (1) scope total "Total: {sub-category}" (verbatim subCategory.subtotal[] under Grand Total, else derived); (2) item rows, one per qualifying non-exclusive item; (3) split rows only under the Grand Total lens and only if the sub-category actually holds mixed item types, otherwise the one-line note "All items in this sub-category are type: X"; (4) an exclusive block if any.

Depth 3 — single item (leaf)

No scope total, no subtotal, no split, no child rows. Shows: a scope identity strip (item name, type badge, "Exclusive" badge if set); one balance row across the period axis with its deltas; a scope-facts strip (first populated period, last populated period, populated-period count in the window, peak balance + its period, trough + its period, net change over the window, latest Δ amount + %); and the note "This scope is a single item; its balance is shown directly."

5.3 Yearly "as-of year end" grid

In yearly granularity the section renders a single table: one column per year (descending); each row's cell is the as-of-quarter balance for that row's own series; the column header is annotated with the as-of quarter, e.g. "2025 (as of Q3)". Year-over-year delta compares a year's as-of balance to the nearest earlier year with an as-of balance (blank years skipped); the first populated year shows "No prior data"; Δ% is "—" when the prior as-of balance is exactly 0. A fully-blank year shows "no data" and "—" for delta. Interior all-blank quarters within a rendered year are kept; only whole leading/trailing blank years are trimmed.

5.4 Collapse behaviour

Default state is per-depth: expanded at drill depth ≥ 1, collapsed at depth 0. A manual toggle (ViewState.scopedDashboardCollapsed) sticks across lens / drill-at-same-depth / granularity / measure changes, but reverts to the per-depth default whenever the drill depth changes. Collapse state is client-side only (mirrored to the URL as scoped=0|1 when overridden).

6. Comparison panel

Rendered only when comparison mode is not Off, at the bottom of the view (a dedicated panel, never an overlay on the primary charts). It shows paired bars per current group-by bucket (A muted, B brand) plus a table with value A, value B, Δ (sign-coloured), Δ %, and a bold lens-total row. The header states the exact resolved periods and any gap fallback, e.g. "YoY · by category · Q2 2024 → Q3 2025". Per bucket: Δ = valueB − valueA; Δ% = Δ / valueA × 100, null when valueA is null or ≤ 0. The panel is transient — it never persists and is cleared on a granularity change.

ModeResolution
OffPanel hidden.
QoQB = latest populated quarter; A = the nearest earlier populated quarter.
YoYB = latest populated quarter; A = the same quarter one year earlier if populated, else the nearest earlier populated period in a prior year (the header names the actual fallback period), else "Insufficient data for a year-over-year comparison."
CustomThe user picks A and B from the list of populated periods.

When fewer than two populated periods exist: "Need at least two populated periods to compare."

7. CSV export

An Export view (CSV) button, top-right. Export is client-side only — no server round-trip. The file is built in the browser, wrapped in a Blob with a leading UTF-8 BOM (﻿) so Thai text opens correctly in Excel, uses \r\n line endings and RFC-4180 quoting, and is offered through a transient <a download>.

7.1 Header comment lines

The file opens with #-prefixed comment lines recording the applied context, then the column header row:

# tracking_set: <name>
# lens: Grand Total | Property | No Property
# drill_path: Grand Total › Investments › Stocks
# group_by: Category | Sub-category | Item | Item type
# granularity: Quarterly | Yearly
# measure: balance | deltaAmount | deltaPercent
# generated_at: <ISO-8601>
# comparison: QOQ | YOY | CUSTOM            (only when a comparison is active)
# comparison_period_a: <label>             (only when a comparison is active)
# comparison_period_b: <label>             (only when a comparison is active)

7.2 Body rows

One CSV covers both the chart-derived bucket rows (one row per bucket × period, plus a lens/scope-total "aggregate" row) and the Scoped Dashboard grid rows — the latter only when that section is expanded (at depth ≥ 1). Columns: tracking_set, lens, drill_path, group_by, granularity, period_label, period_year, period_quarter (blank for yearly), as_of_quarter (blank for quarterly), bucket_name, bucket_kind, balance, delta_amount, delta_percent, share_percent, has_data. Rows reflect the on-screen derived data (post lens filter, post trim, yearly rule applied). bucket_kind is one of category, subCategory, item, itemType, other, aggregate, subCategoryTotal, scopeTotal. No exclusive items appear in any export (split rows, exclusive rows and the depth-0 lens strip are also omitted from the CSV body).

7.3 Comparison CSV

When a comparison is active a second file analysis_..._comparison.csv is also downloaded, with the same # header lines and columns bucket_name, period_a_label, value_a, period_b_label, value_b, delta_amount, delta_percent (one row per bucket, plus the lens-total row).

7.4 Filename

analysis_{setSlug}_{lens}_{groupBy}_{granularity}_{YYYYMMDD}.csv — the date stamp is UTC from generated_at; the comparison file appends _comparison.

Formula-injection neutralisation (added in security review). Any CSV field whose value begins with =, +, -, @ or a tab is prefixed with a single quote (') before quoting, so a maliciously-named category or item cannot execute as a formula when the file is opened in a spreadsheet. Numeric columns are emitted as bare finite numbers (or blank) and bypass this path.

8. Empty & isolation states

  • No tracking set → a "create a tracking set" prompt with a link to the Category page.
  • Tracking set but no Update list with both a year and a quarter set → "No quarterly data yet" with a link to Updates.
  • Drilled node with no qualifying items for the lens → a per-chart "No qualifying items for '{lens}' at this level" state; the KPI row clears.
  • Leaf node → "most detailed level" note; drill disabled.
  • Another user's set id → the endpoint returns a bare 404 and the client shows "Tracking set not found, or the balance grid failed to load." — no indication the set exists (same ownership convention as the rest of the module).

Part II — Technical

9. Governing principle

Extend the existing read path; add no new aggregation and no pre-aggregated storage. Analysis fetches the one balance-grid response and performs only thin, pure, unit-tested transforms over it in the browser. The authoritative delta math stays single-sourced on the server; the client replicates compute_series_deltas semantics only for derived buckets that have no server-provided row. Frontend-only change: no new or modified endpoint, schema, migration, enum, or backend code.

11. ViewState and the derivation library

11.1 ViewState

type Granularity = 'quarterly' | 'yearly';

type GroupByDim  = 'category' | 'subCategory' | 'item' | 'itemType';

interface DrillPath   { lens: Lens; categoryId?: string; subCategoryId?: string; itemId?: string }
type PeriodRef        = { kind: 'quarter'; year: number; quarter: 1|2|3|4 }
                      | { kind: 'year';    year: number };
interface ComparisonConfig { mode: ComparisonMode; periodA?: PeriodRef; periodB?: PeriodRef }

interface ViewState {
  trackingSetId: string;
  lens:        Lens;              // default 'grandTotal'
  granularity: Granularity;       // default 'quarterly'
  measure:     Measure;           // default 'balance'
  groupBy:     GroupByDim;        // default follows drill depth
  drill:       DrillPath;         // default { lens: 'grandTotal' }
  snapshotPeriod?: PeriodRef;     // Breakdown focus; default = latest populated
  deltaMode:   DeltaMode;         // default 'bars'
  comparison:  ComparisonConfig;  // default { mode: 'off' }
  scopedDashboardCollapsed?: boolean;  // undefined ⇒ per-depth default
}

Drill depth is drill.itemId ? 3 : drill.subCategoryId ? 2 : drill.categoryId ? 1 : 0.

12. The client TS replica of compute_series_deltas

The authoritative delta math lives on the server (tracking-backend/app/services/dashboard_balance_grid.py, compute_series_deltas). Wherever a matching server row exists — every item's cells[], and every category / sub-category subtotal[] under the Grand Total lens — the client uses the server deltas verbatim. It re-computes deltas in TypeScript only for derived series that have no server row:

  • item-type buckets (groupBy = 'itemType');
  • lens-filtered hierarchy subtotals (any hierarchy bucket under the Property or No-Property lens — server subtotals are not type-filtered);
  • yearly "as-of" series (any granularity = yearly series);
  • Scoped Dashboard derived totals and split rows;
  • the "Other" rollup band.

computeSeriesDeltas replicates the engine exactly:

lastSeen = null
for v in balances:
  if v == null:  deltaAmount = null; deltaPercent = null; lastSeen unchanged; continue
  if lastSeen == null:  deltaAmount = null; deltaPercent = null          # first point — null, never 0
  else:
    deltaAmount  = v - lastSeen
    deltaPercent = (lastSeen == 0) ? null : deltaAmount / lastSeen * 100  # null ONLY at exactly 0
  lastSeen = v

Blank slots are skipped and year boundaries crossed freely, identical to the server. Parity is locked by tests: a golden-fixture parity test uses balance / deltaAmount / deltaPercent values copied from a real balance-grid response and asserts the TS replica reproduces the server deltas on the Grand Total lens; a trim-parity test asserts trimEmptyEnds yields the identical trimmed window the dashboard chart produces for the same data. Any change to the server engine must be re-verified against these tests (recorded in ADR-019 Consequences).

13. URL serialisation & hostile-input handling

ViewState is fully URL-serialisable via flat query params, and the URL is the only "saved view" (NFR-3, ADR-019 #8). Keys, all omitted when at their default: lens, g (granularity), m (measure), groupBy, cat / sub / item (drill), delta (deltaMode), cmp / cmpA / cmpB (comparison), snap (snapshot period), scoped (0 = force-collapsed, 1 = force-expanded).

  • Enum clamping. queryToViewState passes every enum-valued param through oneOf(value, allowed, fallback): an unrecognised value is silently reset to the default rather than propagated.
  • Period-ref parsing. cmpA / cmpB / snap are parsed by the regex ^(\d{4})(?:Q([1-4]))?$; anything malformed yields undefined.
  • Drill hydration. sub is only honoured if cat is present; item only if sub is present. groupBy is forced to an allowed value for the hydrated depth (and to 'item' at depth 3).
  • Invalid-drill-id reset to root. After the grid loads, the page validates the hydrated drill path against it: a categoryId / subCategoryId / itemId that no longer resolves (renamed, deleted, or a cross-set link) resets drill to { lens }, groupBy to the depth-0 default, and clears snapshotPeriod and scopedDashboardCollapsed — the user lands on the default view rather than stranded on an empty state.

No secret or PII is ever placed in the query string — only non-secret view state.

14. Rendering, data source & memoisation

  • Single data source. trackingService.getBalanceGrid(setId) → GET /api/v1/tracking/sets/{set_id}/dashboard/balance-grid, via React Query key ['tracking-analysis-balance-grid', selectedSetId] (staleTime 10 s). The tracking-set list uses ['tracking-sets']. No other network call is made on lens switch, drill, granularity toggle, measure change, comparison, export, or Scoped Dashboard collapse.
  • Memoisation. chartModel = useMemo(() => deriveChartModel(grid, viewState), [grid, viewState]); scoped = useMemo(() => buildScopedGrid(grid, viewState), [grid, viewState]); statRow is keyed on [chartModel]; the comparison model on [chartModel, viewState.comparison, viewState.groupBy, viewState.lens]. The "Other" cap bounds the series count; data is solo-investor scale (tens of periods × hundreds of items) so recomputation is trivial.
  • Charts. Hand-rolled inline SVG only, via components/charts/svg-primitives.tsx — no charting library (ADR-019 #5). Each chart <svg> scales via viewBox + width:100%; height:auto, is role="img" with an aria-label, and offers a table view so no value is hover-gated.
  • Theme. Dark-only; the view reuses the existing dark design tokens and card shells. No prefers-color-scheme or theme-toggle handling in this feature.

15. Security posture

  • No new endpoint, no new auth surface, no new stored data, no mutations, no audit-log entries for viewing. Same per-user isolation as the rest of the module — a bare 404 (never 403) for another user's set.
  • The CSV blob path contains only the user's own on-screen figures; it makes no network request. Formula-injection neutralisation (leading = + - @ or tab → prefixed ') is applied to every text field (§7).
  • URL query params carry only non-secret view state.
  • Security Gate 4: approved.

17. ADR-019 — summary

Status: Accepted (2026-08-30). Full text: 18-financial-tracker/ANALYSIS-DESIGN.html §5.

Context

The balance-grid endpoint is recomputed from UpdateTrackingList / UpdateTrackingListBalance on every call (6 queries; all grouping / summation / delta done in-memory in Python). It is quarterly only — "years" is a display grouping; there is no yearly aggregation anywhere. Per-cell deltas come from compute_series_deltas. The frontend has no chart library; the app is dark-only; data scale is a single investor. A read-only Analysis view was wanted (trend, composition, delta-trend; sliceable by lens / hierarchy / item type; quarterly and yearly; QoQ / YoY; export) with no data entry, saved views, or annotations this iteration.

Decision

  1. Build Analysis entirely on the frontend from the existing balance-grid response — no new endpoint, no pre-aggregated storage, no migration.
  2. Yearly rollup = "as-of year end": a year's value is the balance of its latest populated quarter; every yearly label names the as-of quarter; YoY deltas use the nearest-earlier-populated rule.
  3. Reproduce compute_series_deltas in a shared, unit-tested lib/tracking-analysis.ts only for derived series; use server deltas verbatim where a row exists; lock parity with golden-fixture tests.
  4. Export = client-side CSV only, with # header comment lines; the body carries the visible derived rows plus the Scoped Dashboard grid rows when that section is expanded. No server export, no PDF.
  5. Charts use the existing hand-rolled inline-SVG pattern via a small extracted svg-primitives module. No charting library.
  6. New route /tracking/analysis; a 4th SubLink under the Tracking accordion; ViewState is URL-serialised.
  7. Dark-only; a future app-wide light theme must revisit these tokens.
  8. Read-only exploration only — no saved / named views, annotations, or auto-refresh; the only client-persisted state is disposable UI preference.
  9. Scoped Dashboard section (rev 2): a collapsible card reproducing the main dashboard's tabular readout constrained to the drill scope, 100% client-side off the same single response; verbatim subtotal[] under Grand Total, derived sums under Property / No-Property.

Alternatives considered

  • A ?granularity=yearly variant or a dedicated yearly endpoint — rejected: forks the delta engine into two implementations for no benefit at this scale.
  • Pre-computed aggregation tables / materialised views — rejected: contradicts the recompute-from-source design; adds migration + drift risk for a solo dataset.
  • Recharts / visx / Chart.js — rejected: inconsistent with the codebase, bundle cost; the required charts fit the existing pattern.
  • Yearly = Q4-only — rejected: blanks any year whose Q4 is unreported even when earlier quarters have data.
  • Yearly = sum / average of the four quarters — rejected: balances are stock quantities, not flows.
  • Server-rendered / PDF export — declined by the user; adds a backend surface and a templating dependency for a single-user tool.
  • Reuse the dashboard's YearTable for the Scoped grid — rejected: it is coupled to the full tree and the whole-set summary rows.

Consequences

Positive: zero backend change, no migration; the heavy delta math stays single-sourced on the server; charts and the Scoped grid stay visually consistent; derivations are pure and independently testable; a shareable URL doubles as an ad-hoc saved view.

Negative: the delta algorithm now exists in Python and TypeScript (used for derived series) — parity must be kept by tests and re-verified on any server-engine change; yearly granularity adds an as-of-quarter annotation everywhere a year is labelled (charts, CSV, Scoped grid); all recomputation runs in the browser inside useMemo; dark-only means no theme handling here; the read-only lock means no persistence layer.

Risks

Parity drift (Python vs TS delta engine); yearly-rule surprise; readability of 100%-stacked / snapshot with many categories; sparse-quarter Δ% distortion; Scoped Dashboard vs KPI-row figure redundancy (mitigated by making the StatRow scope-aware so both are computed from one series). Full risk table: design spec §6.
