1. Overview

The Analysis view is a new, fourth sub-link under the Financial Tracker's Tracking sidebar group (after Dashboard, Updates, Category), at route /tracking/analysis. It is a read-only exploration surface over data already captured by the Updates sub-menu and already exposed by the Dashboard balance-grid endpoint. It lets a single investor answer three questions about their tracked net worth:

  • Trend — how has a value moved over time (line / area across quarters or years)?
  • Proportion / composition — what share of a total does each part hold at a point in time, and how is the mix shifting (100% stacked area over time, ranked bar at one period)?
  • Delta trend — how large was each period-over-period change, absolute and %, and when did the big moves happen (diverging bars / waterfall)?

All three are sliceable by an amount-type lens (Grand Total / Property / No Property), by the category hierarchy (Category → Sub-category → Item), and optionally by item type. Granularity is quarterly or yearly only. The view also offers quarter-vs-quarter and year-vs-year period comparison and an export of the current view.

1.1 In scope

  • Charts: trend, composition-over-time, breakdown-at-a-period, delta-trend (bars + waterfall), a comparison panel, and a KPI stat row.
  • Scoped Dashboard section (rev 2) — the main dashboard's tabular readout (per-year balance grid, scope-total / subtotal / item rows, per-period deltas, Property/Non-Property split, completeness stats) constrained to the current drill scope. See §4.9.
  • Filters: amount-type lens; time granularity (quarterly / yearly); measure (Balance / Δ Amount / Δ %); group-by dimension.
  • Drill-down: Lens → Category → Sub-category → Item, with a breadcrumb and an "Up" control; click a mark to drill.
  • Period comparison: Off / QoQ / YoY / Custom.
  • Export of the current on-screen view — client-side CSV download (§4.8).

1.2 Out of scope this iteration

The feature is read-only exploration only (OQ-7, locked by the user). The following are explicitly deferred — see the Future roadmap in §5.5:

  • Any data entry / editing (balances are entered only via Updates).
  • Persistent saved / named views and a "My Views" menu. A URL that encodes the current view state is the only "saved view" and is ephemeral / informational — not a stored preset.
  • Annotations, notes, thresholds, or alerts on charts or grid rows.
  • Real-time or auto / scheduled refresh, and emailed or pushed analysis snapshots. Data loads once per navigation from the single balance-grid call; the user re-navigates or reloads to refresh.
  • Monthly or finer granularity.
  • A server-rendered / formatted export report (PDF, styled HTML) mirroring the Email Dashboard export — declined by the user, not merely deferred.
  • A light theme — deferred to an app-wide theming effort, not this feature's concern.
  • Enhanced point-by-point keyboard charting beyond the trend-chart period cursor described in §4.5.

3. Phase 1 — Requirements

business-analyst

3.1 Business objective & measurable outcomes

Enable the investor to explore the composition, trend, and period-over-period change of their net-worth data from multiple analytical perspectives — supporting ad-hoc discovery, drill-down, and export — without manual spreadsheet extraction.

Outcomes: the investor can (a) slice by amount-type lens, (b) navigate the full category hierarchy, (c) visualise trend, composition, and delta, (d) compare any two quarters or years, and (e) export the current view — all read-only, at quarterly and yearly granularity, from one screen fed by one API call.

3.2 User stories

  • As the investor, I want to see my net-worth trend over time so that I understand my long-term trajectory.
  • As the investor, I want to break net worth down by category so that I see which categories drive change.
  • As the investor, I want period-over-period change surfaced explicitly so that I spot when significant shifts occurred.
  • As the investor, I want to switch between Grand Total, Property, and No Property so that I can isolate real-estate participation.
  • As the investor, I want to drill Category → Sub-category → Item so that I can chase a movement to its source.
  • As the investor, I want to compare two quarters or two years so that I can quantify performance across periods.
  • As the investor, I want to export what I'm looking at so that I can analyse offline or keep a record.

3.4 Acceptance criteria (Given / When / Then — representative set)

Lens

  • AC-1 — Given a set with quarterly data, When the user selects Property, Then every chart, subtotal, and drill target reflects only type == "Property" items and exclusive items remain excluded.
  • AC-2 — Given the Property lens is active, When the user selects Grand Total, Then all five non-Property types are re-included, exclusive items still excluded, and the drill path resets to root.

Drill / breadcrumb

  • AC-3 — Given Grand Total › Category at root, When the user clicks a category mark ("Investments"), Then the breadcrumb becomes Grand Total › Investments, charts show that category's sub-categories, and group-by advances to Sub-category.
  • AC-4 — Given the user is at Grand Total › Investments › Stocks, When they click "Investments" in the breadcrumb (or "Up"), Then the view returns to Grand Total › Investments and re-renders immediately.
  • AC-5 — Given any drill depth, When the user clicks the lens crumb, Then the view returns to root (Lens → Category, no drill).
  • AC-6 — Given a drilled node with zero qualifying sub-members for the lens, When the drill renders, Then an empty state is shown and further drill is disabled.

Granularity

  • AC-7 — Given quarterly view, When the user switches to Yearly, Then periods aggregate to years (value = latest populated quarter of the year), the x-axis shows years ascending, and each yearly label/tooltip names its as-of quarter.
  • AC-8 — Given yearly view, When the user switches to Quarterly, Then all populated quarters return, interior blanks are skipped, and deltas recompute per quarter.
  • AC-9 — Given granularity changes while a comparison is active, Then the comparison is cleared with a note ("Comparison cleared due to granularity change"); comparisons never mix a quarter with a year.

Trend chart

  • AC-10 — Given data in Q1, Q3, Q4 (Q2 blank), When the quarterly trend renders, Then the line connects Q1 → Q3 → Q4 with no Q2 point and no interpolation.
  • AC-11 — Given the user hovers a data point, Then a tooltip shows period label, series name, balance, Δ amount, and Δ% (or "n/a (prior was ฿0)").
  • AC-12 — Given ≥ 2 buckets, When the trend renders, Then one categorical-coloured line per bucket plus a dashed near-white "Lens total" overlay; clicking a legend label toggles that line's visibility.

Composition

  • AC-13 — Given Grand Total › Category quarterly, When the composition chart renders in Share mode, Then each period is a 100%-tall stack of category bands summing to 100%, hover shows each band's % and absolute value.
  • AC-14 — Given > 8 buckets, When composition renders, Then the smallest are rolled into a muted "Other (n)" band that is not a drill target.
  • AC-15 — Given the breakdown-at-a-period view, When the user steps the period with ◀ ▶, Then it moves only across populated periods and disables at the first/last populated period; null buckets render as a short "no data" tick sorted last.

Delta trend

  • AC-16 — Given balance rises then falls across three populated periods, Then the delta chart shows an up gain-coloured bar, a down loss-coloured bar, and no bar for the first period; sign is also shown by arrow/label.
  • AC-17 — Given a prior populated balance of exactly ฿0 and a current balance of ฿100, Then the bar shows Δ = ฿100 and Δ% renders "n/a" (never ∞).
  • AC-18 — Given an interior gap between two populated periods, Then the later bar is labelled "vs {last populated period}".

Comparison

  • AC-19 — Given the user selects QoQ, Then period B = latest populated quarter, period A = nearest earlier populated quarter, and the panel shows paired bars + a table (value A, value B, Δ, Δ%) per current bucket, with a lens-total row.
  • AC-20 — Given YoY where the same quarter one year earlier is a gap, Then the panel falls back to the nearest earlier populated period and its header names the actual periods used.

Export

  • AC-21 — Given the user exports while viewing quarterly Property › Investments with 4 sub-category series over 6 periods, Then the export's trend table has 24 rows (6 × 4), contains no exclusive items, and figures match the screen to the cent; the header line records lens / group-by / drill path / granularity / timestamp.
  • AC-22 — Given category names contain Thai text, When the file opens in Excel, Then characters render correctly (UTF-8 with BOM).

Empty / isolation

  • AC-23 — Given a user with no tracking set navigates to /tracking/analysis, Then a "create a tracking set" prompt with link is shown, no charts.
  • AC-24 — Given a tracking set with no Update list that has both year and quarter set, Then a "no quarterly data yet" prompt with a link to Updates is shown.
  • AC-25 — Given user A requests user B's set id, Then the endpoint returns a bare 404 and the client shows "tracking set not found" — no indication the set exists.

Scoped Dashboard section (rev 2) — AC-SD-1…43

Drill gating

  • AC-SD-1 — Given drill depth 0, Then the section renders collapsed with the hint "Drill into a category, sub-category, or item to populate the Scoped Dashboard"; if expanded, a 3-row lens-total strip (Grand Total / Property / Non-Property, as-of latest) shows and nothing else.
  • AC-SD-2 — Given drill depth ≥ 1, Then the section renders expanded with a scope-specific grid, and no new network request is made.

Depth 1 (category)

  • AC-SD-3 — first row = "Total: {category}"; per sub-category a bold subtotal row + indented item rows; (Grand Total lens only) two split rows "Property portion" / "Non-Property portion"; an "Excluded from total (exclusive)" block for any exclusive descendants.
  • AC-SD-4 — Grand Total lens: sub-category rows show the server-provided subtotal[] verbatim.
  • AC-SD-5 — Property / No-Property lens: sub-category and scope-total rows show a derived sum over only non-exclusive items of the qualifying type; server subtotals are not used; non-qualifying item rows are hidden.
  • AC-SD-6 — changing the lens re-computes all rollup rows and shows/hides split rows and item rows accordingly, within the stated interaction latency, with no API call.

Depth 2 (sub-category)

  • AC-SD-7 — first row = "Total: {sub-category}"; then item rows; split rows only under Grand Total lens and only if the sub-category has mixed item types, else the note "All items in this sub-category are type: X"; exclusive block if any.
  • AC-SD-8 — scope-total = server subtotal under Grand Total lens; derived sum of qualifying non-exclusive items under Property / No-Property; hidden (not zeroed) when no item qualifies.

Depth 3 (single item / leaf)

  • AC-SD-10 — no scope-total, no subtotal, no split, no child rows; a scope identity strip (name, type badge, "Exclusive" badge if set); one balance row across the axis with its deltas; a scope-facts strip (first / last populated period, populated-period count in window, peak + period, trough + period, net change over window, latest Δ amount + %); the note "This scope is a single item; its balance is shown directly."
  • AC-SD-11 / AC-SD-37 — if the item's type fails the active lens, the row is replaced by "This item (type: X) is not a {Property|Non-Property} item; the {lens} lens excludes it." + a working "Switch to Grand Total" action (sets lens, keeps drill).

Exclusive items

  • AC-SD-13 / AC-SD-14 — every exclusive item is an isolated, badged row under an "Excluded from total (exclusive)" header, shown verbatim, never in any scope-total / subtotal / split (verbatim or derived), and not type-filtered by the lens.

Quarterly grid

  • AC-SD-15…18 — one collapsible table per year, years descending, Q1–Q4 each with a Balance and a Delta cell; "–" for no data; "No prior data" on a row's first populated quarter; leading/trailing all-blank years trimmed, interior all-blank years kept; delta = value − nearest earlier populated value (quarter-over-quarter, gaps skipped).

Yearly "as-of year end" grid

  • AC-SD-19 / AC-SD-20 — one column per year (descending); a row's value = the balance of that year's latest populated quarter; the header is annotated with that quarter, e.g. "2025 (as of Q3)".
  • AC-SD-21…24 — a fully-blank year shows "no data" and "—" for delta; year-over-year delta compares a year's as-of balance to the nearest earlier year with an as-of balance (blank years skipped); first populated year → "No prior data"; Δ% is "—" when the prior as-of balance is exactly 0.

Measure

  • AC-SD-25 / AC-SD-26 — the Balance column is always shown; measure only selects the companion delta column (Δ Amount vs Δ %). (This differs from the charts, where measure selects the plotted quantity outright.)

Collapse

  • AC-SD-27…30 — default expanded at depth ≥ 1, collapsed at depth 0; a manual toggle persists across lens / drill (same depth) / granularity / measure changes but reverts to the per-depth default when the drill depth changes; collapse state is client-side only.

Export

  • AC-SD-31…33 — when the section is expanded, the "export current view" CSV also includes the Scoped Dashboard grid rows (row label × period, balance, Δ amount, Δ %), with the # header comment lines recording lens / drill path / granularity / measure / timestamp; when collapsed or at depth 0 the section contributes no rows.

Empty / partial-data

  • AC-SD-34 — scope with zero populated periods → skeleton of "–", info line "No recorded balances for this scope yet", footnote "0 of N periods populated".
  • AC-SD-35 — single exclusive item scoped → item row + persistent banner that it is excluded from all rollups; no scope-total row; scope-facts strip still shown.
  • AC-SD-36 — scope with no items qualifying for the current lens → "No {Property|Non-Property} items in this scope. Switch the lens to Grand Total to see all {n} items." + a working "Switch to Grand Total" action; scope-total row hidden, not zeroed.

Reactivity & ownership

  • AC-SD-38…41 — changing lens / drill / granularity / measure updates the section entirely client-side within the stated interaction latency, with no API call; a drill to depth 0 collapses the section.
  • AC-SD-42 / AC-SD-43 — the section reads only the already-fetched response for the user's own set; it issues no fetch of its own and adds no cross-user surface.

The business-analyst raised 10 acceptance-level clarifications; all are resolved by §4.9 (derived sums are over leaf descendant items only; exclusive items are never type-filtered; the full scope-facts strip appears only at depth 3; a row's first populated period shows "No prior data" not "—"; the CSV carries both a flat row label and a hierarchical drill_path column; interior all-blank quarters within a rendered year are kept, only whole leading/trailing years are trimmed; the "Switch to Grand Total" action changes only the lens).

4. Phase 2 — Solution & UX Design

solution-architect, frontend-engineer

4.1 Solution overview & governing principle

Principle: extend the existing read path; add no new aggregation and no pre-aggregated storage. Analysis fetches the one balance-grid response and performs only thin, pure, unit-tested transforms over it in the browser. The authoritative delta math stays single-sourced on the server; the client replicates compute_series_deltas semantics only for derived buckets that have no server-provided row (item-type buckets; lens-filtered hierarchy subtotals). No new endpoint, no migration.

Reused as-is: the balance-grid endpoint and trackingService.getBalanceGrid; the wire types in services/tracking.ts; the tracking-set <select> pattern; the hand-rolled inline-SVG chart pattern; the dark design tokens and the dataviz categorical palette; the module's bare-404 ownership convention.

New: one route + page, ~14 presentational components, one shared SVG-primitives module, two pure helper libraries (derivations + CSV export) and their tests; a fourth SubLink in the Tracking accordion; a client-side yearly rollup rule; a client-generated CSV export.

4.2 Information architecture & navigation

  • New sidebar sub-link Analysis under the Tracking accordion, after Dashboard / Updates / Category, at /tracking/analysis.
  • Page top-to-bottom priority: (1) global control row — one filter row scoping every chart; (2) drill breadcrumb + "Up"; (3) KPI stat row; (4) chart grid — Trend (hero, full width) → Composition + Breakdown (paired) → Delta-trend (full width) → Comparison (full width, only when comparison ≠ Off); (5) footnote (gap / exclusive-item disclosure).
  • Controls are always global, never per-chart. A single viewState object; every control mutates it and calls one renderAll().
  • The current view state is serialised to the URL query string, so a link is a shareable ad-hoc "view" (this substitutes for saved views this iteration).

4.3 UX layout & wireframe

Shell & regions

4.6 Data model & derivation spec

All functions live in a new pure, unit-tested lib/tracking-analysis.ts. Input is the raw DashboardBalanceGridOut.

Period axis

  • periodsAsc(grid) — reverse grid.years (descending) to ascending, cross-join with quarters [1,2,3,4] → ordered { year, quarter, index }[], length years.length × 4.
  • cellIndex(grid, year, quarter) — cells are aligned to years descending × [1..4] ascending, so index = yearPosDesc × 4 + (quarter − 1). Compute once, reuse for every array.

Quarterly series per node / bucket

Authoritative (use verbatim): leaf item → item.cells; sub-category node → subCategory.subtotal; category node → category.subtotal; lens aggregate → grandTotal / propertyTotal / nonPropertyTotal.

Derived (no server row exists):

  • Lens = Property / No Property on any hierarchy bucket (server subtotals are not type-filtered): bucketBalance(node,p) = Σ over descendant items where lensIncludes(lens,item) of cell(item,p).balance (skip nulls; null if none populated that period).
  • groupBy = itemType at any depth: for each TrackingItem.type under the node, sum its non-exclusive items' balances per period (lens filter also applied).

Derived delta series — replicate compute_series_deltas exactly

lastSeenValue = null
for each period p in periodsAsc:
  v = balance(p)
  if v == null: deltaAmount(p) = null; deltaPercent(p) = null; continue
  if lastSeenValue == null:
     deltaAmount(p) = null; deltaPercent(p) = null          # first data point — null, never 0
  else:
     deltaAmount(p) = v - lastSeenValue
     deltaPercent(p) = (lastSeenValue == 0) ? null : deltaAmount(p) / lastSeenValue * 100
  lastSeenValue = v

Blank slots skipped; year boundaries crossed freely — identical to the server. A golden-fixture parity test (values copied from a real balance-grid response) must lock this against the Python engine.

Yearly rollup — working rule "as-of year end" (ADR-019 / OQ-1)

  • yearlyValue(node, year) = balance of the latest populated quarter within that year (Q4 if present, else Q3, else Q2, else Q1); null if the year has no populated quarter.
  • yearlyAsOfQuarter(node, year) = which quarter supplied the value — shown in every yearly label/tooltip ("2025 — as of Q3 2025").
  • Yearly delta: run the delta algorithm over the yearly series (one value per year, ascending), nearest-earlier-populated-year rule; deltaPercent null when the prior year value is exactly 0.
  • Rationale: balances are stocks (point-in-time net worth), not flows. "Latest populated quarter" ≈ "net worth at year end" and degrades gracefully when Q4 is missing (normal for the current year). "Q4 only" hides the in-progress year (rejected as default, retained as a possible toggle). "Sum of the four quarters" is invalid for stock values (rejected).

Composition shares

  • periodTotal(p): group-by spanning the whole lens (depth 0, category or itemType) → the lens aggregate array value at p. Drilled → category.subtotal at p for Grand Total; the derived node sum for Property / No Property.
  • share(bucket,p) = bucketBalance(bucket,p) / periodTotal(p) when periodTotal(p) is non-null and > 0; otherwise the period renders blank.
  • "At least one populated" rule and exclusive-exclusion honoured. Shares rounded to 0.1%; last band absorbs the residual.

Gap / trim handling

  • Trim: drop leading and trailing periods where every visible series is null (the same rule the dashboard chart uses — a test asserts identical trimmed windows for identical data).
  • Interior gaps: keep the x position; render as a path gap (line), pinched band (area), or absent bar (delta). Never interpolate.
  • First data point: delta is null, never 0.
  • deltaPercent when prior ≈ 0: "≈ 0" defined as exactly 0 to match the server (OQ-3 may widen this or cap displayed magnitude).

4.8 API contract

Decision: no new endpoint. Analysis is built entirely client-side from the existing GET /api/v1/tracking/sets/{set_id}/dashboard/balance-grid response.

Why reuse is sufficient: the response already contains every raw quantity (per-item cells, all subtotals, grandTotal, propertyBreakdown, per-cell deltas); everything Analysis needs is a pure transform. Data scale is solo-investor (tens of periods × a few hundred items) so useMemo recomputation is trivial. The service is already O(1) in queries and recomputes from source each call. If the item does not qualify for the active lens, the row is replaced by the lens-mismatch empty state (§4.9.5).

Lens interaction rule (critical). The server subtotal[] / grandTotal[] are NOT type-filtered — they sum all non-exclusive items regardless of type. So under a Property or No-Property lens a scoped category/sub-category total must never use the server subtotal; it must be a derived sum over only the lens-qualifying descendant items, using the same bucket-sum + TS delta rule lib/tracking-analysis.ts already defines (§4.6). Under the Grand Total lens use subtotal[] verbatim. Exclusive items are always their own badged row and never in any total, verbatim or derived.

5. ADR-019 — Read-only "Analysis" view: client-side derivation over the existing balance-grid, with an "as-of year end" yearly rollup

Status: Accepted (2026-08-30 — user decided all rev-1 open questions; design-only, build not yet scheduled)

Context

The Financial Tracker exposes GET /api/v1/tracking/sets/{set_id}/dashboard/balance-grid → DashboardBalanceGridOut, recomputed from UpdateTrackingList / UpdateTrackingListBalance on every call (6 queries; all grouping / summation / delta done in-memory in Python). It is quarterly only — "years" is a display grouping; there is no yearly aggregation anywhere. Per-cell deltaAmount / deltaPercent are computed server-side by compute_series_deltas (delta vs nearest earlier populated slot; first point → null; % null when prior is exactly 0). The frontend has no chart library; charts are hand-rolled inline SVG. The app is dark-only. Data scale is a single investor. ADR-018 (Original Investment) is in flight and untouched by this work. A read-only Analysis view is wanted: trend, composition, delta-trend; sliceable by amount-type lens, the category hierarchy, and item type; quarterly and yearly; QoQ / YoY comparison; export of the current view. No data entry, saved views, or annotations this iteration.

Decision

  1. Build Analysis entirely on the frontend from the existing balance-grid response. No new endpoint, no pre-aggregated storage, no migration.
  2. Yearly rollup rule = "as-of year end" decided by user, OQ-1. For any series a year's value is the balance of the latest populated quarter within that year (null if the year has none). Every yearly column / label / tooltip is annotated with the as-of quarter ("2025 (as of Q3)"). Year-over-year deltas compare a year's as-of balance to the nearest earlier year that has an as-of balance (blank years skipped, gaps crossed) — identical to the server's nearest-earlier-populated rule; first populated year → null delta ("No prior data"); Δ% null when the prior as-of balance is exactly 0. One new pure helper (asOfYearlySeries) in lib/tracking-analysis.ts; no other derivation changes.
  3. Reproduce compute_series_deltas semantics in a shared, unit-tested lib/tracking-analysis.ts only for derived series (item-type buckets, lens-filtered subtotals, yearly as-of deltas, Scoped Dashboard derived totals) that have no server row; use server-provided deltas verbatim wherever a matching row exists. Unit tests must assert parity with server-produced deltas on the Grand Total lens so drift is caught.
  4. Export = client-side CSV download only decided by user, OQ-4. The file opens with # comment lines recording the applied context (tracking set, lens, drill path, granularity, group-by, measure, comparison selection if any, ISO-8601 timestamp); the body carries the currently visible derived rows, including the Scoped Dashboard grid rows when that section is expanded. No server-side export, no PDF, no formatted printable report.
  5. Charts use the existing hand-rolled inline-SVG pattern; extract a small components/charts/svg-primitives module for reuse across the charts. Do not add a charting library.
  6. New route /tracking/analysis; new 4th SubLink under the Tracking accordion. ViewState is URL-serialised.
  7. Theming = dark-only decided by user, OQ-6. The Analysis view and the Scoped Dashboard section reuse the existing dark "instrument panel" tokens; no prefers-color-scheme or theme-toggle handling in this feature. A future app-wide light theme must revisit these tokens (tracked there, not here).
  8. Feature scope = read-only exploration only locked by user, OQ-7. No saved or named views, no annotations, no real-time / auto / scheduled refresh, no emailed or pushed snapshots. Data loads once per navigation from the single balance-grid endpoint. The only client-persisted state is ephemeral UI preference (section-collapse flags, last view state) in localStorage.
  9. Scoped Dashboard section rev 2. A collapsible card below the KPI StatRow and above the charts reproduces the main dashboard's tabular readout (per-year quarterly grid or yearly as-of grid, scope-total / subtotal / item rows, per-period deltas, Property/Non-Property split, completeness stats) constrained to the current drill scope, reacting to lens + granularity + measure. Renders only at drill depth ≥ 1 (depth 0 = hint + optional lens-total strip). 100% client-side off the same single endpoint. Under Grand Total lens the scope total uses the server subtotal[] verbatim; under Property / No-Property it is a derived sum of lens-qualifying, non-exclusive descendant items. New components ScopedDashboardSection.tsx, ScopedBalanceGrid.tsx, optional ScopeFactsStrip.tsx; pure logic (buildScopedGrid, asOfYearlySeries) in lib/tracking-analysis.ts. ViewState gains scopedDashboardCollapsed?: boolean. The main dashboard's YearTable is not reused (see §4.7). Full spec §4.9.

Alternatives considered

  • ?granularity=yearly on balance-grid, or a dedicated yearly endpoint — rejected: forks the delta engine into two implementations, no benefit at this scale. Acceptable to revisit later if client-side derivation becomes a performance/payload problem (OQ-8).
  • Pre-computed aggregation tables / materialised views — rejected: contradicts the recompute-from-source design; adds migration + drift risk for a solo-scale dataset.
  • Adopt Recharts / visx / Chart.js — rejected: inconsistent with the whole codebase, bundle cost; the required charts fit the existing pattern.
  • Yearly = last calendar quarter (Q4) only, blank otherwise — rejected: blanks any year whose Q4 is unreported even when earlier quarters have data (hides the in-progress current year).
  • Yearly = sum, or average, of the four quarters — rejected: balances are stock quantities, not flows; summing double-counts and averaging has no net-worth meaning.
  • Server-rendered export / PDF / formatted printable report — explicitly declined by the user (2026-08-30), not planned. Adds a backend surface and a templating dependency for a single-user tool where CSV into a spreadsheet covers the need.
  • Ship a light theme alongside — deferred to an app-wide theming effort, not rejected on merit; out of this feature's scope.
  • Reuse the main dashboard's YearTable for the Scoped Dashboard grid — rejected: it is coupled to the full hierarchy tree and the whole-set summary rows; a focused parallel ScopedBalanceGrid sharing only formatting helpers is simpler than the conditional branching reuse would need.

Consequences

Positive: zero backend change, no migration; ships behind one route; the heavy delta math stays single-sourced on the server; charts and the Scoped grid stay visually consistent with the app; fast iteration; derivations are pure and independently testable with golden fixtures; a shareable URL doubles as an ad-hoc "saved view".

Negative:

  • The delta algorithm now exists in Python and TypeScript — used for derived series (Property / No-Property lens subtotals, yearly as-of deltas, Scoped Dashboard derived totals). Parity must be locked by unit tests asserting equality with server-produced BalanceCell deltas on the Grand Total lens, and re-verified whenever the server engine changes.
  • Yearly granularity introduces as-of-quarter annotations everywhere a year is labelled; charts, CSV, and the Scoped Dashboard must all surface the as-of quarter so a year's number is never ambiguous.
  • All recomputation runs in the browser inside useMemo (mitigated by memo keys and an "Other" bucket cap).
  • Dark-only means no theme handling in this feature; a future app-wide light theme must revisit the Analysis view's tokens.
  • The read-only lock means no persistence layer, no write endpoints, no migration; the only client-persisted state is disposable UI preference in localStorage.
  • The Scoped Dashboard's scope facts overlap the page-level KPI StatRow — resolved by making the StatRow scope-aware (SD-OQ-1) so the figures are computed once and shown consistently, with the Scoped Dashboard adding only the coverage facts the StatRow lacks.

Risks

Parity drift (Python vs TS delta engine); yearly-rule surprise; readability of 100%-stacked / snapshot with many categories; sparse-quarter delta-% distortion; Scoped Dashboard vs KPI-row figure redundancy. See §6.

  • Annotations / commentary pinned to a period or series or grid row.
  • Real-time or scheduled auto-refresh; emailed or pushed analysis snapshots.
  • Server-side or PDF export / formatted printable report.
  • Light theme (moves with the app-wide theming effort).
  • A small dedicated read-only aggregation endpoint — acceptable to introduce later if client-side derivation from balance-grid becomes a performance or payload problem at scale (OQ-8); not built now.

7. Assumptions

  1. Route & nav. The view lives at /tracking/analysis as a 4th sidebar sub-link under Tracking. Set id comes from the on-page tracking-set selector (same pattern as the other tracking pages).
  2. Yearly rollup. Decided (OQ-1): yearly value = the latest populated quarter of that year; every yearly label shows the "as of Qx" quarter; YoY delta compares consecutive yearly as-of values with the nearest-earlier-populated rule.
  3. Export. Decided (OQ-4): client-generated CSV (UTF-8 with BOM) of the flattened current view, with # header comment lines recording the applied lens + filters; a second CSV for an active comparison; Scoped Dashboard rows included when that section is expanded. No server report, no PDF.
  4. No backend change. Analysis reads only the existing balance-grid endpoint; its response already carries the three lens aggregates and per-cell deltas.
  5. Default landing view. Lens = Grand Total, granularity = Quarterly, group-by = Category, measure = Balance, full trimmed history, comparison Off, breakdown period = latest populated. (Confirm via OQ-9 / OQ-10.)
  6. Comparison is transient. It operates on the current lens + drill node, never persists, and is cleared when granularity changes.
  7. Exclusive items. Never in any series / subtotal / total / breakdown / export; still reachable as an explicit leaf drill target.
  8. No saved views / annotations / auto-refresh. Locked (OQ-7): read-only exploration only. A URL that encodes ViewState is the only "saved view" and is ephemeral; data loads once per navigation.
  9. Sparse data is normal. Interior blank quarters and short histories are valid; charts skip and trim rather than interpolate.
  10. No schema change. No new table, column, enum, or migration.
  11. Single primary tracking set is the common case, though multiple are supported; each set's Analysis view is independent.
  12. Dark theme only for the shipped view Decided (OQ-6). The companion mockup keeps a light + dark toggle purely as mockup convenience; the spec targets dark-only.
  13. Scoped Dashboard. Renders only at drill depth ≥ 1; at depth 0 the card is collapsed with a hint (plus an optional 3-row lens-total strip if expanded). It ignores groupBy and comparison and always rolls up the natural hierarchy. See §4.9 and the open questions in §8.3.
