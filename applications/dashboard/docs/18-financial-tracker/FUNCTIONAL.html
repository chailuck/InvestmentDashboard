Financial Tracker — Functional Specification

Version: 3.5 (Phase 1 + Phase 2 + Phase 3 + Phase 4 — "Email Dashboard" button added to the Dashboard page)  |  Last updated: 2026-08-29  |  Routes: /tracking/category, /tracking/updates, /tracking/updates/[listId], /tracking/dashboard

1. Overview

The Financial Tracker ("Tracking" in the sidebar) is a personal financial planning module that lets each user record and organise their own financial holdings — bank accounts, property, investment accounts, tax-saving products, materials (e.g. gold, collectibles), and insurance — in a hierarchy they define themselves.

The hierarchy has four levels:

Tracking Set
  └─ Category               (e.g. "Assets", "Liabilities")
       └─ Sub-category      (e.g. "Current Assets", "Property")
            └─ Tracking Item        (e.g. "SCB Savings Account")
                 └─ Initial Investment Ledger   (optional — see §7)

A user can maintain multiple independent Tracking Sets — for example, a personal set and a family set — each with its own category tree. A tracking set belongs to exactly one user; it is never shared or visible to other users.

This document covers Phase 1 (creating and organising Tracking Sets, Categories, Sub-categories, Tracking Items, and the Initial Investment Ledger — §3–§9), Phase 2 (the "Updates" sub-menu — periodic balance snapshots against a tracking set's hierarchy — §11), Phase 3 (the "Dashboard" sub-menu — a read-only quarterly/yearly balance-grid rollup built from the data captured by Updates — §12), and Phase 4 (the "Email Dashboard" button on the Dashboard page, emailing the user their currently-displayed dashboard plus a full backup export — §13).

The sidebar shows a Tracking accordion group (positioned directly below Action Plan, above Analytics) that expands to reveal three sub-links:

3. Tracking Sets

The Category page opens with a Tracking Set selector. If the user has no tracking sets yet, a prompt invites them to create the first one. Creating a set requires only a name (required) and an optional description.

  • Tracking set names must be unique per user — creating a second set with a name you already used is rejected with an error message.
  • A tracking set can be renamed or deleted at any time. Deleting a tracking set permanently removes every category, sub-category, tracking item, and ledger entry beneath it — this cascade happens automatically when the record is deleted.
  • Switching the selected tracking set in the dropdown immediately loads that set's category tree.

3.1 Auto-created default structure

When a new Tracking Set is created, the system automatically creates a starter structure of categories and sub-categories in the same operation, so the user is never left with an empty tree:

Assets
  ├─ Current Assets
  ├─ Long-term Investment
  └─ Property
Liabilities
  ├─ Current Liabilities
  └─ Long-term Liabilities
These auto-created rows are not special or protected in any way — the user can rename, reorder, or delete any of them immediately, exactly as if they had created them by hand. There is no "default" flag anywhere in the UI or data.

4. Categories

Within a Tracking Set, the Category page shows each Category as an expandable card. A category has a Name, an optional Description, and a display Order.

  • Add Category creates a new category at the end of the current list.
  • Each category card offers up/down arrow buttons to reorder it relative to its siblings, plus rename and delete actions.
  • Deleting a category shows a confirmation dialog warning that all sub-categories and tracking items beneath it will also be deleted.

5. Sub-categories

Expanding a category reveals its Sub-categories, each with the same Name / Description / Order fields and the same add / reorder / rename / delete controls as categories, scoped to sub-categories within that one category.

Deleting a sub-category warns that all tracking items beneath it will also be deleted.

6. Tracking Items

Expanding a sub-category reveals its Tracking Items. Creating an item only requires a Name and a Type up front — the remaining fields are filled in afterwards on the item's own detail page (opened by clicking the item, or via the external-link icon next to it).

6.1 Fields

6.2 Fixed type list

The six item types are a closed list — an item cannot be given a type outside this set, and the constraint is enforced consistently whether the request comes from the UI, a script, or a direct API call:

  • Bank account
  • Property
  • Investment Account
  • TaxSaving
  • Materials
  • Insurance

6.3 Item detail page

Clicking a tracking item navigates to its own page where every field except Order can be edited and saved with a single "Save Changes" action. The page shows a breadcrumb back to the Category page and the item's current Order (informational — reordering itself is done from the Category page).

6.4 Reordering and deleting

Items can be moved up or down among their siblings from the Category page's tree view. Deleting an item shows a confirmation dialog; deleting it also removes any Initial Investment Ledger entries recorded against it.

7. Initial Investment Ledger

When a tracking item's Initial Investment Tracking flag is set to Yes, its detail page gains an "Initial Investment Ledger" section beneath the main form. This is a running log of changes to the item's original invested amount over time — separate from any later balance updates.

7.1 Adding entries

Each ledger entry has a Date and a signed Amount:

  • A positive amount records an increase to the invested total (e.g. an additional deposit).
  • A negative amount records a decrease (e.g. a partial withdrawal).
  • An amount of exactly zero is rejected — a zero-value entry carries no meaning in a ledger.

7.2 Running total

The ledger table lists every entry in date order together with a Running Total column — the cumulative sum of all entries up to and including that row — plus a headline "Current total" figure above the table (the sum of all entries).

7.3 Editing and deleting entries

Any entry can be edited (date and/or amount) or deleted from the ledger table. Editing recomputes the running total for every row from that point forward the next time the ledger is loaded.

The ledger section — and the ability to add or view entries — is only available once Initial Investment Tracking has actually been saved as Yes on the item. Toggling the switch on the item's edit form does not reveal the ledger until "Save Changes" is clicked; this prevents the page from querying a ledger that the backend would still reject.

8. The Exclusive flag

Every tracking item has an Exclusive Yes/No toggle, defaulting to No. In this phase, the flag is reserved for future rollup reporting (for example, letting a future dashboard or net-worth summary exclude marked items from a total). It currently has no visible or functional effect anywhere in the application — it is purely stored for later use.

9. Ownership and privacy

Tracking Sets, Categories, Sub-categories, Tracking Items, and Ledger entries are always scoped to the user who created them. There is no sharing, no admin visibility, and no cross-user access — a user only ever sees their own tracking data.

11. Update Tracking Lists ("Updates" sub-menu) — Phase 2

The Updates sub-link lets a user periodically capture a dated snapshot of the latest balance for every tracking item in one of their Tracking Sets — for example, once a quarter — and see how each item's balance changed versus the previous snapshot. Each snapshot is called an Update Tracking List.

11.1 Updates list page (/tracking/updates)

The page opens with the same kind of Tracking Set selector used on the Category page. Once a set is selected, the page shows a table of that set's existing Update Tracking Lists — one row per snapshot — with two columns:

  • Transaction Date — the as-of date the snapshot represents (not necessarily the date it was entered).
  • Quarter/Year — an optional free-text label (e.g. "Q3 2026") the user can attach to the snapshot for their own reference; shown as a dash if left blank.

Rows are listed most-recent Transaction Date first. Clicking a row opens that list's detail page. A Create New List button opens a small modal asking for the Transaction Date (required, pre-filled with today's date) and an optional Quarter/Year label; confirming creates the header and navigates straight to its detail page so the user can start entering balances.

There is no restriction against creating two Update Tracking Lists with the same Transaction Date for the same tracking set — for example, to re-record a snapshot rather than editing the original. Both rows are kept and both are independently visible in the list.

11.2 Update Tracking List detail page (/tracking/updates/[listId])

The detail page shows the same Category → Sub-category → Tracking Item hierarchy as the Category page, but as a read-oriented table rather than an editable tree. For every tracking item in the set's current hierarchy, the row shows:

ColumnMeaning
Item / TypeThe tracking item's name and its fixed type badge (Bank account, Property, etc.)
Latest BalanceAn editable numeric field — the balance recorded for this item on this snapshot. Blank if no balance has been saved for this item on this list yet.
DeltaThe change versus this item's balance on the chronologically previous Update Tracking List for the same tracking set — see §11.4.

The Transaction Date and Quarter/Year label shown at the top of the page can be edited independently of the balances, via a small pencil-icon edit control that reveals inline date/text fields with its own Save/Cancel.

If the tracking set has no items yet (nothing under any category/sub-category), the page shows a message directing the user back to the Category page to add items first, since there is nothing to record a balance against.

11.3 Editing balances — "Save All" pattern

Balances are entered directly into the Latest Balance field for each item. Edits are not saved automatically as the user types or moves between fields. Instead, a single Save All button at the bottom of the page commits every changed field in one action; the button is disabled and shows "All changes saved" when there is nothing pending. This mirrors the same edit-then-explicit-save pattern used on the Tracking Item detail page (§6.3) rather than saving each field the moment it loses focus.

  • Clearing a field back to empty and saving records "no balance" for that item on this list (distinct from a balance of zero, which is a real recorded value).
  • A non-numeric value in a Latest Balance field blocks the Save All action with an inline error until corrected.
  • Saving is all-or-nothing for the batch of changed fields in that click — either every change in the click is recorded, or none are (see TECHNICAL.html §5 for the underlying validation guarantee).

11.4 How the balance change ("Delta") is calculated

For each item, the Delta column compares its Latest Balance on this list against its balance on the closest earlier Update Tracking List in the same tracking set (ordered by Transaction Date, and by creation time for same-date lists). It shows both the signed amount change and, where a meaningful percentage exists, the percent change in parentheses, colour-coded green for an increase and red for a decrease.

SituationWhat the user sees
A previous list exists and both balances are recordedSigned amount and signed percent, e.g. +1,500.00 (+3.00%)
A previous list exists, both balances recorded, but the previous balance was exactly zeroSigned amount only — percent change from zero is undefined and is never shown as a misleading 0% or an error
This is the first Update Tracking List for the set, or the item had no recorded balance on the previous list"No prior data" — shown instead of a fabricated zero, so the user is never misled into thinking a balance went from 0 to its current value
The delta is always calculated fresh when the page is loaded — it is never a stored, cached value. If the user goes back and edits an older list's balance for an item, every newer list's Delta for that same item updates automatically the next time its detail page is viewed, with no extra action required.

A "View previous update list" link appears on the detail page whenever a previous list exists, for quick navigation to compare the two snapshots directly.

11.5 Important design decision: the hierarchy shown is always the CURRENT one, not a snapshot

An Update Tracking List snapshot freezes the balance values the user enters for it — those numbers do not change unless a user manually edits them. It does not freeze the shape of the category/sub-category/item hierarchy itself. Every time an Update Tracking List's detail page is opened, it is built fresh from whatever the tracking set's category/sub-category/item structure looks like right now.

In plain terms, this means:

  • If a tracking item is added to the set today, it will retroactively appear (with a blank Latest Balance and "No prior data" for its Delta) on the detail page of every Update Tracking List ever created for that set, including ones from months or years ago — because opening any of those old lists re-reads the hierarchy as it exists today.
  • If a tracking item, category, or sub-category is later renamed, the old list's detail page shows the current name, not whatever name was in use when that snapshot was originally recorded.
  • If a tracking item is deleted, it (and any balance ever recorded against it) disappears from every Update Tracking List's detail view, past and present, because the deletion cascades to its balance rows and it is no longer part of the current hierarchy being displayed.
This was a deliberate simplicity trade-off, reviewed and approved for Phase 2, rather than an oversight. The application currently has no requirement for point-in-time historical accuracy of the hierarchy's shape — only of the balance values, which are preserved exactly. If a future requirement needs old snapshots to show the category/item structure exactly as it existed at the time, that would require capturing a structural snapshot per list (a bigger redesign) and is not covered by anything in Phase 2.

11.6 Ownership and privacy

Update Tracking Lists and their balance rows follow the same ownership rule as every other Financial Tracker entity (§9): they are scoped to the user who owns the parent Tracking Set, with no sharing or cross-user visibility.

12. Dashboard ("Dashboard" sub-menu) — Phase 3

The Dashboard sub-link gives a user a single, read-only report that rolls up every balance ever recorded via the Updates sub-menu (§11) into one quarterly/yearly grid, laid out with the same Category → Sub-category → Tracking Item hierarchy used everywhere else in the Financial Tracker. It answers "how has my net worth (or any category of it) moved, quarter by quarter and year by year?" without the user having to open each Update Tracking List individually and compare figures by hand.

12.1 Dashboard page (/tracking/dashboard)

The page opens with the same kind of Tracking Set selector used on the Category and Updates pages (§12.2). Once a set is selected, the page loads and renders, beneath the selector, two charts side by side summarising every category's balance across every quarter at a glance — a lines-only Category Trend chart on the left (§12.10) and a stacked-bar Category Breakdown chart on the right (§12.11) — followed by one separate table per year (§12.3), each independently collapsible as a whole unit (§12.5) and each carrying its own Grand Total Summary as its own first rows (§12.4). On narrower screens the two charts stack vertically instead of sitting side by side. Each year's table — including its Grand Total Summary rows — scrolls horizontally on its own when wider than the screen, since a tracking set with many categories/items produces a genuinely wide row; nothing about the page shrinks or reflows columns to force a fit.

The page has no forms, no editable fields, and no save action anywhere — it is a report, not an editor. Balances are entered and corrected exclusively from the Updates sub-menu (§11); the Dashboard only ever displays what has already been recorded there.

12.2 Tracking Set selector

Identical in behaviour to the selector on the Category and Updates pages: it defaults to the user's first Tracking Set once the list of sets has loaded, and switching the selection immediately reloads the grid for the newly chosen set. If the user has no tracking sets yet, the page invites them to create one from the Category page first, since there is nothing to report on otherwise.

12.3 The grid layout — years and quarters

Years are ordered most recent first (descending), reading top to bottom down the page. Each year is rendered as its own separate, self-contained table — its own header bar and its own set of column headers — rather than as a column-group inside one shared wide table; this is what lets a single year be collapsed or expanded independently (§12.5) with no effect on any other year's table. Within a year's table, every quarter (Q1 through Q4) is shown as its own pair of columns — a Balance column and a Delta column — even for a quarter that has no recorded snapshot at all. A year only gets a table at all if the tracking set has at least one Update Tracking List for that year with both a quarter and a year value saved on it (see §11.2 for how those are set); a year is never partially shown with some quarters silently missing from its table.

If two different Update Tracking Lists were both tagged with the same year and quarter (for example, two snapshots both labelled "Q3 2026" — allowed by design, §11.1), the grid shows exactly one of them for that quarter: whichever one was created most recently. The other is simply not used for this report; it remains fully visible and editable on the Updates page as always.

Rows follow the same Category → Sub-category → Tracking Item hierarchy as the Category and Updates pages, always reflecting the current structure — the same "always current, never a point-in-time snapshot" behaviour already established for the Updates detail page (§11.5) applies here too.

12.4 Subtotal rows

Beneath each Sub-category's items, and beneath each Category's sub-categories, a bold subtotal row shows that group's combined balance and delta for every quarter — the sum of every non-Exclusive item beneath it that has data for that quarter (see §12.7 for how Exclusive items are treated). A subtotal cell is populated as soon as at least one item in the group has a value for that quarter; a subtotal is never left blank merely because one sibling item happens to have no history yet.

Each year's table shows its own Grand Total Summary as that table's first rows, directly beneath its column headers and above its Category rows. (This replaces an earlier version of this page, which showed a single Grand Total Summary in its own section pinned above all year tables at the top of the page — that page-top placement no longer exists.) Every year's Grand Total Summary shows the same full-history figures — a single Grand Total row summing every non-Exclusive item in the entire tracking set, followed by two secondary rows, Property Total and Non-Property Total, splitting that same Grand Total between Tracking Items of type Property and everything else (again excluding Exclusive items) — sliced down to that one table's own four quarters, exactly like every other row in the table. These two secondary rows always add up to the Grand Total for any populated quarter. Because these rows are rendered unconditionally at the top of every year's table, they are never hidden by that year's own Category/Sub-category collapse state (§12.5); only collapsing the entire year-table (§12.5) hides them, along with everything else in that table. The Non-Property Total row additionally carries a distinct visual highlight and an inline savings-target progress indicator — see §12.12.

12.5 Collapse and expand controls

Each Category's and each Sub-category's own row doubles as its collapse/expand toggle — clicking it hides or reveals the rows beneath it (a Sub-category's items, or a Category's sub-categories and everything beneath them). Collapsing a group never hides that group's own subtotal row; the subtotal stays visible so the rolled-up figures remain useful even while the detail underneath is tucked away.

Independently, each year's table has its own collapse toggle on its header bar: collapsing a year replaces that entire table with just its header bar (the year label plus a collapsed-state icon), so a user can shrink the page down to just the years they currently care about without affecting any other year's table. Expanding it again restores the full Category → Sub-category → Tracking Item hierarchy for that year, including that table's own Grand Total Summary rows (§12.4). Since the Grand Total Summary no longer has a separate page-top section of its own — it now lives at the top of each year's table (§12.4) — collapsing every year in turn hides every Grand Total Summary along with them; there is no longer a way to see the overall totals while every year is fully collapsed.

A global row of three buttons sits above the grid and bulk-toggles every Category and Sub-category at once: Detail expands everything (every Category and Sub-category open, down to Item rows); Sub-category expands every Category but collapses every Sub-category, so Category and Sub-category subtotal rows are visible while Item rows are hidden; Summary collapses every Category (and, with it, every Sub-category beneath it), leaving only Category subtotal rows visible. This is a bulk convenience layered on top of the per-row toggles, not a replacement for them: after clicking Summary or Sub-category, a user can still re-expand one Category or Sub-category individually by clicking it, without affecting any other group's collapsed state. The grid loads fully expanded (Detail) by default. None of the three buttons affects year-table collapsing, which is controlled solely by each year's own header button.

12.6 Blank quarters and the "no data" convention

A quarter for which no data exists for a given row — whether because no snapshot was ever recorded for that quarter, or because this particular item/subtotal simply had nothing to report that quarter — shows as a dash ("–") in its Balance cell rather than a blank cell or a zero. A zero is a real, meaningful recorded balance and is always shown as "0.00", never conflated with "no data". Every populated Balance and Delta amount on this page is rendered with thousand-separating commas (e.g. "1,234,567.89" rather than "1234567.89"), for readability on larger figures such as the Grand Total.

The Delta cell for a row follows the same convention as the Updates page (§11.4): comparing this quarter's balance against the nearest earlier quarter that actually has data for that same row — not necessarily the column immediately to its left. A blank quarter in between is simply skipped when looking backward for a comparison point, and the search freely crosses from one year into the previous year if that is where the nearest real data point happens to be. If no earlier populated quarter exists at all for that row (e.g. the very first quarter it ever has data), the Delta cell shows "No prior data" rather than a fabricated change. As on the Updates page, a comparison against a previous balance of exactly zero still shows the signed amount changed, but suppresses the percentage (a percentage change from zero is not a meaningful number).

12.7 The Exclusive flag's effect on the Dashboard

A Tracking Item with its Exclusive flag (§8) set to Yes still appears as its own row in the grid, with its own balances and deltas shown normally — it is visually marked with a small "Excl." badge next to its name so this is clear at a glance. However, it is left out of every rollup figure above it: its Sub-category's subtotal, its Category's subtotal, the Grand Total, and the Property/Non-Property breakdown all compute as if that item were not present. This is the first functional use of the Exclusive flag anywhere in the Financial Tracker — in Phase 1 it was reserved but had no effect (§8).

12.8 Read-only by design

Every figure on this page is derived, on the fly, from the Update Tracking Lists already recorded via the Updates sub-menu. There is nothing to type, nothing to save, and no action on this page changes any stored data. If a figure looks wrong, the fix is always made on the Updates page against the relevant snapshot (§11.3) — the Dashboard will reflect that correction the next time it is loaded.

12.9 Out of scope for this phase

A few ideas from the original requirements were deliberately not built as part of this phase — noted here so readers know these are intentional scope decisions, not gaps:

  • The reference spreadsheet's bespoke "Actual asset / Real estate / Total asset" three-way split is not implemented; only the Property vs. Non-Property breakdown described in §12.4 is available.
  • Free-text annotations on individual grid cells are not supported.
  • An alternate layout — "every quarter in a single row" rather than grouped by year — was mentioned as an option in the original requirements but was not built; only the year-grouped grid described in §12.3 exists.

12.10 Category Trend chart (left)

This section, §12.11, and §12.12 document a frontend-only revision to the Dashboard page. No backend endpoint, response field, or database schema changed — every feature described here is built entirely from data the balance-grid response (§12.1, §9.2's getBalanceGrid()) already returns.

Directly beneath the Tracking Set selector, above every year's table, the page shows two charts side by side (§12.1): a lines-only chart titled Category Trend on the left, and a stacked-bar chart titled Category Breakdown on the right (§12.11). Both charts share the exact same quarter range on their x-axis, so a quarter plotted on one is always plotted at the same horizontal position on the other. This section covers the left chart only.

Revised in this version: this chart previously also rendered a stacked bar as a background layer (an earlier revision of this same section). That bar layer has moved to its own chart — see §12.11 — so this chart is now lines only, exactly as it was before that earlier revision.

The Category Trend chart plots one line per Category — the same subtotal figures shown in that Category's subtotal row within each year's table (§12.4) — plus one additional Grand Total line, across every quarter within the tracking set's active history, ordered chronologically left to right (oldest to newest). This is the reverse of the year-tables' newest-first ordering (§12.3); the chart is the one place on this page where the x-axis reads in normal calendar order.

  • A legend above the chart identifies each line by name and color swatch. The Grand Total line is distinguished from every Category line by a dashed stroke and a bold label, not by color alone, so it reads as an aggregate rather than one more category.
  • Hovering anywhere over the chart shows a tooltip for the nearest quarter, listing every series' value for that quarter (or "No data" for a series with nothing recorded then).
  • A quarter for which a given line has no recorded data (the same "no data" condition described in §12.6) is rendered as a genuine gap in that line — it breaks and resumes at the next quarter that has data — never as a fabricated zero or a value interpolated across the gap.
  • The chart always reflects the tracking set's full history and is unaffected by the Detail/Sub-category/Summary view-mode buttons or by any year-table being collapsed (§12.5) — it renders once, independently of those toggles.

X-axis range — trimmed at both ends (revised in this version): "the tracking set's active history" means the chart's x-axis starts at the earliest quarter with any recorded data in any series (Category subtotal or Grand Total) and ends at the latest quarter with any recorded data in any series — both a leading run of blank quarters before the set's first snapshot AND a trailing run of blank quarters after its most recent snapshot are trimmed off the chart entirely. Previously only the leading run was trimmed; a set whose most recent Update Tracking Lists hadn't yet reached the current quarter would show one or more empty trailing quarters on the chart, which no longer happens. An interior gap — a blank quarter sitting between two quarters that do have data — is never trimmed; it still renders as a visible break in the affected line(s), per the gap-handling bullet above. This trimming is chart-only: the per-year tables (§12.3/§12.4) are unaffected and continue to show all 4 quarters of every year, with "–" for any blank quarter, regardless of what the charts trim.

The chart is built entirely from the same balance-grid data already loaded for the tables below it (§12.1) — no separate request is made to produce it.

12.11 Category Breakdown chart (right) — stacked bars and aggregate overlay lines

The right-hand chart, titled Category Breakdown, renders a stacked bar per quarter — one segment per Category — plus two additional aggregate lines drawn on top of the bars: Non-Property Total and Grand Total. It shares the Category Trend chart's exact quarter range (§12.10), including the same both-ends trimming, so the two charts' x-axes always line up. This lets the pair of charts together answer both "how did each category trend over time" (the left chart's lines) and "what did the total split look like in any one quarter, and how does it compare to the two running totals" (this chart) — without cramming both readings onto a single chart.

Revised in this version: in the previous revision of this page, the stacked bars were a background layer on the same chart as the category lines, with no overlay lines of their own. Both changed here: the bars now live on their own chart (this section), and this chart gains the two new overlay lines described below.

Stacked bars

  • Segments: each bar has one segment per Category, sized to that category's own subtotal balance for that quarter — the same figure plotted by that category's line on the left chart (§12.10) and shown in that category's subtotal row in the year tables (§12.4).
  • Stack order: segments are stacked bottom-to-top by ascending Order (§4) — the same display order used for a category's position on the Category page — never by whatever order the underlying data happens to arrive in. The lowest-ordered category is always the bottom segment.
  • Color: each segment reuses the exact same color already assigned to that category's line on the left chart's legend (§12.10). No second color palette is introduced for the bars — a category is identifiable by one consistent color across both charts.
  • Missing data: a category with no recorded data for a given quarter contributes no segment at all for that quarter's bar — never a zero-height or fabricated sliver. This matches the "never fabricate a zero" convention already established for the left chart's line gaps (§12.10) and for blank cells throughout the Dashboard (§12.6).

Non-Property Total and Grand Total overlay lines (new in this version)

Two additional lines are drawn over the stacked bars, each with its own distinct color and dash pattern — neither reuses a Category color nor the other overlay line's exact treatment, so the two are never mistaken for each other or for a category at a glance:

  • Non-Property Total — the same figure shown in each year table's Non-Property Total row (§12.4, §12.12).
  • Grand Total — the same figure plotted by the Grand Total line on the left chart (§12.10) and shown in each year table's Grand Total row (§12.4).

Both lines are traced directly from their own real, independently-recorded data — the same Non-Property Total and Grand Total figures used everywhere else on this page — never derived by reading pixel positions off the stacked bar segments. In the normal case, where every Property-type item lives in its own distinct category rather than being mixed into a non-Property category, the Non-Property Total line will visually land right on the boundary between the topmost non-Property bar segment and the Property segment above it — but this is simply what happens naturally when two independently-correct totals are both drawn on the same scale, not a rule this chart enforces. If a category ever mixed Property and non-Property items together, the Non-Property Total line and that stack boundary would diverge slightly — which would be the chart correctly showing two genuinely different figures, not a bug to fix.

Both overlay lines' current values are shown directly on the chart — next to their line, in the "millions" format already used elsewhere in this app for compact large figures (e.g. "9.50M") — without requiring the user to hover. This is in addition to, not instead of, the normal hover tooltip described below, which continues to show the fuller thousand-comma figure for every series at the hovered quarter.

Shared chart mechanics

  • Hover tooltip: hovering anywhere over the chart shows a tooltip for the nearest quarter, listing every category's value, plus both overlay lines' values, for that quarter (or "No data" for any series with nothing recorded then) — the same tooltip behavior as the left chart (§12.10).
  • Y-axis scale: the chart's vertical scale accommodates whichever is tallest among three things for any given quarter: the stacked category total, the Grand Total line's value, and the Non-Property Total line's value. None of the three is guaranteed to bound the other two, so all three are checked — nothing on this chart is ever clipped at the top.
  • X-axis behavior: the same both-ends trimming described in §12.10 applies here identically, since both charts share one quarter range — the chart never starts or ends with a run of empty bars beyond the tracking set's actual recorded history.
In the rare case where every category is missing data for a quarter but the Grand Total or Non-Property Total line still has a value plotted there (a data inconsistency that should not normally occur), no bar is drawn for that quarter at all, rather than guessing at a single fabricated segment — the two overlay lines still plot normally regardless. This is a deliberately minimal, documented edge-case treatment — not a scenario expected to occur under normal use.

12.12 Non-Property Total highlight and target

Within each year's Grand Total Summary block (§12.4), the Non-Property Total row now has its own distinct visual highlight — a tinted background and border in this app's "info" accent color — clearly distinguishing it from the brand-colored Grand Total row above it and the neutral Property Total row alongside it. Previously all three rows used only two visual tiers (Grand Total, and everything else); Non-Property Total now reads as its own, third tier.

Revised in this version: the Non-Property Total row's Balance VALUES now render bold, matching the existing bold-value treatment already used by every Category and Sub-category subtotal row (§12.4). Previously these Balance values rendered in the same plain/lighter weight as an ordinary item row's Balance — inconsistent with every other subtotal-tier row on the page — which was an oversight, now corrected. (The Delta amount/percent styling was, and remains, the same medium weight used on every row throughout the page — Category and Sub-category subtotal rows never bolded their Delta values either, so there was nothing to fix there.) The row's background/border highlight and its target/progress indicator (below) are unchanged by this fix.

Target and progress

Directly beneath the Non-Property Total row, a lightweight "current / target" indicator shows:

  • The Non-Property Total balance from the most recent quarter with any recorded data across the entire tracking set — not the most recent quarter within that one year's table. This means the same current figure and the same progress bar appear identically in every year's table, since it is one dataset-wide indicator rather than a per-year one.
  • A target amount, defaulting to 20,000,000 THB for a tracking set that has never had a target set. The target is a simple personal savings-style goal, not a system-computed figure.
  • A short horizontal progress bar showing current progress toward the target (capped visually at 100% once the target is met or exceeded).

If the tracking set has no Non-Property data recorded at all yet, the current figure is unavailable and the progress indicator is simply not shown — nothing is fabricated in its place.

Editing the target

The target amount is editable inline: clicking it turns it into a numeric input; pressing Enter or clicking away saves the new value, and pressing Escape cancels the edit and restores the previous value. An invalid entry (blank, zero, negative, or non-numeric) is rejected and the field reverts to the last valid value rather than saving.

The target is a client-side-only display preference, not core financial data. It is stored in the browser's localStorage, keyed per tracking set, and is never sent to or stored by any backend. This was an explicit product decision, not an oversight or a temporary gap:
  • The target is not backed up — clearing browser data, using a different browser, or reinstalling the OS loses it, silently reverting to the 20,000,000 THB default.
  • The target does not sync across devices or browsers — setting it on a laptop has no effect on the same tracking set viewed on a phone or a different browser profile; each is its own independent 20,000,000 THB default until set locally.
  • Because it is scoped per tracking set (not per user account), switching tracking sets on the same device/browser can show a different target for each set, exactly as if each set had always had its own independent goal.

Color convention when the target is met

When the current figure meets or exceeds the target, the current-value text and the progress bar switch to this app's existing "gain" (green) color — the same color already used elsewhere on this page for a positive balance change. Below target, the indicator intentionally uses a neutral color rather than the "loss" (red) color: falling short of a personal savings goal is not the same thing as a balance going down, so this page does not reuse its loss color to describe it.

13. Email Dashboard export — Phase 4

An Email Dashboard button on the Dashboard page (§12.1) lets the user send themselves, by email, exactly what the Dashboard is currently showing them — plus a complete backup of every piece of data behind the whole tracking set — with a single click, so they have an off-app copy of both the report and the raw data without having to screenshot the page or export anything by hand.

13.1 What gets sent, and to whom

Clicking Email Dashboard sends one email containing two things:

  • An HTML table — built from exactly what is on screen at the moment of the click, using the current Detail/Sub-category/Summary view mode and the current collapse/expand state of every year, Category, and Sub-category (§12.5). If a year or a Category/Sub-category group is collapsed on screen, its detail rows are genuinely left out of the email, not merely hidden by styling — someone reading the email in a plain-text or restrictive mail client sees the same rows a screenshot of the current page would show, no more.
  • A full backup of the tracking set, as a JSON file attached to the email — every Tracking Set, Category, Sub-category, Tracking Item, Update Tracking List, Update Tracking List balance, and Initial Investment Ledger entry the user has ever recorded under this tracking set, not only what happens to be visible in the current view. This is the same complete data the Dashboard's figures are computed from, captured as a point-in-time snapshot.
The email always goes to the user's own registered account email address. There is no address field anywhere — on the button, in a dialog, or otherwise — where a different recipient could be entered. This is a deliberate security choice, reviewed and confirmed during this feature's build: the recipient is always resolved from the user's own signed-in session, never typed in by anyone, so there is no way for this feature to be used to send a user's financial data to an address that isn't their own.

13.2 What the button does, step by step

  1. The button builds the HTML table described in §13.1 from data the Dashboard page has already loaded — nothing is re-fetched for this step.
  2. It then requests the full backup snapshot described in §13.1 for the currently-selected Tracking Set.
  3. Once both the HTML table and the backup are ready, it sends them together as one email to the user's own address.
  4. A confirmation message names the address the email was sent to once sending succeeds.

13.3 Button behaviour while sending

The button shows a spinner and is disabled for the duration of the click — a second click cannot start an overlapping send. It always returns to its normal, clickable state again once the attempt finishes, whether it succeeded or failed, so a failed attempt never leaves the button stuck.

13.4 What happens when something goes wrong

Three distinct situations can prevent the email from being delivered, and each is reported with its own message so the user always knows what did or didn't happen — in particular, whether any email was actually attempted:

SituationMessage shownWas an email attempted?
The backup snapshot could not be retrieved"Could not build backup — dashboard not emailed"No — the send is never attempted without a genuine, complete backup attached. This is a deliberate design rule: this feature never sends a partial export.
Email sending is not set up on the server at all"Email is not configured on the server."No — the server rejected the request before attempting to send anything.
The backup was ready and a send was attempted, but the send itself failed"Backup was prepared, but sending the email failed. Try again."Yes — the attempt was genuinely made and genuinely failed; retrying is the correct next step.
These three messages are worded differently on purpose. The first is the only one where the user should not expect to check their inbox at all; the other two both represent an attempted send, so retrying is the sensible response to either.

13.5 Ownership and privacy

The backup snapshot behind this feature is generated from the same tracking set the user already owns and is looking at (§9), using the same ownership rule as everywhere else in the Financial Tracker: a request for a tracking set that doesn't exist or belongs to someone else is rejected identically to any other not-found resource, never confirming or denying that it exists for another user.

13.6 Out of scope for this phase

  • There is no schedule or recurring send for this feature — it is a manual, on-demand, one-click action every time.
  • There is no history or log of previously sent emails visible in the app; the record of what was sent lives only in the user's own inbox.
  • There is no restore/import feature that consumes the backup JSON attachment yet — today it is a one-way export intended to be a safety copy the user holds onto, not something the app itself can currently read back in.
